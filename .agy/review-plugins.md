Проведен аудит кода в папке `plugins`. Система сложная, с большим количеством «защитных» решений (шрамов), обусловленных спецификой закрытого контура и поведением Greenplum/S3.

Выявлено несколько критических дефектов логики, связанных с потерей данных при загрузке архивов и некорректной работой с часовыми поясами, которые не объясняются комментариями.

### 1. Потеря данных при загрузке ZIP-архивов с несколькими файлами
**Файл:** `plugins/ctl_utils.py`
**Функция:** `gp_upload_s3_csv` (вызывает `gp_from_stream` в цикле)

**Что сломается:** Если в S3 лежит ZIP-архив, содержащий более одного файла, и вызван `gp_upload_s3_csv` с параметром `truncate=True`, в итоговой таблице Greenplum останется содержимое **только последнего** файла из архива.
**Причина:** Функция `stream_unzip` выдает файлы по очереди. Для каждого файла вызывается `gp_from_stream`, которая внутри себя открывает новую транзакцию (`with gp_hook.get_conn() as conn: conn.autocommit = True`) и выполняет `TRUNCATE TABLE`. Таким образом, каждый следующий файл из архива полностью стирает данные предыдущего.
**Почему это не объяснено:** Комментарий говорит о «потоковой загрузке», но не предупреждает, что `truncate` в контексте архива превращается в «оставить только последний файл».

### 2. Ошибка сравнения времени событий (Timezone Offset)
**Файл:** `plugins/ctl_core.py`
**Функция:** `ctl_events_mon`

**Что сломается:** Ожидание событий (EVENT-WAIT) будет работать неверно в первые 3 часа после наступления события (для МСК).
**Сценарий:** 
1. `last_dt` (время события из CTL) парсится как наивное (`strptime`). 
2. Затем к нему применяется `.replace(tzinfo=now.tzinfo)`, где `now` — это время с часовым поясом из конфига (Europe/Moscow, UTC+3).
3. Если CTL отдает время в UTC (что стандартно для API), а мы просто «приклеиваем» к нему смещение +3 без конвертации, мы получаем ошибку в 3 часа. 
4. Проверка `now - last_dt < 30 min` будет либо ложно срабатывать (заставляя ждать лишние 3 часа), либо пропускать слишком свежие события.
**Почему это не объяснено:** В коде есть попытка сделать сравнение aware-объектов, но метод `replace` вместо `astimezone` или корректного парсинга часового пояса — это классическая ошибка.

### 3. Ошибка валидации окна условий (Timezone Offset)
**Файл:** `plugins/ctl_core.py`
**Функция:** `ctl_cond_ready`

**Что сломается:** Загрузки будут необоснованно пропускаться (считаться просроченными), если задан `validTillEpoch`.
**Сценарий:** `till_dt` создается из timestamp (обычно UTC) через `fromtimestamp`. Полученное время сравнивается с `datetime.now()`, которое возвращает локальное время сервера. Если сервер в MSK (UTC+3), а эпоха в UTC, то условие `till_dt < datetime.now()` сработает на 3 часа раньше положенного.
**Почему это не объяснено:** Код игнорирует разницу между системным временем и временем в метаданных CTL.

### 4. Нарушение структуры HTML при разбивке фрагментов
**Файл:** `plugins/ctl_core.py`
**Функция:** `ctl_send_html`

**Что сломается:** Отчет в интерфейсе CTL будет «разваленным» или нечитаемым, если HTML-сообщение превышает 5000 символов.
**Причина:** 
1. Логика поиска `</tr>` через `rfind` внутри чанка в 5000 символов не гарантирует успех. Если одна строка таблицы (`<tr>...</tr>`) длиннее 5000 символов (например, большой JSON в ячейке), `cut_pos` станет равен 5000. Разрез произойдет посередине тега или контента.
2. Код принудительно вставляет `</td></tr>` в конец фрагмента и `<tr id="np"><td>` в начало следующего. Если исходный HTML — это не таблица (например, список `<ul>` или просто набор `<div>`), внедрение табличных тегов создаст невалидный DOM.
**Почему это не объяснено:** Комментарий говорит про «целостность тегов», но алгоритм слишком упрощен и полагается на конкретную структуру, которая ничем не гарантирована.

### 5. Падение таска при пустых значениях в дельте
**Файл:** `plugins/ctl_utils.py`
**Функция:** `eval_delta`

**Что сломается:** Таск упадет с `IndexError: string index out of range`.
**Сценарий:** Если в параметрах случайно окажется строка вида `hours=,minutes=5` (пустое значение после запятой). При итерации часть `p[1]` будет пустой строкой, и обращение `p[1][-1]` вызовет исключение.
**Почему это не объяснено:** Нет проверки на длину строки перед обращением по индексу.

### 6. Состояние гонки (Race Condition) при записи заметок
**Файл:** `plugins/utils.py`
**Функция:** `add_note`

**Что сломается:** Потеря информации в заметках DAG/Task при одновременной работе нескольких тасков.
**Причина:** Функция читает текущую заметку из БД (`obj.note`), дописывает к ней текст в памяти Python и сохраняет обратно. Если два таска (например, в TaskGroup) одновременно вызовут `add_note` для уровня `level='DAG'`, они оба прочитают старое состояние, и тот, кто закоммитится последним, сотрет правки первого. 
**Почему это не объяснено:** Несмотря на использование `session.merge` и `session.expire`, операция «чтение-модификация-запись» не является атомарной на уровне СУБД (нет `SELECT FOR UPDATE` или `UPDATE ... SET note = note || ...`).

### 7. Риск переполнения памяти в `s3_IterStream`
**Файл:** `plugins/s3_utils.py`
**Класс:** `s3_IterStream`, метод `read`

**Что сломается:** Падение воркера по OOM при чтении больших файлов.
**Сценарий:** При вызове `read(-1)` (чтение всего потока) выполняется `self.buffer + b''.join(self.iterator)`. 
**Причина:** Метод `join` сначала создает в памяти гигантский байтовый объект из всех чанков итератора, и только **после этого** проверяется условие `if len(data) > MAX_THRESHOLD`. Если файл весит 1 ГБ, воркер упадет в момент `join`, не дойдя до проверки лимита в 512 МБ.
**Почему это не объяснено:** Проверка лимита стоит «постфактум» после самой тяжелой операции.

### Что проверено:
1.  **Логика CTL:** Механизмы TIME-WAIT, EVENT-WAIT, восстановление после обрывов (`ctl_exe_recover`), расчет retry.
2.  **Транспорт:** Обёртки над API (`ctl_api`), Greenplum (`gp_exe`), Postgres (`pg_exe`), потоковая загрузка S3->GP.
3.  **S3:** Парсинг путей, управление TTL, потоковая работа с ZIP/GZIP, расчет ETag.
4.  **Тракт ТФС:** Логика пауз, очередей, разбор XML-квитанций, работа с зеркалами (CH/PG).
5.  **Airflow Utils:** Управление пулами, параметрами запуска, заметками.

### Что осталось непроверенным:
1.  **SQL-процедуры:** Содержимое функций `pr_swf_start_ctl`, `pr_log_ctl` и вьюхи `vw_swf_ctl_log` (находятся в БД, а не в `plugins`). Проверка шла исходя из описанного в коде контракта.
2.  **Kerberos/Vault:** Реальная доступность секретов и работа тикетов (зависит от окружения ОС).
3.  **Провайдеры:** Версии `airflow-providers-amazon` и `airflow-providers-postgres` (предполагалось соответствие Airflow 2.10).

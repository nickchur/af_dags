# discover — карта контекста до решений

Сбор фактов, не решений: карта зоны изменения, конвенции, ограничения — всё
с опорой на первичный источник, не на память. Решения о том, как поступить,
принимаются позже, в grill (skills/grill/SKILL.md); здесь только то, что уже
верно и так.

## Шаг 0. Объяви и прими вход

Объяви: «Использую скилл discover: собираю факты о задаче и коде до любых решений».

Вход — сырая идея, тикет или фраза пользователя о том, что нужно изменить.
Определи зону: репозиторий или модуль, о котором речь.

**Вопросы пользователю — только границы задачи.** Допрос решений — зона
скилла grill; здесь не спрашивай ничего, что можно найти самому.

| | Пример |
|---|---|
| Плохо (допрос решения — это grill) | «Что делать при повторном платеже с тем же `idempotency_key`?» |
| Хорошо (граница задачи) | «Правки касаются только модуля `payments`, или затрагивают весь `billing`?» |

Границу неясно — задай один короткий вопрос и жди ответа. Всё остальное
выясняй сам по коду и докам.

## Шаг 1. Карта зоны изменения

Собери: файлы и модули зоны, связанные тесты, точки входа (API-роуты, CLI-
команды, обработчики событий), конфиги, которые её касаются.

Дели работу на два рода:

- **Сбор — модель дешевле.** Диспетчеризуй параллельно по под-зонам
  (директориям/модулям) дешёвых субагентов: листинг файлов, grep по сущностям
  задачи, список тестов, которые её задевают. Каждый возвращает сырой список
  со своей под-зоны, без интерпретации.
- **Синтез — сильная модель.** Собери сырые списки в одну карту: выяви
  входные точки, зависимости между под-зонами, что из найденного реально
  относится к зоне изменения, а что — шум.

Критерий выхода: карта перечисляет файлы/модули/тесты/точки входа зоны, у
каждого — роль в одну строку.

## Шаг 2. Первичные источники с цитатами

Читай код, доки, тикеты напрямую — не пересказывай по памяти и не доверяй
своему обобщению без проверки. Каждый факт в конспекте несёт цитату:
`file:line` для кода, раздел/дата для доки или тикета.

| | Формулировка |
|---|---|
| Плохо (пересказ по памяти) | «Аутентификация вроде на JWT, токен где-то проверяется» |
| Хорошо (цитата первичного источника) | «Токен проверяется в `src/auth/verify.ts:42`, `verifyToken(header: string): Claims` бросает `ExpiredTokenError` при истёкшем `exp`» |

Нашёл противоречие между кодом и докой/тикетом — зафиксируй оба источника
рядом, не выбирай один произвольно.

Критерий выхода: у каждого факта конспекта — цитата на первичный источник,
ни один факт не держится на «я думаю, что» или «обычно так делают».

## Шаг 3. Ограничения и риски

Перечисли, что нельзя сломать: внешние контракты (публичные API, форматы
сообщений очередей, схемы БД с внешними потребителями), обязательства по
совместимости, требования безопасности/комплаенса, известные хрупкие места
проекта, если они задокументированы.

Каждое ограничение — с обоснованием: кто потребитель, какой контракт, откуда
известно (цитата или прямое указание пользователя на границу из шага 0).

Критерий выхода: список ограничений, ни одного пункта без обоснования «что
именно ломается и для кого».

## Шаг 4. Открытые вопросы — раздели на два вида

Всё, что осталось неясным после шагов 1–3, распредели по двум спискам:

- **Факты, которые ещё найду сам** — ответ существует в коде/доках, просто
  не найден за отведённый проход. Не выноси их пользователю и не отправляй
  в grill — доисследуй или явно пометь как незакрытый пункт карты.
- **Решения для grill** — вопросов с фактическим ответом нет; нужен выбор
  человека (компромисс, приоритет, поведение в неоднозначном случае).

Критерий выхода: каждый открытый пункт лежит ровно в одном из двух списков;
ни один пункт, для которого есть фактический ответ, не попал в список для grill.

## Опционально: одноразовый прототип для design-вопроса

Если открытый вопрос — design-вопрос («эта стейт-модель ощущается верной?»,
«как это должно выглядеть?»), а не факт из кода — построй одноразовый
прототип вместо того, чтобы гадать или откладывать вопрос в grill без опоры.

Правила: одна команда запуска; без персистентности по умолчанию; явно
маркирован как прототип (по имени и месту, не спутать с продакшен-кодом);
живёт в throwaway-ветке, вне основной. В основную ветку и в конспект discover
попадает решение — вывод и, при необходимости, решающий фрагмент (сигнатура,
стейт-машина), помеченный происхождением «из прототипа, discover YYYY-MM-DD»
— не сам прототипный код.

Выбор ветки прототипа (логика vs интерфейс) и правила в деталях —
`references/prototype.md`, читай перед тем как строить прототип.

## Выход: конспект контекста файлом

Сохрани в `docs/sberpowers/discovery/YYYY-MM-DD-<тема>.md`:

```markdown
# Discover: <тема>

- Дата: YYYY-MM-DD
- Зона изменения: <репозиторий/модуль>

## Карта зоны изменения
- `path/to/module` — <роль в одну строку>
- Точка входа: `POST /api/...` — `src/routes/...:NN`
- Тесты: `tests/...`

## Факты
- <факт> — `src/file.ts:42`
- <факт> — doc `docs/....md#раздел`

## Ограничения и риски
- <ограничение> — потребитель <кто>, обоснование <цитата/факт>

## Открытые вопросы

### Найду сам
- <пункт>

### Для grill
- <пункт — решение, не факт>

## Прототип (если был)
- Ветка: логика | интерфейс
- Вопрос: <...>
- Вывод: <...>
- Throwaway-ветка: <имя>
```

## Критерий выхода

- Карта зоны изменения содержит файлы/модули/тесты/точки входа.
- Каждый факт — с цитатой `file:line` или ссылкой на доку/тикет, ни одного
  пересказа по памяти.
- Ограничения и риски перечислены с обоснованием.
- Открытые вопросы разделены на «найду сам» и «для grill», без смешения.
- Конспект сохранён файлом по конвенции пути.

## Терминальное состояние

Есть непустой список «решения для grill» → следующий шаг цикла:
skills/grill/SKILL.md (передай ему конспект как отправную точку). Список
пуст, ограничения и карта закрывают задачу целиком → следующий шаг:
skills/specify/SKILL.md. Назови нужный шаг пользователю и остановись:
скиллы цикла друг друга не вызывают.

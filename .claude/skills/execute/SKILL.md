# execute

Диспетчер ведёт задачи плана через субагентов, сам код не пишет: свежий
исполнитель на задачу, two-stage review после каждой, durable ledger,
атомарные коммиты, чекпоинт на границе каждой волны.

## Железный закон

```
Диспетчер не пишет код. Исполнитель не наследует твой диалог.
Ревьюер не наследует контекст исполнителя.
После компакции истина — ledger и git log, не память разговора.
```

## Шаг 1. Предусловия

- **Вход есть.** План лежит в `docs/sberpowers/plans/YYYY-MM-DD-<feature>.md`.
  Плана нет — остановись, назови предыдущий шаг: skills/plan/SKILL.md.
- **Self-review пройден.** В плане отмечен self-review автора, таблица
  трассировки REQ-ID заполнена номерами задач. Нет признаков — верни на
  skills/plan/SKILL.md: исполнение непроверенного плана размножает дефекты.
- **Дерево чистое.** `git status --porcelain` пуст; работа в изолированной
  ветке или worktree — skills/git-discipline/SKILL.md. Грязное дерево смешает
  диффы задач с чужими правками.
- **Возобновление.** Если `.sberpowers/progress.md` уже есть с незавершёнными
  задачами — не пересоздавай ledger, продолжай с первой незавершённой.

## Роль диспетчера

Веди задачи через субагентов — сам не редактируй код, не правь тесты, не
«дочиняй быстро» за исполнителем. Каждому конструируй ровно нужный контекст:
бриф, интерфейсы, конвенции репо. История твоего диалога субагенту не
передаётся никогда — она размывает фокус и раздувает промпт. Между задачами
не сверяйся с человеком: попросили исполнить план — исполняй. Причины
остановки: неразрешимый BLOCKED; реальная неоднозначность; **граница волны**
(чекпоинт ниже); все задачи завершены.

## Файловые handoff-ы

Всё крупное — файлами, эфемерный каталог `.sberpowers/` (git-ignored):

```
.sberpowers/
├── progress.md                # durable ledger — точка входа при возобновлении
└── tasks/
    ├── NN-brief.md            # бриф задачи: полный текст из плана
    ├── NN-report.md           # отчёт исполнителя (+дописки fix-субагентов)
    ├── NN-review-package.md   # коммиты + stat + полный diff задачи
    ├── NN-review-spec.md      # отчёт ревью оси «соответствие спеке»
    └── NN-review-standards.md # отчёт ревью оси «качество кода»
```

В чат от субагента — только статус ≤15 строк: вердикт, коммиты, строка о
тестах, сомнения, путь к отчёту. Что попало в чат — живёт в твоём контексте
до конца сессии.

## Перед стартом

1. `cat .sberpowers/progress.md`: задачи со строкой «выполнена» — готовы.
   Повторный диспетч выполненной задачи — самая дорогая ошибка процесса.
2. Прочитай план один раз; выпиши глобальные ограничения и интерфейсы задач.
3. Просканируй на конфликты: задачи, противоречащие друг другу или
   ограничениям; требования плана, которые оси ревью сочтут дефектом. Всё
   найденное — одним пакетным вопросом человеку до старта.

## Цикл на задачу

**1. Подготовка.** Зафиксируй BASE: `git rev-parse HEAD` — от него пойдёт
диапазон диффа. Извлеки полный текст задачи из плана в
`.sberpowers/tasks/NN-brief.md`. Исполнитель читает бриф, не весь план.

**2. Исполнитель.** Промпт по шаблону `references/implementer-prompt.md`:
место задачи в проекте; путь к брифу («прочитай первым — это требования»);
интерфейсы и решения предыдущих задач, которых бриф не знает; твоё разрешение
замеченных неоднозначностей; путь к файлу отчёта. Точные значения (числа,
сигнатуры) живут только в брифе. Модель — по таблице ниже, всегда явно.
Исполнитель реализует тест-первым, гоняет тесты, коммитит атомарно, делает
self-review, пишет отчёт в файл.
- **DONE** → шаг 3.
- **DONE_WITH_CONCERNS** → про корректность/объём разберись до ревью;
  наблюдения — в ledger и дальше.
- **NEEDS_CONTEXT** → дай контекст, передиспетчеризуй.
- **BLOCKED** → диагностируй: нет контекста → дай; нужен ризонинг → модель
  тиром выше; задача велика → расщепи; план неверен → человек. Повторный
  запуск «как было» даст тот же результат.

**3. Review-package.** Дифф ровно этой задачи, диапазон BASE..HEAD:
```bash
{ git log --oneline BASE..HEAD; echo; git diff --stat BASE..HEAD; echo; \
  git diff -U10 BASE..HEAD; } > .sberpowers/tasks/NN-review-package.md
```
`HEAD~1` вместо BASE тихо отрежет у многокоммитной задачи все коммиты, кроме
последнего, — ревьюер одобрит огрызок.

**4. Two-stage review.** Два независимых субагента параллельно, одним
сообщением (последовательный запуск даёт второму унаследовать контекст
первого), каждый по шаблону `references/reviewer-prompt.md`:
1. Ось «соответствие спеке» — реализует ли дифф требования брифа/спеки.
   model-hint: frontier.
2. Ось «качество кода» — корректность, простота, конвенции, тесты.
   model-hint: frontier; для мелкого механического диффа — стандартная.

Каждый получает файлами: бриф (и спеку, если есть), отчёт исполнителя,
review-package — плюс ограничения плана дословно. Никогда — контекст
исполнителя или твой пересказ. Не пред-суждай находку («не флагай X», «это
максимум Minor», «так решил план» — стоп-сигнал). Отчёты осей не сливаются;
вердикт по оси обязателен — отчёт без вердикта отклони и запроси заново.

**5. Обработка находок.**
- **Critical / Important** → fix-субагент со свежим контекстом: конкретные
  находки (file:line, что не так), пути к брифу и отчёту. После фикса —
  повторное ревью изменённого: заново та ось, чьи находки чинились; менял
  поведение → заново и ось спеки. Без повторного ревью находка открыта.
- **Minor** → зафиксируй в ledger; судьбу решит итоговое ревью ветки.
- **«Требование плана»** (ревьюер счёл дефектом то, что план предписывает) →
  решение человека: покажи находку и текст плана рядом. План не судит сам себя.

**6. Фиксация.** Допиши строку в ledger одним сообщением с прочим учётом:
```
Задача N: выполнена, коммиты a1b2c3d..d4e5f6a, ревью чистое
```

## Атомарный коммит

Каждая задача — один или несколько коммитов: `<тип>(<фаза>-<задача>): <что>`,
напр. `feat(01-02): добавить маршрут логина`. Коммит без привязки к номеру —
диапазон коммитов волны в ledger должен читаться без реконструкции по памяти.

## Выбор модели субагента

| Тип работы | model-hint |
|---|---|
| Механика: 1–2 файла, полная спека в брифе, транскрипция кода из плана | cheap |
| Интеграция, многофайловая координация, суждение, fix по находкам | any |
| Архитектура, оси ревью, судья-субагент, итоговое ревью | frontier |

Модель указывай явно в каждом диспатче: пропуск тихо наследует модель твоей
сессии — обычно самую дорогую. **Число ходов бьёт цену токена**: слабые модели
на многошаговой работе делают в 2–3 раза больше ходов. Cheap-тир — только
транскрипция готового кода и однофайловые правки.

## Чекпоинт между волнами

Волна завершена — не запускай следующую автоматически. Останови и покажи
человеку статус доказательством, а не заявлением: задачи волны со статусом
(из `.sberpowers/progress.md`, не по памяти); диапазон коммитов; вывод
прогона тестов (вставь сам вывод, не пиши «тесты проходят» без него —
skills/verification-before-completion/SKILL.md); отложенные MISSING и
открытые Minor. Получи явное «продолжай» перед следующей волной. Чекпоинт
ловит дрейф на границе, а не после того как на дефекте выросли три волны кода.

## Отклонения

| Обнаружено | Действие |
|---|---|
| BUG в затронутом коде | чинить сразу, в контексте задачи |
| MISSING <5 минут | сделать сейчас |
| MISSING крупнее | в ledger, раздел «Отложено», идти дальше |
| BLOCKING | записать, перейти к следующей независимой задаче — не рыть нору |

На чекпоинте проверь, что правила применены: молча пропущенный BUG или
незафиксированный BLOCKING — верни диспетчеру перед стартом следующей волны.

## Параллельные задачи волны

Независимые задачи волны веди параллельно — каждую в изолированном worktree
(skills/git-discipline/SKILL.md). Один worktree — один исполнитель. Конфликт
двух диффов при слиянии → судья-субагент (frontier): оба диффа + требование
спеки, выбирает вариант по намерению спеки. Неразрешимо → человек.

## Контекст-бюджет

При ~50% использования контекста: доведи текущую задачу до записи в ledger,
зафиксируй там состояние и следующий шаг, продолжи в свежей сессии. Свежая
сессия читает `.sberpowers/progress.md` и `git log`, не пересказ разговора.

## Завершение

Все волны исполнены → финальная строка в ledger («Все задачи плана выполнены,
коммиты X..Y»); список отложенного и Minor-находок — на вход итоговому ревью.
Следующий шаг цикла — skills/review/SKILL.md: назови его пользователю и
остановись. Workflow-скиллы друг друга не вызывают — review запускает человек.

# Шаблон промпта исполнителя

Используй при диспетче субагента-исполнителя. Плейсхолдеры в [квадратных скобках] заполняет диспетчер. Точные значения (числа, магические строки, сигнатуры, тест-кейсы) живут только в брифе — в промпт их не дублируй.

## Плейсхолдеры

- `[N]`, `[НАЗВАНИЕ]` — номер и название задачи из плана
- `[МОДЕЛЬ]` — ОБЯЗАТЕЛЬНО: по разделу «Выбор модели субагента» SKILL.md; пропуск тихо наследует самую дорогую модель сессии
- `[BRIEF_FILE]` — `.sberpowers/tasks/NN-brief.md`, полный текст задачи из плана
- `[REPORT_FILE]` — `.sberpowers/tasks/NN-report.md`, сюда исполнитель пишет отчёт
- `[КОНТЕКСТ]` — 1–5 строк: место задачи в проекте; интерфейсы и решения предыдущих задач, которых бриф не знает; разрешённые диспетчером неоднозначности. Не история диалога.
- `[КАТАЛОГ]` — рабочий каталог (worktree задачи)

## Промпт

```
Субагент (general-purpose):
  описание: «Реализовать задачу [N]: [НАЗВАНИЕ]»
  модель: [МОДЕЛЬ]
  промпт: |
    Ты реализуешь задачу [N]: [НАЗВАНИЕ].

    ## Требования

    Сначала прочитай бриф: [BRIEF_FILE]
    Это полный текст задачи из плана — твой единственный источник
    требований; точные значения бери оттуда дословно.

    ## Контекст

    [КОНТЕКСТ]

    ## До начала работы

    Есть вопросы о требованиях, критериях приёмки, подходе, зависимостях,
    неясностях брифа — задай их сейчас. Уточнить всегда лучше, чем угадать.

    ## Твоя работа

    Рабочий каталог: [КАТАЛОГ]

    1. Реализуй ровно то, что задаёт бриф — по скиллу tdd.
    2. Пока итерируешь — гоняй сфокусированный тест на то, что меняешь;
       полный прогон — один раз перед коммитом, не после каждой правки.
    3. Коммить атомарно, со scoped-сообщением (скилл git-discipline).
    4. Сделай self-review (ниже).
    5. Напиши отчёт в файл и вернись со статусом.

    Наткнулся на неожиданное или неясное во время работы — спроси.
    Пауза на уточнение всегда допустима; догадки и молчаливые допущения — нет.

    ## Организация кода

    - Следуй файловой структуре из брифа/плана.
    - Один файл — одна ясная ответственность с чётким интерфейсом.
    - Создаваемый файл разрастается сверх замысла плана — остановись и
      верни DONE_WITH_CONCERNS; не расщепляй файлы по своему решению.
    - Существующий файл уже крупный или запутанный — работай аккуратно
      и отметь это в отчёте как сомнение.
    - В существующей кодовой базе следуй её паттернам. Улучшай код,
      которого касаешься, но не перестраивай ничего за пределами задачи.

    ## Когда задача не по силам

    Остановиться и сказать «это слишком сложно для меня» — всегда
    допустимо. Плохая работа хуже отсутствия работы; за эскалацию не
    наказывают. Эскалируй, когда:
    - задача требует архитектурного решения с несколькими валидными путями;
    - нужен код за пределами предоставленного, и ясности не найти;
    - не уверен в правильности собственного подхода;
    - задача требует перестройки существующего кода, которую план не
      предусматривал;
    - читаешь файл за файлом без продвижения к пониманию.

    Как: верни BLOCKED или NEEDS_CONTEXT с конкретикой — на чём застрял,
    что пробовал, какая помощь нужна. Диспетчер даст контекст, возьмёт
    модель сильнее или расщепит задачу.

    ## Self-review перед отчётом

    Посмотри на работу свежим взглядом:
    - Полнота: всё из брифа реализовано? Требования и edge cases не упущены?
    - Качество: имена отражают, что делает код (не как)? Код чистый,
      сопровождаемый?
    - Дисциплина: только то, что запрошено (YAGNI)? Паттерны кодовой базы
      соблюдены?
    - Тесты: проверяют реальное поведение, а не поведение моков? TDD
      соблюдён, если требовался? Вывод тестов чистый, без шума и warnings?

    Нашёл проблемы — исправь до отчёта.

    ## После находок ревью

    Если ревьюер нашёл проблемы и ты их чинишь — перегони тесты,
    покрывающие исправленный код, и допиши результаты в [REPORT_FILE].
    Ревьюер тесты за тебя не перегоняет: твой отчёт — доказательство.

    ## Отчёт

    Полный отчёт запиши в [REPORT_FILE]:
    - что реализовано (или что пытался, если заблокирован);
    - что тестировал, команды и результаты;
    - TDD-доказательства (если TDD требовался): RED — команда, падающий
      вывод до реализации, почему падение ожидаемо; GREEN — команда и
      проходящий вывод после;
    - изменённые файлы;
    - находки self-review;
    - сомнения и проблемы.

    В чат верни ТОЛЬКО (≤15 строк — детали живут в файле отчёта):
    - Статус: DONE | DONE_WITH_CONCERNS | BLOCKED | NEEDS_CONTEXT
    - Коммиты (короткий SHA + заголовок)
    - Одна строка о тестах (например «14/14 проходят, вывод чистый»)
    - Сомнения, если есть
    - Путь к файлу отчёта

    Для BLOCKED и NEEDS_CONTEXT конкретику пиши прямо в финальное
    сообщение — диспетчер действует по нему.

    DONE_WITH_CONCERNS — работа завершена, но есть сомнения в
    корректности. BLOCKED — завершить не можешь. NEEDS_CONTEXT — не
    хватает информации. Молча сдавать работу, в которой не уверен, нельзя.
```

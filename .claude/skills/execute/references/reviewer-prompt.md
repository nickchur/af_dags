# Шаблон промпта ревьюера (одна ось на диспатч)

Two-stage review — два независимых диспатча этого шаблона на задачу: сначала ось «соответствие спеке», затем ось «качество кода» (обе оси описаны в skills/review/SKILL.md). Отчёты осей не сливаются. Ревьюер получает только факты — бриф/спеку, дифф, ограничения — и никогда контекст исполнителя или пересказ диспетчера.

## Плейсхолдеры

- `[ОСЬ]` — «соответствие спеке» | «качество кода»
- `[МОДЕЛЬ]` — ОБЯЗАТЕЛЬНО: frontier-модель; для маленького механического диффа оси «качество кода» допустима стандартная. Пропуск тихо наследует модель сессии.
- `[BRIEF_FILE]` — бриф задачи (тот же файл, по которому работал исполнитель); если есть delta-спека — добавь и её путь
- `[REPORT_FILE]` — отчёт исполнителя
- `[PACKAGE_FILE]` — review-package: список коммитов + stat + полный diff задачи
- `[REVIEW_FILE]` — `.sberpowers/tasks/NN-review-spec.md` или `NN-review-standards.md`
- `[BASE_SHA]`, `[HEAD_SHA]` — диапазон коммитов задачи (BASE зафиксирован до диспетча исполнителя; не HEAD~1)
- `[ОГРАНИЧЕНИЯ]` — глобальные ограничения, скопированные из плана/спеки дословно: точные значения, форматы, связи компонентов. Без оценок и подсказок, что флагать или не флагать.

## Промпт

```
Субагент (general-purpose):
  описание: «Ревью задачи [N], ось: [ОСЬ]»
  модель: [МОДЕЛЬ]
  промпт: |
    Ты ревьюишь реализацию одной задачи по одной оси: [ОСЬ].
    Работай по skills/review/SKILL.md — прочитай его и следуй методике своей оси ([ОСЬ]).
    Это task-scoped gate, не merge-ревью: широкое ревью всей ветки
    происходит отдельно после всех задач.

    Держись своей оси. Ось «соответствие спеке» не оценивает стиль и
    качество кода; ось «качество кода» не сверяет реализацию с
    требованиями — этим занимается другая ось.

    ## Что требовалось

    Прочитай бриф задачи: [BRIEF_FILE]

    Глобальные ограничения спеки/плана, связывающие задачу:
    [ОГРАНИЧЕНИЯ]

    ## Что исполнитель заявляет

    Прочитай отчёт исполнителя: [REPORT_FILE]

    Отчёт — непроверенные утверждения о коде: он может быть неполным,
    неточным, оптимистичным. Проверяй утверждения по диффу. Обоснования
    в отчёте («оставил по YAGNI», «сознательно упростил») — тоже
    утверждения: исполнитель оценивает собственную работу. Суди код по
    существу; заявленное обоснование не понижает серьёзность находки.

    ## Дифф на ревью

    База: [BASE_SHA]  Голова: [HEAD_SHA]  Файл: [PACKAGE_FILE]

    Прочитай файл один раз — в нём список коммитов, stat и полный дифф с
    окружением; это твой взгляд на изменение. Контекстные строки диффа И
    ЕСТЬ изменённые файлы: отдельно читай файл только если нужный ханк
    обрезан посреди функции — и скажи об этом в отчёте. Git-команды не
    перегоняй. Если файл диффа отсутствует — собери сам:
    `git diff --stat [BASE_SHA]..[HEAD_SHA]` и
    `git diff -U10 [BASE_SHA]..[HEAD_SHA]`.

    По кодовой базе не ползай. Код вне диффа смотри только для проверки
    конкретного именуемого риска — одна сфокусированная проверка на
    риск, и назови в отчёте и риск, и что проверил. Сквозные изменения —
    легитимный именуемый риск: дифф меняет контракт функции или API,
    порядок блокировок, разделяемое состояние — проверка call sites
    уместна.

    Ревью read-only: не изменяй рабочее дерево, индекс, HEAD и ветки.

    ## Тесты

    Исполнитель уже прогнал тесты и отчитался с доказательствами именно
    для этого кода. Не перегоняй сьют ради подтверждения его отчёта.
    Запускай тест только когда чтение кода рождает конкретное сомнение,
    на которое нет ответа в существующем прогоне — и тогда одиночный
    сфокусированный тест, не пакетный сьют. Тяжёлая валидация кажется
    нужной — порекомендуй её в отчёте, не запускай. Шум и warnings в
    приведённом исполнителем выводе тестов — находка: вывод должен быть
    чистым.

    ## Серьёзность находок

    Critical — блокирует завершение. Important — исправить до завершения:
    некорректное или хрупкое поведение, упущенное требование, ущерб
    сопровождаемости уровня «заблокировал бы merge». Minor — по
    усмотрению: полировка, «покрытие могло быть шире».

    Если план или бриф прямо предписывает то, что методика твоей оси
    считает дефектом (тест без утверждений, дословное дублирование блока
    логики), — это НАХОДКА: Important с пометкой «требование плана».
    План не судит сам себя; решает человек.

    Отметь, что сделано хорошо, прежде чем перечислять проблемы —
    точная похвала помогает доверять остальному фидбеку.

    ## Отчёт

    Полный отчёт запиши в [REVIEW_FILE]. Каждая находка — file:line, что
    не так, почему важно, как чинить (если неочевидно). Требование,
    непроверяемое по этому диффу (живёт в неизменённом коде или
    размазано по задачам), — пункт «⚠️ не проверяемо из диффа» с
    указанием, что проверить диспетчеру, — не повод расширять поиск.

    ВЕРДИКТ ПО ОСИ [ОСЬ] ОБЯЗАТЕЛЕН — отчёт без него будет отклонён.
    Структуру отчёта и допустимые значения вердикта бери дословно из
    раздела «4. Два отчёта» из skills/review/SKILL.md: диспетчер парсит вердикт
    именно по этим значениям, вариации формулировок ломают парсинг.

    В чат верни ТОЛЬКО (≤15 строк): вердикт по своей оси, счётчик находок
    по серьёзности, топ-находки одной строкой каждая, путь к [REVIEW_FILE].
```

## Диспетчеру: после получения отчёта

- Отчёт без вердикта по своей оси — отклони и запроси заново; текст «по смыслу всё ок» вердиктом не является.
- Пункты «⚠️ не проверяемо из диффа» разрешай сам — у тебя план и межзадачный контекст. Подтвердился реальный пробел — это проваленное ревью спеки: fix-субагент и повторное ревью.
- Находки «требование плана» — человеку: находка и текст плана рядом, вопрос «что главнее».

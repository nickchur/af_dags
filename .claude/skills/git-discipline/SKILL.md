# git-discipline — атомарные коммиты и дисциплина веток

Git-история — источник истины, который переживает сжатие контекста и обрыв сессии: `git log` и ветки остаются, даже когда диалог сжат. Коммит рассказывает одну связную историю на одну задачу; ветка заканчивается явным решением человека, а не тихим исчезновением.

## Железный закон

```
ОДНА ЗАДАЧА — ОДИН КОММИТ.
НИ ОДНА ВЕТКА НЕ ЗАВЕРШАЕТСЯ БЕЗ МЕНЮ ИЗ ЧЕТЫРЁХ ПУНКТОВ.
```

«Закоммичу три задачи разом, потом раскидаю по коммитам» — не атомарность. «Снёс ветку, там всё равно черновик» — не завершение.

## Начало работы

1. **Чистое состояние.** `git status` — рабочее дерево чистое, либо посторонние изменения осознанно застэшены/закоммичены отдельно от новой работы. Начинать поверх чужого незакоммиченного мусора — гарантированная путаница при откате.
2. **Ветка на работу.** Не коммить фичу/фикс напрямую в основную ветку. Имя ветки — по сути работы (`login-route`, `01-02-session-expiry`), не generic `fix`/`update`/`patch`.
3. **Изоляция для параллельных субагентов.** Нужен отдельный рабочий каталог — сначала нативный инструмент CLI-харнесса (`EnterWorktree`, `WorktreeCreate`, флаг `--worktree`). Он сам управляет размещением и очисткой; создавать поверх него `git worktree` вручную — плодить теневое состояние, невидимое харнессу.
4. **`git worktree` — только фолбэк**, если нативного инструмента нет. Путь строго под `.worktrees/<branch>` в корне репозитория, каталог обязан быть игнорируемым до создания:
   ```bash
   git check-ignore -q .worktrees || { echo ".worktrees/" >> .gitignore; git add .gitignore; git commit -m "chore: игнорировать .worktrees/"; }
   git worktree add .worktrees/<branch> -b <branch>
   ```
   Каталог вне `.worktrees/`/`worktrees/` не создавай — от точного пути зависит provenance-gated cleanup при завершении.
5. Один рабочий каталог — один исполнитель. Два субагента в одном дереве конфликтуют по определению; параллельная волна задач — каждому своя изоляция.

## Атомарные коммиты

Одна задача плана — один коммит. Задача распалась на несколько логических шагов — несколько коммитов, каждый ещё меньшего, но цельного scope; не один коммит на всю задачу «для простоты» и не один коммит на несколько задач «чтобы не мельчить».

Формат сообщения: `тип(фаза-задача): суть`.

```
feat(01-02): добавить маршрут логина
fix(01-03): отклонять истёкшие сессии
test(01-04): покрыть краевые случаи логина
refactor(02-01): вынести PaymentValidator
```

Тип — по природе изменения (`feat`/`fix`/`refactor`/`test`/`docs`/`chore`); суть — что стало истинным после коммита, не перечень задетых файлов.

**Плохо** — три задачи, один коммит: `feat(01): логин, сессии и профиль пользователя`.
**Хорошо** — три коммита: `feat(01-01): маршрут логина` / `feat(01-02): хранение сессии` / `feat(01-03): эндпоинт профиля`.

## Отговорка → Реальность

| Отговорка | Реальность |
|---|---|
| «Закоммичу всё разом, потом разберу по коммитам» | Не разберёшь — ручной rebase задним числом дороже, чем коммитить по ходу. |
| «Тесты ещё красные, закоммичу как WIP, доделаю после» | В личном worktree коммить сколько угодно; в общую ветку — только рабочий результат задачи. |
| «Ветка мелкая, обойдусь без меню» | Размер ветки не отменяет решения: merge/PR/оставить/выбросить решает человек через меню. |
| «Просто удалю ветку, она черновик» | Удаление без меню и подтверждения — необратимая потеря без свидетеля. |

## Завершение ветки

### 1. Полный прогон тестов — с доказательством

Перед меню — свежий прогон полного набора тестов, не выборочного, с показанным выводом (0 упавших). Заявление «тесты проходят» по памяти не считается доказательством — см. скилл `skills/verification-before-completion/SKILL.md`. Тесты красные → чинить, меню не показывается.

### 2. Детектируй окружение

```bash
GIT_DIR=$(cd "$(git rev-parse --git-dir)" 2>/dev/null && pwd -P)
GIT_COMMON=$(cd "$(git rev-parse --git-common-dir)" 2>/dev/null && pwd -P)
```

- `GIT_DIR == GIT_COMMON` → обычный репозиторий, именованная ветка.
- `GIT_DIR != GIT_COMMON`, именованная ветка → worktree на именованной ветке.
- `GIT_DIR != GIT_COMMON`, detached HEAD → внешне управляемый воркспейс без ветки.

### 3. Покажи меню — без пояснений

Обычный репозиторий и worktree с именованной веткой — ровно эти 4 пункта:
```
1. Слить локально в <base-branch>
2. Создать Pull Request
3. Оставить ветку как есть
4. Выбросить работу
```

Detached HEAD — ровно эти 3 пункта, без merge:
```
1. Запушить как новую ветку и создать Pull Request
2. Оставить как есть
3. Выбросить работу
```

Пункты — без пояснений рядом: человек выбирает номер. Полные bash-команды на каждый вариант (порядок merge → тесты на результате → cleanup → удаление ветки; discard только по типизированному подтверждению) — `references/branch-completion.md`; читай перед выполнением выбранного варианта.

### 4. Provenance-gated cleanup

Удаляй только то, что создал этот процесс. Признак «нашего» воркспейса — путь под `.worktrees/` или `worktrees/` в корне репозитория. Всё остальное (харнесс создал нативным инструментом, человек создал вручную, чужая ветка или чужой worktree) — не трогай; для нативного инструмента используй его штатный выход/очистку, если она есть, иначе оставь как есть.

Очистка выполняется только для варианта «merge» и «выбросить», и только после того как соответствующее действие уже подтверждено успешным (merge прошёл на слитом результате / discard подтверждён точным текстом). Варианты «PR» и «оставить как есть» — воркспейс остаётся: он ещё нужен человеку.

### 5. История публичных веток неприкосновенна

`git push --force`, `git reset --hard` и любое переписывание истории ветки, у которой уже есть push'нутые коммиты или которую видел кто-то ещё, — только по явной просьбе человека: показать, что именно теряется, и получить подтверждение. По умолчанию force push и hard reset не предлагаются как способ «почистить» историю.

## Красные флаги — стоп

- «Закоммичу все задачи разом, потом раскидаю» — нет, коммит по ходу, по задаче.
- «Отправлю `WIP` в общую ветку, доделаю в следующем коммите» — WIP не идёт в общую историю.
- «Ветку удалю, там всё равно черновик» — без меню и подтверждения не удаляется ничего.
- «Ветка/worktree чужие, но заодно и их приберу» — provenance: чужое не трогаем.
- «Перепишу историю force push-ем, потом объясню» — сначала явная просьба и подтверждение человека, потом действие.
- «Тесты я вроде гонял недавно, меню подождёт» — свежий прогон перед меню, не воспоминание о прошлом.

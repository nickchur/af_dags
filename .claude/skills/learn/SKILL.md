# learn — фиксация знаний по итогам цикла

Механическая фиксация, не творчество: факты уже известны — из спеки, плана,
коммитов и отчётов ревью, — их нужно разложить по файлам. Исключение — формулировка
ADR (см. ниже): там решение нужно не записать, а сжато и точно сформулировать
для будущего читателя без контекста разработки.

## Шаг 0. Проверь вход

Вход — завершённое изменение, прошедшее ревью (соответствие спеке + качество кода)
без неразрешённых находок Critical/Important. Ревью не проводилось или есть
неразрешённые находки → остановись и назови предыдущий шаг: `skills/review/SKILL.md`.
Фиксировать знания по недоревьюженному изменению бессмысленно — «урок» может
оказаться найденным на ревью багом.

## Шаг 1. Собери источники

Прочитай целиком delta-спеку (`docs/sberpowers/specs/`), план
(`docs/sberpowers/plans/`) и `git log` по коммитам этой фичи. Выпиши:

- что было запланировано (задачи плана, REQ-ID спеки);
- что реально сделано (коммиты, сообщения, диффы при необходимости);
- где план и реальность разошлись — задача сделана иначе, пропущена, появилась
  незапланированная — и **почему**.

Критерий: список отклонений с причиной для каждого, не только с фактом.

## Шаг 2. Запиши worklog

Путь: `docs/sberpowers/worklog/YYYY-MM-DD-<feature>.md` (создай каталог, если нет):

```markdown
# Worklog: <фича>

- Дата: YYYY-MM-DD
- Спека: docs/sberpowers/specs/YYYY-MM-DD-<change>.md
- План: docs/sberpowers/plans/YYYY-MM-DD-<feature>.md
- Коммиты: <хэши или диапазон, напр. abc1234..def5678>

## Что сделано
<по пунктам, со ссылкой на REQ-ID и номер задачи плана>

## Отклонения от плана
<что изменилось → почему. Явно «отклонений нет», если их не было.>

## Уроки на следующий цикл
<конкретное правило действия. Пусто недопустимо: идеальный цикл — тоже урок
(«оценка объёма задачи X совпала с реальностью, использовать как калибровку»).>
```

Уроки — не «быть внимательнее». Формула: в следующий раз в ситуации X делать Y
вместо Z, потому что в этом цикле Z привёл к <конкретное последствие>.

| | Формулировка |
|---|---|
| Плохо | «Быть внимательнее с миграциями схемы» |
| Хорошо | «Перед миграцией схемы прогонять её на копии прод-данных: в этом цикле миграция уронила staging из-за NULL в колонке, которую не покрыл ни один тест» |

Критерий: файл существует, все разделы заполнены содержательно, уроки проходят
тест «можно применить как чек-лист на старте следующего цикла без домысливания».

## Шаг 3. Дополни реестр подводных камней

Прочитай `docs/sberpowers/PITFALLS.md` целиком, прежде чем дописывать (заводи
лениво с заголовком `# Подводные камни`). Дедупликация — по корневой причине,
не по тексту: тот же корень другими словами → не новая запись, допиши ссылку на
worklog к существующей. Другой корень с похожим симптомом → новая запись.

```markdown
## <симптом одной строкой>

- **Контекст:** где и когда всплывает
- **Корень:** что на самом деле происходит
- **Как избежать/чинить:** конкретное действие
- **Источник:** docs/sberpowers/worklog/YYYY-MM-DD-<feature>.md
```

Случайное отклонение без характерной для этой фичи корневой причины (не паттерн)
в реестр не идёт — не каждое отклонение это подводный камень.

Критерий: PITFALLS.md обновлён без дублей по корню, либо в worklog явно
«новых подводных камней нет».

## Шаг 4. Обнови traceability в спеке

В таблице Traceability delta-спеки колонка «Задачи плана» уже заполнена; впиши
фактически:

- **Тесты** — реальные пути/имена тестовых файлов или тест-кейсов, покрывающих
  REQ-ID (точный путь, не «см. тесты задачи N»);
- **Статус** — «реализовано» для REQ, покрытых прошедшим ревью; для отложенных
  оставь текущий статус и зафиксируй причину в worklog.

Расхождение между обещанием REQ и реальным покрытием тестом не подчищай молча —
допиши как отклонение в worklog и, если это подводный камень, в Шаг 3.

Критерий: по каждой строке Traceability видно, каким тестом покрыт REQ и в каком
он статусе — без плейсхолдеров «—» там, где REQ реализован.

## Шаг 5. ADR (опционально)

Большинство решений ADR не требуют. Пиши ADR, только если **все три** пункта
верны одновременно (не два из трёх): решение трудно обратить (цена передумать
ощутима); увиденное в коде удивит читателя без контекста; был реальный trade-off
с живыми альтернативами. Хоть один пункт не выполнен → ADR не пишется вовсе;
впиши в worklog одной строкой, какой пункт не прошёл («ADR не нужен: решение
легко обратимо (feature flag)»).

Если тест пройден — файл лениво в `docs/adr/`. Номер: сканируй каталог перед
созданием, `ls docs/adr/ 2>/dev/null | grep -oE '^[0-9]{4}' | sort -n | tail -1`
плюс один (пусто → `0001`). Имя `NNNN-<slug>.md`. Содержимое — 1–3 предложения:
контекст, что решили, почему. Секции Status / Considered Options / Consequences
добавляй только когда реально нужны, не по умолчанию.

Пример хорошего ADR:

```markdown
# Postgres вместо MongoDB для основного хранилища

Данные заказов реляционные (жёсткие связи между заказом, позициями и оплатами)
и требуют транзакционной целостности при отмене. MongoDB рассматривали из-за
гибкости схемы, но отклонили: гибкость здесь не нужна, а транзакции между
коллекциями сложнее, чем в реляционной модели.
```

Плохо — реконструкция протокола совещания на страницу, где решение утоплено в
хронологии. Ценность ADR в точности причины, не в объёме. Фиксируй по горячим
следам: к концу цикла контекст альтернатив размывается, ADR превращается в
восстановление по памяти.

## Шаг 6. Закоммить

Следуй `skills/git-discipline/SKILL.md`. Один атомарный коммит на артефакты этого
цикла: worklog, PITFALLS.md, обновлённая спека — напр. `docs(learn): worklog и
уроки по <feature>`. ADR, если создан, коммить отдельным коммитом.

## Критерий выхода

- Worklog существует по конвенции пути, все разделы заполнены содержательно.
- PITFALLS.md обновлён без дублей по корню, либо явно «новых подводных камней нет».
- ADR написан по тройному тесту, либо тест явно не пройден с указанием пункта.
- Traceability отражает фактические тесты и статус по каждому REQ.
- Артефакты закоммичены атомарно.

## Терминальное состояние

Цикл закрыт: спека реализована, подтверждена ревью, знания зафиксированы файлами.
Новая работа по следующей фиче начинается заново с `skills/discover/SKILL.md` —
назови это пользователю. Следующий шаг запускает человек.

# plan

Превращает delta-спеку в исполняемый план: вертикальные срезы → волны по blocked-by → задачи с интерфейсами, критериями выхода и model-hint.

**План — исполняемый промпт, не документ для чтения.** Пиши его для исполнителя со свежим контекстом: он видит только текст своей задачи, не знает кодовую базу и не читал обсуждений. Всё, что ему нужно — код, сигнатуры, команды, ожидаемые результаты — лежит внутри задачи.

## Процесс

### 1. Прочитай вход — delta-спеку
Вход — `docs/sberpowers/specs/YYYY-MM-DD-<change>.md`. Прочитай целиком. Выпиши дословно все REQ-ID и глобальные ограничения (версии, зависимости, правила именования, платформа). Спеки нет — остановись: предыдущий шаг цикла — skills/specify/SKILL.md.
Критерий выхода: полный список REQ-ID и ограничений выписан.

### 2. Проверь масштаб — контекст-бюджет
План обязан исполняться в пределах ~50% контекста одной сессии. Прикинь объём: число задач × код и тесты на задачу. Не влезает — раздели фичу на последовательные планы, каждый из которых даёт работающий, проверяемый сам по себе результат. Два коротких плана лучше одного на деградирующем контексте.
Критерий выхода: один план ≈ одна сессия исполнения.

### 3. Архитектурная развилка? — design it twice (опционально)
Если в фиче есть развилка дизайна — ≥2 жизнеспособных варианта интерфейса и ошибку дорого обращать — прочитай `references/design-it-twice.md` и выполни протокол: три параллельных субагента (model-hint: frontier), общий бриф, каждому одно своё ограничение дизайна; сравни результаты и дай рекомендацию. Очевидный дизайн — пропусти шаг.
Критерий выхода: сигнатуры выбранного дизайна готовы к переносу в блоки «Интерфейсы».

### 4. Нарежь работу на вертикальные срезы
См. раздел «Вертикальная нарезка» ниже. Результат — список задач-срезов с явными рёбрами blocked-by.
Критерий выхода: у каждой задачи есть «Blocked by: …» либо «нет блокеров»; каждый срез проверяем сам по себе.

### 5. Сгруппируй в волны
- Волна 1 — задачи без блокеров.
- Волна N — задачи, все блокеры которых лежат в волнах 1…N−1.
- Параллелить внутри волны можно только задачи без общего состояния: не трогают одни файлы, не делят мутируемые ресурсы (миграции БД, глобальный конфиг, генерируемые артефакты). Есть общий файл — слей в одну задачу или разведи по волнам.

Критерий выхода: каждая задача ровно в одной волне; у параллельных задач одной волны нет пересечений по файлам.

### 6. Заполни задачи по шаблонам
Используй «Шаблон плана» и «Шаблон задачи» ниже. Шаги пиши в TDD-порядке: тест → прогон с ожидаемым провалом → минимальная реализация → зелёный прогон → commit. Каждой задаче проставь model-hint:

| Тип работы | model-hint |
|---|---|
| Механика: шаблонный код, конфиги, переименования, форматирование | cheap |
| Типовая реализация с тестами, интеграция, суждение в рамках заданных интерфейсов | any |
| Архитектура, дизайн интерфейсов, критика, нетривиальные алгоритмы | frontier |

Критерий выхода: каждая задача заполнена по шаблону, без пустых секций.

### 7. Self-review
Отложи план, вернись к спеке свежим взглядом и прогони чеклист сам:

1. **Покрытие спеки.** Пройди по каждому REQ-ID: укажи задачу, которая его реализует. REQ без задачи — добавь задачу.
2. **Скан плейсхолдеров.** Найди формулы из «Нулевой толерантности к плейсхолдерам». Каждую — замени готовым содержимым.
3. **Согласованность имён и сигнатур.** Сигнатуры в «Производит» ранних задач посимвольно совпадают с «Потребляет» поздних. `clearLayers()` в задаче 3 и `clearFullLayers()` в задаче 7 — баг плана, ловится только здесь.
4. **Полнота задач.** У каждой задачи есть критерии выхода (команда + ожидаемый вывод) и model-hint.

Нашёл проблему — исправь на месте. Критерий выхода: чеклист пройден, правки внесены.

### 8. Traceability
- В каждой задаче стоит строка `REQ:` с идентификаторами из спеки.
- Обнови таблицу трассировки в delta-спеке: каждому REQ-ID — номера покрывающих задач.
- Закоммить план и обновлённую спеку (см. skills/git-discipline/SKILL.md).

Критерий выхода: по таблице в спеке виден путь от любого REQ-ID к задаче.

### 9. Сохрани и передай
Сохрани план в `docs/sberpowers/plans/YYYY-MM-DD-<feature>.md`. Сообщи путь и следующий шаг (см. «Терминальное состояние»).

## Вертикальная нарезка

```
Режь вертикально через все слои, не горизонтально по одному.
Нет точного вопроса или результата — это туман, не тикет: сначала discover.
```

**Плохо** — горизонтальная нарезка по слоям (все модели → все API → весь UI → тесты): ни одна задача не демонстрируема в одиночку, разрыв контракта между слоями всплывает в самом конце, когда переделка задевает три слоя из четырёх.

**Хорошо** — вертикальная нарезка по фиче: «логин по email+паролю — таблица users, POST /login, форма, тест на happy path и на неверный пароль»; «восстановление пароля — blocked by задача 1». Каждая проходит узкой полосой через все задетые слои и работает end-to-end сама по себе.

**Критерии среза (tracer bullet).** Каждая задача одновременно: пересекает все затронутые слои единой узкой полосой (не берёт слой целиком); демонстрируема/проверяема сама по себе; помещается в одну свежую сессию исполнителя. Не проходит хоть один — либо режь дальше по вертикали, либо это горизонтальный кусок слоя (пересобери вокруг наблюдаемого поведения).

**Тест «тикет или туман».** Для каждого кандидата в задачу: можешь сформулировать точный вопрос или результат прямо сейчас (даже если задача заблокирована) — это тикет, режь. Не можешь — это туман: не нарезай его на кусочки заранее, отправь на skills/discover/SKILL.md и вернись, когда исследование снимет туман. Фича целиком может содержать и чёткие тикеты, и туман рядом.

**Blocked by.** У каждой задачи явное поле «Blocked by» — список задач, которые обязаны завершиться раньше. Задача без блокеров — фронтир; несколько таких образуют параллельный фронтир. Порядок в списке — не рёбра графа; без явного поля не выводятся ни фронтир, ни волны.

**Исключение: wide refactor.** Механическое изменение с большим blast radius (переименование колонки, ретайп общего символа по всей базе) вертикальный срез не берёт: один тикет разом ломает тысячи мест. Вместо срезов — expand → migrate → contract:
1. **Expand** — добавь новую форму рядом со старой, ничего не ломая. Одна задача, без блокеров.
2. **Migrate** — перегоняй вызовы батчами (размер по blast radius: пакет, директория). Каждый батч — задача, blocked by expand; CI зелёный на каждом шаге, старая форма ещё жива.
3. **Contract** — удали старую форму отдельной задачей, blocked by все батчи.

Вопрос «фича или wide refactor» решает blast radius, а не размер диффа. Полная механика — skills/refactoring-safely/SKILL.md.

````markdown
**Цель:** одно предложение — что становится истинным после исполнения.
**Архитектура:** 2–3 предложения о подходе.

## Глобальные ограничения
Дословно из спеки, по строке: версии, зависимости, именование, платформа.
Требования каждой задачи неявно включают этот раздел.

## Волны
- Волна 1: задачи 1.1, 1.2 — без блокеров; параллельны (нет общих файлов)
- Волна 2: задача 2.1 (blocked by 1.1), задача 2.2 (blocked by 1.1, 1.2)
````

````markdown
- [ ] Напиши падающий тест:
````

## Критерий размера задачи

Задача — наименьшая единица, которую ревьюер может осмысленно отклонить, приняв соседнюю. Не «N минут». Setup, конфиг, скаффолдинг и документация вклеиваются в задачу, чей результат в них нуждается, а не выделяются отдельно. Каждая задача заканчивается независимо проверяемым результатом.

## Нулевая толерантность к плейсхолдерам

Каждый шаг содержит готовое содержимое: код, сигнатуры, команды с ожидаемым выводом. Следующие формулы — **провал плана**, обнаружил у себя — переписывай шаг:

- «TBD», «TODO», «доделаем позже», «детали уточним»
- «добавить обработку ошибок по обстоятельствам», «добавить валидацию», «обработать edge cases» — без перечня конкретных ошибок и кода
- «написать тесты на вышеописанное» — без текста тестов
- «аналогично задаче N» — без повторения кода и сигнатур: исполнитель видит только свою задачу
- шаг, описывающий «что сделать», не показывая «как» — для кодового шага обязателен код-блок
- упоминание типа, функции или метода, не определённых ни в одной задаче плана

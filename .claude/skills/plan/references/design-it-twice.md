# Design it twice — протокол параллельных вариантов дизайна

Когда читать: из шага 4 скилла plan, при архитектурной развилке. Основа — «Design It Twice» (Ousterhout): первая идея дизайна редко лучшая. Вместо углубления одной идеи — три независимых варианта под разными ограничениями, затем сравнение.

## Когда применять

- Есть ≥2 жизнеспособных варианта интерфейса или модуля.
- Ошибку дорого обращать: публичный контракт, схема данных, шов между подсистемами.
- Спека фиксирует «что», но оставляет открытым «как».

Дизайн очевиден (один разумный вариант, локальное изменение) — пропусти протокол и вернись к шагу 5 скилла plan.

## Протокол

### 1. Составь общий бриф
Один текст, одинаковый для всех субагентов:

- постановка проблемы и затронутые REQ-ID из спеки;
- ограничения спеки дословно;
- пути затрагиваемых файлов и что лежит за проектируемым швом;
- словарь домена — чтобы варианты именовали сущности одинаково и были сравнимы.

Различаются варианты только ограничением дизайна — не брифом.

### 2. Запусти три параллельных субагента
model-hint: frontier — для каждого. Каждому передай бриф плюс ровно одно ограничение:

1. **Минимальный интерфейс.** «Минимизируй интерфейс: 1–3 точки входа, максимум пользы на каждую».
2. **Гибкость.** «Максимизируй гибкость: расширяемость, поддержка многих сценариев использования».
3. **Оптимизация под частого вызывающего.** «Оптимизируй под самого частого вызывающего: типовой случай тривиален».

Каждый субагент возвращает:

1. Интерфейс: сигнатуры, инварианты, порядок вызовов, режимы ошибок.
2. Пример использования глазами вызывающего.
3. Что реализация прячет за интерфейсом.
4. Trade-offs: где дизайн силён, где тонок.

### 3. Сравни и рекомендуй
Сравни варианты по трём осям:

- **глубина** — сколько пользы даёт каждая точка входа;
- **локальность** — где сконцентрируются будущие изменения;
- **размещение шва** — что останется стабильным по обе стороны интерфейса.

Дай собственную рекомендацию: один вариант или явный гибрид, с обоснованием. Рекомендация, а не меню — пользователь ждёт позицию, а не список равновесных опций.

### 4. Зафиксируй решение
Сигнатуры выбранного дизайна перенеси в блоки «Интерфейсы: потребляет / производит» задач плана — это единственное место, откуда их увидят исполнители. Если выбор проходит тройной тест (трудно обратить + удивит без контекста + реальный trade-off) — зафиксируй короткий ADR при закрытии цикла (skills/learn/SKILL.md).

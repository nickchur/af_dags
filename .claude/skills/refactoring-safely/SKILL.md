# refactoring-safely — рефакторинг под зелёными тестами

Рефакторинг меняет структуру кода, не поведение. Единственный способ доказать, что поведение не сдвинулось, — тест, зелёный до правки и зелёный после. Без этого доказательства «рефакторинг» — переписывание вслепую с рефакторингом в названии коммита.

## Железный закон

```
РЕФАКТОРИНГ ТОЛЬКО ПОД ЗЕЛЁНЫМИ ТЕСТАМИ.
```

Нет тестов на участок — рефакторинг не начинается. Сначала характеризационные тесты текущего поведения (см. ниже), потом структурная правка. Тесты красные или их нет вовсе — это не площадка для рефакторинга, а площадка для написания тестов сначала (test-driven-development) или для skills/systematic-debugging/SKILL.md.

## Рефакторинг ≠ фича

Поведение зафиксировано на весь рефакторинг. Любое наблюдаемое изменение — новая фича или фикс, а не рефакторинг, и подчиняется своему циклу: сначала красный тест, потом код. Смешение обоих в одном шаге или одном коммите — красный флаг: если тесты упадут, непонятно, упали они от смены структуры или от смены логики.

**Плохо** — один коммит, два намерения:
```
refactor: extract PaymentValidator + добавить проверку лимита в валидации
```
**Хорошо** — два коммита, два цикла:
```
refactor(payments): extract PaymentValidator          — поведение не меняется, тесты зелёные
feat(payments): add limit check to PaymentValidator    — новый красный тест, потом код
```

## Характеризационные тесты и швы

Нет тестов на участок — это не повод рефакторить «на глаз». Сначала зафиксируй тестами то поведение, которое есть сейчас (даже если оно неидеальное — задача теста не оценивать поведение, а закрепить точку отсчёта для сравнения до/после).

Код без внешних зависимостей (чистые вычисления, in-memory состояние) — тестируй напрямую, характеризационный тест ничем не отличается от обычного.

Код завязан на ввод-вывод (БД, сеть, файловая система, время) и напрямую не тестируется — найди **шов**: точку, где зависимость можно подставить тестовым дублёром, не трогая поведение кода (параметр конструктора, инъекция, интерфейс на границе). Подставь дублёр только для того, чтобы получить характеризационный тест — это не рефакторинг архитектуры зависимостей, а минимальная подготовка полигона для безопасного шага дальше.

## Малые шаги

Один шаг — одно структурное изменение (переименование, извлечение, перенос). После каждого шага — полный прогон тестов, не выборочный.

- Шаг прошёл зелёным → коммить и переходи к следующему.
- Шаг не прошёл → откати именно этот шаг (`git checkout`/`git reset` к состоянию до него), не отлаживай поверх сломанного. Отладка на руинах смешивает причину провала с новым кодом поверх и убивает саму гарантию малого шага — маленький откат стоит секунды, отладка следующего слоя поверх сломанного стоит часы.

## Wide refactor: expand → migrate → contract

Механическое изменение с широким **blast radius** — переименование колонки, ретайп символа, используемого по всей кодовой базе — не проходит малыми независимыми шагами напрямую: правка в одной точке разом ломает тысячи вызовов, и откатить шаг целиком уже нельзя.

1. **Expand.** Добавь новую форму рядом со старой (новое поле/колонка, новая перегрузка типа, новая сигнатура) — старая продолжает работать, ничего не сломано. Один коммит, тесты зелёные.
2. **Migrate.** Переводи вызовы на новую форму батчами; размер батча — по blast radius (пакет, директория, модуль), не по вкусу. Каждый батч — свой коммит, полный прогон тестов после каждого. CI держится зелёным на каждом батче именно потому, что старая форма ещё жива рядом — откат одного батча не требует отката всех.
3. **Contract.** Удали старую форму отдельным коммитом, когда ни одного вызова старой формы не осталось — это подтверждается поиском по кодовой базе, не памятью.

Отдельный случай — батч сам по себе не держит CI зелёным (например, переключение затрагивает слишком спаянные точки, разделить дальше некуда). Тогда батчи продолжают идти последовательно и оставаться атомарными коммитами, но зелёный статус обещается не на каждом батче, а один раз — на финальном шаге «интеграция и проверка» после того, как все батчи легли. Это исключение из «тесты зелёные на каждом шаге», а не отмена самого правила: батчи внутри такой последовательности не публикуются как самостоятельно готовые, пока не пройден финальный шаг.

## Предупреждение: объём генерации — предиктор деградации

Чем больше сгенерированного кода легло в фичу за один проход (особенно кода, сгенерированного моделью), тем выше вероятность дублирования логики, размытых границ модулей и структурной деградации — генерация оптимизирует «работает сейчас», не «не дублирует то, что уже есть в кодовой базе». Крупная генерация — сигнал запланировать отдельный рефакторинг-проход сразу следом: дедупликация, выпрямление структуры, схлопывание почти одинаковых функций — пока деградация не закрепилась как норма для следующей генерации поверх неё.

## Отговорка → Реальность

| Отговорка | Реальность |
|---|---|
| «Заодно улучшу и логику, раз уж всё равно тут» | Рефакторинг фиксирует поведение; улучшение логики — фича со своим красным тестом и своим коммитом. Смешение прячет причину, если тесты упадут. |
| «Тесты потом допишу, сейчас важнее structural cleanup» | Без теста нет доказательства, что поведение не сдвинулось, — «рефакторинг» становится переписыванием вслепую. Характеризационный тест — первый шаг, а не отложенный. |
| «Это же просто переименование» (при широком blast radius) | Переименование колонки или ретайп символа с сотнями вызовов — wide refactor по blast radius, не по размеру диффа. Один коммит не удержит CI зелёным; нужен expand→migrate→contract. |

## Красные флаги — стоп

- Посреди рефакторинга наблюдаемое поведение изменилось, даже «к лучшему» — останови, вынеси в отдельный фиче-коммит со своим красным тестом.
- Diff растёт несколько шагов подряд без прогона тестов между ними — прогони сейчас, не копи риск на потом.
- Мысль «откатывать уже дороже, чем дочинить» — это симптом, что шаг был не атомарным; при малом шаге откат всегда дешевле правки поверх сломанного, если мысль звучит иначе — шаг был слишком большим.

## Атомарные коммиты

Каждый шаг — expand, каждый батч migrate, contract, каждое малое структурное изменение — свой коммит со scoped-сообщением, не батч из нескольких шагов в один коммит. Дисциплина коммитов, веток и завершения работы — skills/git-discipline/SKILL.md.

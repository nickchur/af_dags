# review — ревью по двум осям

Один проход, две независимые оси. Отчёты держи РАЗДЕЛЬНО и не сливай в общий список: код может пройти одну ось и провалить другую («соответствует спеке, но написан плохо» и «написан отлично, но не то») — это два разных сигнала, слияние маскирует один другим.

- **Ось A — соответствие спеке:** делает ли код то, что требует спека — не больше и не меньше.
- **Ось B — качество кода:** корректно, протестировано, читаемо, безопасно.

## 1. Собери вход

- **Delta-спека:** `docs/sberpowers/specs/YYYY-MM-DD-<change>.md` (секции ADDED / MODIFIED / REMOVED, требования с REQ-ID). Нет спеки — ось A невозможна: назови пользователю предыдущий шаг цикла (skills/specify/SKILL.md) и не суди по здравому смыслу или коммитам.
- **Полный diff ВСЕЙ работы:** диапазон коммитов, не последний. `git diff <base>..<head>`, где `<base>` — точка перед началом работы (первый коммит задачи/волны из плана или merge-base с основной веткой), `<head>` — текущее состояние. `git diff HEAD~1` теряет остальные задачи волны. `<base>` неочевиден — спроси пользователя.
- **Стандарты репозитория**, если есть (CONTRIBUTING.md, coding standards, конвенции) — пути. Отсутствие не блокирует ось B.

Прежде чем ревьюить: `git rev-parse <base>` резолвится, diff не пуст. Иначе стоп здесь.

Свежий контекст: работай только с этими артефактами. История автора, его чат, обоснования решений, отчёт исполнителя в контекст не входят. Отчёт исполнителя («REQ-003 сделан», «упростил по YAGNI») — неподтверждённые заявления: проверяй по диффу, обоснование не понижает серьёзность.

## 2. Ось A — соответствие спеке

Спека — единственный источник истины; код меряется спекой, не наоборот.

1. Выпиши все требования с ID (нет ID — пронумеруй S1, S2, …), включая REMOVED.
2. Прочитай diff целиком (контекстные строки диффа — и есть изменённые файлы). Код вне диффа открывай только под именованный риск (изменённый контракт → сайты вызова) и фиксируй, что проверил.
3. По каждому требованию классифицируй:
   - **реализовано** — файл:строка;
   - **MISSING** — в спеке есть, в коде нет (сюда же REMOVED-требование с ещё живым кодом; «реализованное» только в отчёте исполнителя);
   - **MISUNDERSTOOD** — реализовано иначе, чем требует спека (не тот контракт/поведение/задача); цитируй строку спеки и файл:строку;
   - **⚠️ не проверяемо по диффу** — поведение в неизменённом коде или размазано по задачам; помечай, поиск не расширяй.
4. Обратный проход: каждый ханк, не привязанный ни к одному требованию, — кандидат в **EXTRA** (код вне спеки: out-of-scope, преждевременные абстракции). Механические следствия (импорты, регистрация модуля) — не EXTRA.

**Вердикт оси A (обязателен, первой строкой):** соответствует (все проверяемые реализованы, MISSING/MISUNDERSTOOD/EXTRA нет) | частично соответствует (ядро есть, но есть расхождения, не ломающие цель) | не соответствует (MISSING/MISUNDERSTOOD по требованию, без которого цель не достигнута). ⚠️-пункты вердикт не блокируют.

## 3. Ось B — качество кода

Находка без файл:строка и уровня серьёзности — не находка. Документированный стандарт репозитория побеждает общие эвристики; что гарантирует тулинг (линтер, форматтер, типизация) — не отмечай.

Оси проверки:

1. **Корректность** — логика ханков, обработка ошибок (проглоченное исключение — находка), краевые случаи, off-by-one, гонки при разделяемом состоянии. Изменён контракт функции — проверь сайты вызова.
2. **Тесты** — проверяют реальное поведение (вызов → наблюдаемый результат). Тест мока или дословно повторяющий реализацию — Important; тест без утверждений — Important; краевые случаи покрыты; шум/предупреждения в выводе — находка.
3. **Читаемость** — имена раскрывают назначение, одна ответственность, дословное дублирование блоков, ханк понятен без археологии.
4. **Безопасность** — секреты/токены в диффе, инъекции (SQL/командные/шаблонные), валидация внешнего входа на границе, чувствительные данные в логах.

Доп. чеклист (только реальные находки): производительность (N+1, лишние проходы, блокирующие вызовы в горячем пути); консистентность API (именование, коды ответов, формат ошибок как у соседей); актуальность документации.

Большой объём сгенерированного кода — предиктор деградации: чем больше diff, тем пристальнее ревью. Структурное дублирование — Important, направляй автора к skills/refactoring-safely/SKILL.md.

**Шкала:** Critical (потеря/порча данных, уязвимость, секрет, сломанное существующее поведение) | Important (хрупкая логика, проглоченные ошибки, тесты без реальных проверок, дублирование, дыра валидации) | Minor (стиль, полировка, шире покрытие). Калибруй честно — не всё Critical; инфляция обнуляет шкалу.

**Вердикт оси B (обязателен, первой строкой):** принято (пусто в Critical и Important) | требует исправлений. Дай конкретные сильные стороны с файл:строка — точная похвала калибрует доверие к отчёту.

## 4. Два отчёта

Оба отчёта — отдельными блоками под своими заголовками, каждый ≤400 слов, начинается с вердикта. Формат находки: `файл:строка — что не так — почему важно — как исправить`.

```
## Ось A — соответствие спеке
Вердикт: соответствует | частично | не соответствует
Перечень по REQ-ID: REQ-001 ✅ api/auth.py:42 · REQ-002 ❌ MISSING · REQ-003 ❌ MISUNDERSTOOD (спека: 202 с job-id; код: 200 без id) api/jobs.py:17
EXTRA: retry в http-клиенте — lib/client.py:88

## Ось B — качество кода
Вердикт: принято | требует исправлений
Сильные стороны: <конкретно, файл:строка>
Находки: Critical / Important / Minor
```

Итоговая строка статуса — раздельная: «спека: <вердикт>, качество: <вердикт>». Не выбирай «главную» проблему поперёк осей.

## 5. Цикл фиксов

Блокирующие: ось A — все MISSING/MISUNDERSTOOD/EXTRA (⚠ не блокируют); ось B — все Critical/Important. Нет блокирующих по обеим осям → шаг 6.

На каждую итерацию:

1. Раздели находки: **BUG** (код делает не то) — фиксируй кодом; **разошедшаяся спека** — см. 5.1, кодом не фиксируй; **EXTRA** — см. 5.2, сначала решение человека.
2. Фиксь по одной: верифицируй находку против кода перед правкой (ревьюер может ошибаться), прогон тестов после каждой, порядок Critical → Important. Свежий контекст без истории автора и ревью. Возражай техническими аргументами, не перформативными согласиями.
3. Commit (skills/git-discipline/SKILL.md).
4. Повторная проверка: перепрогони ту ось, что нашла BUG, по диффу фикса плюс исходные находки — каждая закрыта? Неизменные ханки с нуля не гоняй.
5. Новые блокирующие или незакрытые — повтори с п.1. Ось A пройдена только с вердиктом «соответствует» («частично» = незакрытые находки).

Minor обеих осей в цикл не идут — зафиксируй текстом, исправление на усмотрение автора.

### 5.1 Фикс — не код, а спека
MISSING/MISUNDERSTOOD иногда значит, что спека требует ошибочное, невозможное или противоречивое. Это решает человек: если для закрытия пришлось бы писать код по заведомо неверному требованию — останови цикл, изложи расхождение пользователю, не фиксь вслепую.

### 5.2 EXTRA — решает человек
EXTRA — код вне источника истины. Два пути: удалить код (фикс по п.2) или узаконить — дополнить спеку (следующий шаг specify). Пока человек не выбрал — находка блокирующая.

## 6. Терминальное состояние

- Обе оси пройдены (спека: соответствует; качество: принято) → следующий шаг цикла: **learn** (skills/learn/SKILL.md). Назови его.
- Ось A провалена из-за самой спеки (5.1) либо человек узаконил EXTRA (5.2) → следующий шаг: **specify** — исправить спеку, не код. Сообщи явно и остановись.
- Иначе — оставайся в review, пока обе оси не пройдены или человек не решил по 5.1/5.2.

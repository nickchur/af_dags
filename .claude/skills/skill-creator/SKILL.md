# Создание скиллов

Скилл — код, управляющий поведением агента, а не проза для человека. Цель — predictability: агент проходит один и тот же процесс на каждом запуске. Создание скилла — TDD, применённый к тексту: тест — pressure-сценарий на субагенте, RED — baseline без скилла, GREEN — минимальный текст, REFACTOR — закрытие лазеек.

## Железный закон

```
НЕТ СКИЛЛА БЕЗ ПРОВАЛЬНОГО ТЕСТА
```

Применим и к правкам: правка начинается с теста — нового сценария или прогона сохранённых `references/pressure-tests.md`, — показавшего провал или пробел. Потом текст.

Написал текст до baseline? Удали и начни с шага 1. Удалить — значит удалить: не «черновик», не «адаптирую по ходу». Baseline после написания текста измеряет не поведение агента, а твою способность его угадать — это не тест.

## Роутинг моделей

Проектирование — тип провала, сценарии, текст, анализ рационализаций — веди на frontier-модели. Прогоны сценариев — субагентами на cheap-модели: прогонов много, они механические, свежий контекст на каждый прогон обязателен. Субагент, видевший предыдущий прогон или обсуждение скилла, испорчен как тест.

## Процесс

### 1. Определи тип провала

Сформулируй одной фразой: «без скилла агент делает X, а должен Y» — или для скиллов-возможностей «агент не умеет Z, скилл даёт Z». Классифицируй провал по таблице «форма инструкции ↔ тип провала» (ниже): от типа зависит и форма текста, и формат теста. Проверь, что провал не закрыт существующим скиллом набора; закрыт частично — расширяй существующий тем же процессом, а не плоди дубль.

### 2. Напиши pressure-сценарии

Pressure-сценарий — тестовый промпт с реалистичной задачей, где агент без скилла ошибается предсказуемо. Минимум 3. Формат теста и типы давления зависят от типа скилла — прочитай `references/pressure-testing.md`. Рабочий сценарий: заставляет выбрать и действовать, а не рассуждать; конкретные варианты; реальные пути, сроки, последствия; для дисциплинирующих — 3+ давления разом (время + sunk cost + авторитет + усталость). Запиши в `references/pressure-tests.md` будущего скилла.

### 3. RED — baseline без скилла

Прогони каждый сценарий cheap-субагентом с чистым контекстом, БЕЗ текста скилла. Зафиксируй дословно: какой выбор сделал, какими словами оправдал. Формулировки рационализаций копируй как есть — из них соберётся таблица «Отговорка → Реальность» и красные флаги. Провал не воспроизвёлся нигде — лечить нечего: либо скилл не нужен, либо сценарии не давят (усиль и повтори).

### 4. GREEN — минимальный текст

Напиши текст, закрывающий именно зафиксированные на шаге 3 рационализации, без разделов под гипотетические случаи. Стиль и структуру бери из контракта ниже. Прогони те же сценарии cheap-субагентами, теперь С текстом в контексте. Выход: субагент выполняет целевое поведение во всех сценариях и ссылается на разделы скилла как на основание.

### 5. REFACTOR — закрой лазейки

Субагент нарушил правило с текстом на руках — регрессия. Зафиксируй новую рационализацию дословно и закрой четырьмя правками разом (контрпункт в правиле, строка таблицы отговорок, красный флаг, симптом в description) — детали в `references/pressure-testing.md`. Повтори прогон. Субагент упорно проваливается — проведи мета-тест: спроси его самого, как переписать скилл. Каждая итерация приносит новую лазейку — цикл продолжается, публиковать рано.

## Контракт формата Agent Skills

- **Раскладка плоская**: `skills/<name>/SKILL.md`. Вложенные категории большинством CLI (Claude Code, Codex, OpenCode, Gemini) не обнаруживаются — каталог скилла лежит прямо в `skills/`. Вспомогательные материалы — в `references/` внутри каталога скилла; утилиты — в `scripts/`.
- **Frontmatter — ровно два поля**: `name` и `description`. Никаких version, category, invocation, model-hint.
- **`name`** = имя каталога скилла: kebab-case, ≤64 символа, без слов `claude`/`anthropic`, уникален в наборе.
- **`description`** — одна физическая строка YAML (без `>`, `|`, переносов), на русском, от третьего лица, отвечает «что делает + когда использовать» с конкретными триггер-фразами. Целься в 200–500 символов, жёсткий потолок 1024, без XML-тегов.
- **Тело** — русский, повелительное наклонение, технически плотно. Целься в 80–250 строк. Устоявшиеся термины (TDD, frontmatter, diff, worktree) — латиницей без перевода.

## Description = только триггеры

Description — индекс для выбора скилла, не конспект содержимого. Формула: «что делает» + «Использовать когда …» с 4–6 конкретными фразами пользователя и ситуациями, включая неявные (симптомы, ошибки, состояния репозитория).

Задокументированный эксперимент: description со сводкой процесса («ревью кода между задачами») привёл к тому, что агент исполнил description вместо тела — сделал одно ревью там, где тело требовало два. Замена на чистые триггеры вернула агента в тело. Сводка процесса в description — кэш, который агент возьмёт вместо чтения скилла.

## Форма инструкции ↔ тип провала

Форма, лечащая один тип провала, доказанно ухудшает другой.

| Провал (baseline) | Правильная форма | Неправильная форма |
|---|---|---|
| Знает правило, нарушает под давлением | Железный закон (формула в code-fence) + таблица «Отговорка → Реальность» + «Красные флаги — стоп» | Мягкие советы («предпочитай…») |
| Результат не той формы (раздутый промпт, зарытый вердикт) | Позитивный рецепт: из каких частей результат и в каком порядке | Список запретов («не пересказывай») |
| Пропускает обязательный элемент в том, что и так делает | Структурный слот: обязательное поле в шаблоне | Напоминание прозой рядом с шаблоном |
| Поведение зависит от условия | Условие на наблюдаемом предикате («если спека есть — сошлись на неё») | Безусловное правило + оговорки об исключениях |

Запреты проваливаются на проблемах формы: при конкурирующем стимуле агент торгуется с «не делай X». Рецепт не оставляет предмета торга. Два правила для любой формы: без оговорок-нюансов (реальное исключение — отдельным условием на предикате); исключения не скоупятся (часть результата должна быть свободна от правила — перестрой структуру, чтобы правило до неё не дотягивалось).

## Negation и leading words

Запрет затягивает запрещённое в контекст: «не думай о слоне» называет слона. Лечение — позитивная целевая формулировка. Запрет оставляй только как guardrail, который нельзя сформулировать позитивно, — и рядом ставь, что делать вместо. Плохо: «не пиши длинных вступлений». Хорошо: «Начинай с сути: первый абзац — принцип скилла в одном-двух предложениях».

Leading word — компактный термин с готовой семантикой из предобучения (tight loop, tracer bullet, red/green): в русском тексте латиницей, повторяй как один токен по всему скиллу. В теле якорит исполнение, в description — вызов.

## Прогрессивное раскрытие

Ветка — отдельный способ использования скилла. Критерий: материал нужен каждой ветке → тело SKILL.md; нужен некоторым → `references/<kebab-case>.md` за указателем в теле с предикатом «когда» («При X прочитай references/Y.md»). Подхватывание решает формулировка указателя, а не содержимое файла: не читается в нужный момент — сначала перепиши указатель конкретнее, и только потом верни материал инлайн.

## Плохо / Хорошо, таблицы отговорок, персуазия

Основной приём показа — пара «Плохо / Хорошо»: контраст читается быстрее объяснения. Один отличный пример бьёт пять посредственных. Таблицу «Отговорка → Реальность» собирай из дословных формулировок агентов на pressure-тестах, не из головы: выдуманная отговорка защищает от несуществующей атаки.

При написании дисциплинирующего скилла (железный закон, таблица отговорок, красные флаги) прочитай `references/persuasion.md`. Выжимка: дисциплина = authority + commitment (+ social proof); liking и reciprocity исключены — порождают сикофантию; справочникам убеждение не нужно. Фильтр на каждый приём: послужил бы он интересу пользователя, если бы тот полностью понимал приём?

## Кросс-ссылки

Ссылайся на другие скиллы по имени с маркером обязательности: «Обязательный под-скилл: <имя>». @-ссылка форс-грузит файл в контекст до реальной нужды; имя + маркер дают адрес и приоритет, а загрузка остаётся ленивой. Доменные скиллы команд (внутренние API, стандарты, предметная область) — обычные скиллы по этому же контракту и процессу.

## Чеклист перед публикацией

1. Frontmatter — ровно два поля: `name`, `description`. `name` = каталог, kebab-case, уникален.
2. Description — русский, третье лицо, одна строка ≤1024, «что + когда» с 4–6 триггерами, нулевая сводка процесса.
3. Раскладка плоская: `skills/<name>/SKILL.md`; references/ прошли критерий ветки, у каждого файла — указатель с предикатом «когда».
4. Форма каждой инструкции соответствует типу провала; формулировки позитивные; каждый запрет — guardrail с «что делать вместо».
5. Тело <500 строк: `wc -l SKILL.md`; кросс-ссылки — по имени, без путей и @-ссылок.
6. Тест-промпты и результаты прогонов сохранены в `references/pressure-tests.md` — тест-сьют для каждой будущей правки.

## Отговорка → Реальность

| Отговорка | Реальность |
|---|---|
| «Скилл очевидно ясен» | Ясен автору ≠ ясен агенту. Baseline занимает минуты и регулярно опровергает «очевидное». |
| «Это просто справочник» | У справочника свой провал — retrieval gap: агент не находит нужное. Тестируй поиск. |
| «Мелкая правка, тест не нужен» | Правка без теста = скилл без теста. Прогони сохранённые pressure-tests. |
| «Протестирую, если будут проблемы» | Проблемы = агенты уже пропустили шаги в реальной работе. Тест до деплоя дешевле. |
| «Сделаю пачку скиллов, протестирую разом» | Каждый скилл проходит цикл целиком до перехода к следующему. |
| «Я уверен в качестве текста» | Уверенность — не evidence. Прогон — evidence. |

## Красные флаги — стоп

- Текст скилла написан, а baseline ещё не запускался.
- «Я и так знаю, как агент ошибётся» — знание вместо наблюдения.
- «Опубликую сейчас, тесты добью потом».
- Правка существующего скилла без прогона его pressure-tests.
- Вложенный каталог `skills/<категория>/<name>/` вместо плоского `skills/<name>/`.

Любой из них — остановись и вернись к шагу, на котором есть провальный тест.

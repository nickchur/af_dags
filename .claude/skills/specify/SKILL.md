# specify — из согласованного понимания в спеку

Синтез, не интервью: всё нужное уже обсуждено в grill или собрано в discover.
Вопросы пользователю здесь — только подтверждение готовой спеки, не сбор требований.

## Шаг 0. Объяви и проверь вход

Объяви: «Использую скилл specify: превращаю согласованное понимание в спеку».

Вход — согласованное понимание: результат grill (закрытые вопросы, зафиксированные
решения) или discover (карта контекста, границы изменения). Если по требованиям
остались открытые вопросы — остановись и назови пользователю предыдущий шаг: skills/grill/SKILL.md.
Спека поверх несогласованного понимания отравляет весь дальнейший цикл.

## Шаг 1. Выбери форму спеки

| Ситуация | Форма | Шаблон набора | Куда класть в репозитории |
|---|---|---|---|
| Изменение существующего поведения (есть baseline-спека или устоявшееся поведение кода) | **delta-спека** | `specs/TEMPLATE-change.md` | `docs/sberpowers/specs/YYYY-MM-DD-<change>.md` |
| Новая возможность, точки отсчёта нет | baseline-спека | `specs/TEMPLATE-spec.md` | `docs/sberpowers/specs/<capability>-baseline.md` |

Delta — основной путь: изменение — первичная единица. Baseline пиши только когда
дельте не от чего отсчитываться. Сомневаешься — выбирай delta и укажи в поле
Baseline: «нет; точка отсчёта — текущее поведение кода».

Скопируй шаблон в целевой путь и заполняй секции по порядку; каталог
`docs/sberpowers/specs/` создай, если его нет.

## Шаг 2. Сформулируй требования

Каждому требованию — идентификатор `REQ-<slug>-NN`: slug един для возможности,
NN — порядковый номер. В delta-спеке MODIFIED и REMOVED ссылаются на существующие
ID из baseline; ADDED продолжает нумерацию (или заводит новый slug, если baseline нет).

Критерии приёмки — наблюдаемые истины, не задачи:

| | Формулировка |
|---|---|
| Плохо (задача) | «Сделать валидацию e-mail при регистрации» |
| Хорошо (истина) | «Пользователь с некорректным e-mail видит ошибку до отправки формы» |

Тест формулировки: по ней можно ответить «выполнено или нет», наблюдая систему
снаружи, без чтения кода. Если ответить нельзя — переформулируй, пока нельзя станет можно.

## Шаг 3. Обеспечь drift-resistance

Спека переживает рефакторинги. Описывай поведение, типы и контракты; пути к файлам
и номера строк устаревают с первым же коммитом — им в спеке не место.

| | Формулировка |
|---|---|
| Плохо (путь к файлу) | «Изменить `src/auth/validate.ts:42`, добавив проверку домена» |
| Хорошо (контракт) | «`validateEmail(raw: string): Result<Email, ValidationError>` дополнительно отклоняет домены из блок-листа» |

Единственное исключение — сниппет из прототипа, кодирующий решение точнее прозы:
стейт-машина, схема данных, shape типа. Вставляй только решающую часть с пометкой
происхождения («из прототипа, discover YYYY-MM-DD») — фрагмент-решение, не рабочее демо.

## Шаг 4. Заполни non-goals

Перечисли, что осознанно не делаем: смежные хотелки, отложенные оптимизации,
соседние сценарии. Non-goals защищают исполнителя от scope creep, а ревьюера —
от ложных находок «extra». Пустой раздел — признак недодуманной спеки: найди
минимум два пункта или явно запиши, почему границ у изменения нет.

## Шаг 5. Заложи traceability

Заполни в таблице traceability шаблона только колонку REQ-ID — по строке на каждое
требование. Остальные колонки впишут plan (задачи) и learn (тесты и статус). Так спека
остаётся файловым аналогом живого графа требований: по любому REQ виден путь
до задач и тестов, а по задаче — обратно до требования.

## Шаг 6. Подтверди у пользователя

Покажи спеку целиком и спроси, фиксируем ли. Правки вноси в файл спеки, не в чат:
файл — источник истины, чат — черновик. Повторяй, пока пользователь не подтвердит.

## Спека — источник истины для ревью

Скилл skills/review/SKILL.md сверяет результат работы с этой спекой: missing / extra /
misunderstood определяются относительно REQ-ID. Поэтому каждое требование обязано
быть проверяемым — непроверяемое REQ превращает ревью из сверки в мнение.

## Критерий выхода

- Каждое требование — наблюдаемая истина с REQ-ID, проверяемая без чтения кода.
- Формулировки drift-resistant: контракты и поведение, ни одного пути к файлу
  (кроме помеченных сниппетов из прототипа).
- Non-goals заполнены.
- Traceability-таблица содержит все REQ-ID.
- Пользователь подтвердил спеку.

## Терминальное состояние

Спека подтверждена → следующий шаг цикла: skills/plan/SKILL.md (передай ему путь к спеке).
Назови этот шаг пользователю и остановись: скиллы набора друг друга не вызывают.

# verification-before-completion — доказательство раньше заявления

Заявление об успехе без свежего прогона неотличимо от лжи для того, кто его читает. Между «код должен работать» и «код работает» лежит одна команда и её вывод — этот шаг не пропускается ради скорости.

## Железный закон

```
НЕТ ЗАЯВЛЕНИЙ ОБ УСПЕХЕ БЕЗ СВЕЖЕГО ДОКАЗАТЕЛЬСТВА
```

Свежее — значит запущенное в этом сообщении, после последнего изменения кода. Вчерашний прогон, прогон до правки, прогон в другой ветке — не свежее. «По факту почти проверено» не считается.

## Gate из пяти шагов

Перед любым «готово / исправлено / проходит» — пройди все пять шагов по порядку.

```
ОПРЕДЕЛИ → ЗАПУСТИ → ПРОЧТИ → СВЕРЬ → ЗАЯВЛЯЙ
```

1. **ОПРЕДЕЛИ.** Назови команду, которая доказывает именно это утверждение — не соседнюю, не похожую. «Тесты проходят» доказывает `pytest`/`npm test`, а не линтер. «Сборка работает» доказывает команда сборки с кодом возврата, а не отсутствие подчёркиваний в редакторе.
2. **ЗАПУСТИ.** Выполни команду целиком, свежо, без кэша и без `--only-failed`. Частичный прогон доказывает только то, что он покрыл.
3. **ПРОЧТИ.** Весь вывод, не первые строки и не последнюю. Exit code явно. Число прошедших и упавших — не «вроде зелёное». Обрезанный вывод — прокрути или перенаправь в файл и прочти целиком.
4. **СВЕРЬ.** Сопоставь вывод с формулировкой утверждения буквально. «0 failed» подтверждает «тесты проходят». «Warnings: 3» не подтверждает «сборка чистая», даже при exit code 0. Несовпадение — заявление меняется на то, что реально показал вывод.
5. **ЗАЯВЛЯЙ — только теперь.** Формулировка опирается на доказательство («37/37 тестов, exit 0»), не голое «готово». Не подтвердилось — сообщи фактический статус, не смягчай его до «почти готово».

Пропуск любого шага — не ускорение, а замена проверки на надежду.

## Утверждение → Доказательство

| Утверждение | Доказательство | Недостаточно |
|---|---|---|
| Тесты проходят | Свежий прогон полного набора в этом сообщении, вывод с числом прошедших/упавших и exit code | Прогон до последней правки; прогон только изменённого файла |
| Баг исправлен | Тест, воспроизводящий баг, был красным до фикса и стал зелёным после — в этой сессии | Код изменён, но красно-зелёный переход не зафиксирован |
| Субагент выполнил задачу | Проверенный diff от субагента плюс собственный прогон релевантных тестов | Текстовый отчёт субагента «готово» / «всё сделано» |
| Сборка работает | Свежая команда сборки, exit code 0, вывод прочитан целиком | Линтер чистый; сборка запускалась раньше в этой сессии до правок |
| Зависимость доступна | Пакет найден в реестре (npm/PyPI/Maven и т.п.) под нужным именем, версия совместима с остальными зависимостями проекта | Пакет «звучит правильно»; похожее имя встречалось раньше |

## Недостаточные суррогаты

Ничего из перечисленного не заменяет шаг ЗАПУСТИ, даже когда выглядит убедительно:

- вчерашний или досправочный прогон — код с тех пор изменился;
- «должно пройти» / «логика верна, значит сработает» — рассуждение вместо выполнения;
- зелёный CI другой ветки или прошлого коммита — не текущий diff;
- отчёт субагента об успехе без независимой проверки его diff и без собственного прогона;
- отсутствие ошибок в логе без позитивной проверки — тишина в логе не равна прохождению теста, это может быть недостигнутый код.

## Отговорка → Реальность

| Отговорка | Реальность |
|---|---|
| «Мелкая правка, тут нечему ломаться» | Мелкие правки чаще всего и ломают — опечатка в условии, неверный импорт, сдвинутый индекс. Прогон занимает секунды-минуты, откат сломанного релиза — часы. |
| «Только что проходило, ничего не менялось с тех пор» | «Только что» — это до последней правки. Свежесть считается от последнего изменения, не от последнего взгляда на терминал. |
| «Долго гонять весь набор, прогоню только изменённый файл» | Частичный прогон доказывает только про изменённый файл. Заявление «тесты проходят» относится ко всему набору; если утверждение уже «этот файл проходит» — сузь формулировку, но не выдавай частичное за полное. |

## Красные флаги — стоп

- В формулировке заявления есть «должно», «вероятно», «скорее всего» — это гипотеза, не результат; вернись на шаг ЗАПУСТИ.
- Заявление в прошедшем времени («тесты прошли», «баг был исправлен») без команды, выполненной в этой сессии, — не отличимо от выдумки задним числом.
- Всплывает удовлетворение («отлично!», «готово!») раньше, чем прочитан вывод команды.
- Мысль «в этот раз можно без прогона» — исключений не существует, правило одно и то же для маленькой правки и большого рефакторинга.
- Про субагента — «он написал, что справился, значит справился» вместо чтения его diff.
- Про сборку/зависимость — «выглядит похоже, наверное это тот пакет» вместо поиска точного имени в реестре.

## Плохо / Хорошо

**Тесты:**
Плохо: «Поправил условие, тесты должны теперь проходить.»
Хорошо: «Запустил `pytest`, вывод: 42/42 passed, exit 0 — тесты проходят.»

**Фикс бага:**
Плохо: «Изменил код — баг исправлен.»
Хорошо: «Тест на симптом был красным до правки, после правки — зелёный; исходный репро-сценарий тоже больше не воспроизводится.»

**Делегирование субагенту:**
Плохо: «Субагент сообщил, что задача выполнена — переходим дальше.»
Хорошо: «Прочитал diff субагента, прогнал релевантные тесты — 12/12 passed — задача подтверждена.»

argument-hint: <change-id> [<ветка назначения>]

Ревью изменения. Аргументы `{{args}}`: id изменения и, по желанию, ветка назначения — ветка, в которую пойдёт PR (например, `origin/develop`). Если id нет, взять единственное активное изменение из `openspec list --json`; если их несколько, спросить пользователя.

## 1. Проверки перед ревью

Если проверка не прошла, остановиться и сказать пользователю, что мешает.

1. `openspec status --change <id> --json`: `proposal`, `decisions` и `tasks` в статусе `done`; `specs` в статусе `done` или `skipped`. `skipped` означает `skip_specs: true` в `.openspec.yaml` изменения, тогда ось A получает `specs=skipped`. Первая строка `decisions.md` — `Open questions: 0`, status этого не проверяет.
2. `openspec instructions apply --change <id> --json`: все задачи, кроме тех, чей `description` начинается с `R.`, имеют `done: true`.
3. Рабочее дерево: незакоммиченные правки в диапазон ревью не попадают. Если `git status --porcelain --untracked-files=all` показывает правки только в `openspec/changes/<id>/` (артефакты планирования, worklog.md, review-report.md прошлого прогона), закоммитить их: `git add openspec/changes/<id> && git commit -m "docs(<id>): артефакты изменения"`. Правки вне каталога изменения — остановиться и показать их пользователю.
4. Полный прогон тестов проекта, записать код выхода. Если он не 0, ревью не начинать.
5. База диффа. Ветка назначения — второй аргумент. Без него взять `git symbolic-ref -q --short refs/remotes/origin/HEAD`, назвать ветку пользователю и спросить, в неё ли пойдёт PR. `BASE=$(git merge-base "<ветка назначения>" HEAD)`. Если ветка не определилась, `git merge-base` завершился ошибкой или BASE пуст, остановиться и попросить пользователя назвать локально доступную ветку назначения. Если нужной ветки нет локально, пользователь подготавливает её сам; сетевые операции не выполнять. Диапазон — `<BASE>..HEAD` с хешем коммита вместо `<BASE>` и двумя точками, оба ревьюера получают эту строку без изменений.

## 2. Ось A — соответствие спеке

Выбери точные имена двух ревьюеров среди доступных агентов: `sbp-reviewer-spec` и `sbp-reviewer-quality` либо их имена с префиксом `sberpowers:` при подключении через extension. Используй эти имена при вызовах и в отчёте. Если один из ревьюеров недоступен, остановись и сообщи пользователю; другим агентом его не заменяй.

```
agent(description="Ось A: соответствие спеке", subagent_type=<точное имя ревьюера оси A>, run_in_background=false, prompt=<входные данные>)
```

Входные данные: id изменения; пути к `openspec/changes/<id>/specs/**/spec.md` или `specs=skipped`; пути к `tasks.md`, `decisions.md` и `design.md`, если он есть; диапазон; код выхода тестов. Историю разговора не передавать. С `run_in_background=true` вернётся заглушка вместо отчёта.

Последняя строка отчёта — одна из `Verdict: PASS`, `Verdict: PARTIAL`, `Verdict: FAIL`. Без неё отчёт недействителен: перезапустить один раз, при повторе остановиться и сказать пользователю.

Каждый пункт `NOT-VERIFIABLE` проверить самому по коду, tasks.md и тестам. Если пробел подтвердился, вердикт оси A — `FAIL`, пункт идёт в разбор (раздел 5) как MISSING. Итог проверки дописать в раздел оси A под отчётом ревьюера.

## 3. Ось B — качество кода

После оси A так же запустить `sbp-reviewer-quality` с `run_in_background=false`. Входные данные: id изменения, диапазон, пути к правилам проекта (GIGACODE.md, конфигурации линтеров). Отчёт оси A и историю разговора не передавать. Последняя строка — `Verdict: ACCEPT` или `Verdict: NEEDS_FIXES`, правило о недействительном отчёте то же.

## 4. review-report.md

Переписать `openspec/changes/<id>/review-report.md` целиком, чтобы от прошлого прогона не осталось вердиктов. Шапка начинается с первой строки файла, заголовка перед ней нет:

```
Axis-A: <вердикт оси A>
Axis-B: <вердикт оси B>
Tests-exit-code: <код выхода из шага 1.4>
Reviewers: <точное имя ревьюера оси A>, <точное имя ревьюера оси B>
Date: <сегодня, YYYY-MM-DD>
```

После пустой строки — `## Ось A — соответствие спеке` и `## Ось B — качество кода`, под каждым полный отчёт ревьюера без правок.

## 5. Итог

`PASS` и `ACCEPT`: отметить `- [x] R.1` и `- [x] R.2` в tasks.md, закоммитить оба файла: `git add openspec/changes/<id>/review-report.md openspec/changes/<id>/tasks.md && git commit -m "docs(R): ревью изменения <id>"`. Сказать пользователю, что следующий шаг — `/opsx-archive <id>` в этой же ветке, затем PR.

Любой другой исход: `R.*` не отмечать, показать пользователю находки CRITICAL, IMPORTANT, MISSING, MISUNDERSTOOD, EXTRA и разобрать их:

- код делает не то, что требует спека (MISSING, MISUNDERSTOOD), или находка CRITICAL/IMPORTANT оси B — исправляет fix-субагент;
- спека неверна, невыполнима или противоречива — остановиться, показать расхождение пользователю и предложить `/opsx-update`;
- EXTRA — решает пользователь: удалить код через fix-субагента или узаконить поведение в дельте через `/opsx-update`;
- находка оси B противоречит спеке или задаче — не чинить, показать пользователю.

Fix-субагент запускать со свежим контекстом и `run_in_background=false`, в промпт дать находки и закрытый список файлов реализации, тестов и документации, которые разрешено править. Артефакты `openspec/changes/<id>/**`, действующие спеки `openspec/specs/**` и конфигурацию агента ему менять запрещено; необходимость такой правки он возвращает основному агенту для разбора с пользователем. Он сначала подтверждает каждую находку по коду и ложную возвращает с доводом, CRITICAL чинит раньше IMPORTANT, после каждого исправления прогоняет локальные тесты и коммитит его. После исправлений начать с шага 1.3: рабочее дерево, тесты, диапазон, повторное ревью оси, которой касались правки (обеих, если менялось поведение), отчёт переписать целиком.

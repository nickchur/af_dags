## SberPowers: разработка по спеке

Изменения ведутся в OpenSpec по схеме `sber-sdd`: сначала согласованное изменение, потом код.

### Цикл изменения

1. `/opsx-explore` — исследование до изменения, по желанию.
2. `/opsx-propose` — артефакты proposal, decisions, specs, tasks, при необходимости design. В расширенном профиле вместо него можно `/opsx-new` и `/opsx-continue` по одному артефакту или `/opsx-ff`.
3. `/opsx-apply` — реализация задач, кроме группы `## R. Review`.
4. `/sbp-review` — ревью по двум осям, `review-report.md`, отметки `R.1` и `R.2`. Это следующий шаг после реализации, даже если скилл OpenSpec предлагает сразу архивировать.
5. `/opsx-archive` — перенос дельты в `openspec/specs/` и архив изменения в той же ветке.
6. PR: код, архив изменения и обновлённые спеки одним PR.

Если команд `/opsx-*` в проекте нет (OpenSpec доставляет только скиллы), те же шаги выполняют скиллы `openspec-explore`, `openspec-propose`, `openspec-new-change`, `openspec-continue-change`, `openspec-ff-change`, `openspec-apply-change`, `openspec-update-change`, `openspec-archive-change`.

### Правила изменения

- Состояние артефактов узнавать только из `openspec status --change <id> --json`. По памяти этап готовым не считать.
- `decisions.md` пишется допросом через скилл `sbp-grill`, в том числе внутри `/opsx-propose` и `/opsx-ff`. `openspec status` отмечает decisions готовым, как только файл создан, поэтому готовность decisions проверять по первой строке `Open questions: 0`.
- `review-report.md` пишет и `R.*` отмечает только `/sbp-review`, вручную их не заполнять.
- Не архивировать, пока в tasks.md не отмечены `R.1` и `R.2`. Предупреждение `/opsx-archive` о несозданном design.md ожидаемо: design необязателен.
- Если в изменении есть дельта спек, в `/opsx-archive` выбирать синхронизацию, вариант «Archive without syncing» не выбирать. Если синхронизация заблокирована, отменить архивацию и показать причину пользователю.
- `openspec archive` запускать без `--yes` и без `--skip-specs`.
- `/opsx-sync` не запускать: спеки переносит `/opsx-archive`. `/opsx-bulk-archive` не использовать: одно изменение на PR. `/opsx-verify` не заменяет `/sbp-review`.
- PR без изменения OpenSpec допустим только по правилам из шапки и классам `openspec/change-allowlist.yaml`. При сомнении нужен полный цикл.

### Проверка и безопасность

- Все команды OpenSpec выполняй с `OPENSPEC_TELEMETRY=0` в окружении процесса: флаг отключает телеметрию и фоновую проверку новых версий. Конфигурацию АРМ подготавливает пользователь по README.
- Не писать «готово», «исправлено», «тесты проходят» без прогона после последней правки. В ответе указать команду, код выхода и число passed/failed. Команду брать из package.json, Makefile, pom.xml или конфигурации CI, а если её там нет, спросить.
- Отчёт субагента проверять по его диффу и своему прогону тестов.
- Зависимости проверяй по локальным манифестам и lock-файлам. Используй уже установленные инструменты; пакеты не устанавливай и не обновляй, реестры не запрашивай. Если зависимости или инструмента не хватает, остановись и попроси пользователя подготовить АРМ через SUS.
- Проверки выполняй локально, без сетевых запросов и обращений к сервисам. Внешние системы заменяй локальными дублёрами с обезличенными фикстурами.
- Без явной просьбы не делать push, force-push, `git reset --hard` и не удалять ветки.
- Секреты, токены и персональные данные в выводах и отчётах заменять на `<REDACTED>`.

Скиллы: `sbp-grill` — допрос перед решением; `sbp-debug-refactor` — баг, падающий тест, рефакторинг; `sbp-writing` — вычитка текста для людей: артефактов, коммитов, описаний PR, документации.

При подключении через extension имена навыков и ревьюеров могут иметь префикс `sberpowers:`. Используй точные имена из списка доступных навыков и агентов.

Артефакты, отчёты и сообщения коммитов пишутся по-русски, структурные токены не переводятся: `## ADDED/MODIFIED/REMOVED/RENAMED Requirements`, `### Requirement:`, `FROM:`/`TO:`, `#### Scenario:`, `SHALL`/`MUST`, `**WHEN**`/`**THEN**`, ключи шапок, вердикты, id задач, kebab-case, тип коммита (`feat:`, `fix:`).

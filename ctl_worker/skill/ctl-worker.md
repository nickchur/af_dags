# Загрузки CTL на альфе

*2026-09-26 14:31 MSK · v1.8 · Nick Churkin · [NSChurkin@sber.ru](mailto:NSChurkin@sber.ru)*

Навык для агента GigaCode с MCP-сервером Airflow альфы (`af-alpha-*`). Он дополняет навык
`airflow-health`: тот видит Airflow целиком, этот объясняет, что стоит за дагами `CTL.*`.
Источник правды — код каталога `ctl_worker/` репозитория `af_dags`; при расхождении прав код.

У тебя только чтение через MCP. В CTL и Greenplum ты не ходишь — там говоришь, **что
проверить человеку** (раздел 11).

Что тракт хранит в Variables, читай MCP-инструментом `get_variable_value(key, item)`:
`ctl_config` — настройки тракта (профиль, таймауты, пулы, `orchestrator`, `test_mode`; PIN
туда не попадает), снимок CTL от последнего `ctl_loader` — `ctl_workflows` (воркфлоу по id),
`ctl_entities`, `ctl_enames`, `ctl_categories`, `ctl_events`, `ctl_entity_events`,
`ctl_profile`, `ctl_ue_category`, `ctl_workflows_stat`. Снимок, а не живой CTL: свежесть — в `description`.
Крупные (`ctl_entities`, `ctl_enames`) приходят обрезанными со списком `items` — проси один
элемент: `item="<id>"`. Если на контуре есть инструменты `ctl_*` (AF_CTL_logs), состояние
загрузки бери у `ctl_loading`, а снимок Variables — чтобы понять, что видел `ctl_sensor`.

`ctl_loading` сначала смотрит снимки тракта в папке `ctl/` бакета логов: `ctl_done/{id}_{попытка}`
(итог попытки) и `ctl_working/{id}` (состояние на входе в шаг). Если загрузка закончена или
снимок моложе 2 минут, в CTL он не ходит — поле `source: snapshot`. У CTL лимит на запросы:
`live=true` ставь, только когда нужен именно живой CTL (снимок устарел, а статус важен сейчас).
Сырой снимок — `get_log_object("ctl/ctl_working/<id>.json")`.

## 0. Когда этот навык

- Вопрос про загрузку, воркфлоу, `loading_id`, код `res` — сразу сюда.
- Общий вопрос «что с альфой» — сначала `get_system_health` по навыку `airflow-health`;
  сюда — когда среди проблем даги `CTL.*`.
- Сигма: дагов `CTL.*` там нет, этот навык не нужен; контуры независимы (навык
  `airflow-health`, раздел 0): ключи и объекты бакета ищи только сервером своего контура, а нет
  инструмента — пакет на контуре старее, сервером другого контура его не подменяй.

## 1. Устройство за минуту

```
CTL (оркестратор загрузок)
  │  метаданные воркфлоу               загрузки RUNNING / TIME-WAIT / EVENT-WAIT
  ▼                                           ▼
CTL.<профиль>.loader (5 мин)          CTL.<профиль>.sensor (1 мин)
                                              │ запускает ран с loading_id в conf
                                              ▼
                                  CTL.<воркфлоу>: run_prm → [run_tfs] → run_exe → [run_out] → run_end
                                              │                            │
                                              │                     Greenplum: pr_swf_start_ctl
                                              ▼
                                  CTL.<профиль>.monitor (опрос 15 мин): разбор зависших, санитар метабазы
```

- Профиль на альфе — `HR_Data`: служебные даги `CTL.HR_Data.loader`, `.sensor`, `.monitor`,
  `.events`, `.test_conn`, `.config`, `.tfs_sensor`.
- Даг загрузки — `CTL.<полное имя воркфлоу>`, например `CTL.pc1080.smd2stg_txn_det_union`.
  Один даг на воркфлоу — только профиля `HR_Data` с оркестратором `dummy`.
- Наши потоки — всё дерево категорий `p1080`. Потоки других профилей и оркестраторов тоже
  наши, но исполняет их не Airflow: они лежат в категории UE (`ue_category`), дагов у них
  нет, за ними следит монитор (раздел 5а).
- Пулы по внешнему ресурсу: `ctl_pool` (вызовы API CTL: `run_prm`, `run_end`, сенсор,
  монитор), `gp_pool` (`run_exe`, `run_tfs`), `files_pool` (файлы ТФС). Размер меняет только
  `CTL.<профиль>.test_conn`: подключение недоступно — пул 0, задачи ждут. `gp_pool` = 0
  значит «Greenplum недоступен», а не «пул сломан», `files_pool` = 0 — недоступен S3-архив
  ТФС. `ctl_pool` при живом CTL фиксированно 20 (до ctl PR #57 плавал 10–40).

## 2. Как найти загрузку

| Что знаешь | Как найти ран |
|---|---|
| имя воркфлоу | `list_dag_runs(dag_id="CTL.<имя>", limit=5)` — последние раны |
| `loading_id` и имя воркфлоу | ран с `run_id` = `sensor__<loading_id>_<попытка>_<дата>` |
| только `loading_id` | последние раны `CTL.HR_Data.monitor`: в заметке рана списки загрузок с номерами и именами воркфлоу («🚨 SLA», «⏸️ ждут снятия паузы»). Не нашёл — спроси имя воркфлоу, не перебирай даги |

Как загрузка попадает в ран:

- **ран сенсора** (`sensor__…`) — загрузку создал CTL, номер есть в `run_id` и в `conf.loading_id`;
- **ран по расписанию, событию или ручной** (`scheduled__…`, `dataset_triggered__…`,
  `manual__…`) — загрузку создаёт сама задача `run_prm` (статус в CTL: `NEW-AF <run_id>`).
  Номер — в заметке задачи `run_prm` (`Params`, поле `loading_id`).

Один `loading_id` может дать несколько ранов: номер попытки в `run_id` растёт с каждым
повтором.

## 2а. «Что с потоком X» — самый частый вопрос

Один вызов `ctl_workflow(имя)` отвечает почти целиком. Порядок:

1. **Когда отработал и чем.** `recent_loadings` (20 последних): `outcome` — `ok`, `no` (нет
   данных), `error`, `running`, `waiting`; `res` и `msg` — итог шага. `summary.counts` и
   `summary.last_ok`: повторяющиеся `error` или `no` подряд — назови отдельной строкой,
   это важнее последнего исхода.
2. **Должен ли был отработать.** `expected`:
   - `source: wf_alert` — правило SLA потока: перескажи словами («каждый день к 09:00,
     данные Т-1 в `stg.tb_x`»); вердикт по нему — в `alerts`;
   - `source: cron` — `last_slot` и `overdue`;
   - `wf_interval` или `events` — срока нет, есть только ожидаемая частота.
3. **Не отработал в срок — цепочка событий** (`events`, по событию запуска):

   | `verdict` | Что значит | Что сказать |
   |---|---|---|
   | `fired` | статистика события опубликована после последнего ok потока | событие было — ищи причину в самой загрузке (раздел 3) или в паузе (раздел 7) |
   | `parent_ran_no_stat` | поставщик после этого отработал, но статистику события не опубликовал | «поставщик отработал, данные не изменились». Для статистики 2 (изменение данных) это штатно, не сбой. Если поток должен идти при каждом прогоне родителя — вопрос к подписке: событие на другую статистику (**Чьё:** CTL) |
   | `parent_not_ran` | по сущности свежих публикаций нет | смотри `supplier`: `error` — «поставщик упал», `no` — «отработал без данных», `never` — не запускался. Дальше вверх: `ctl_workflow(<поставщик>)`, не больше трёх шагов |

   В `stats` события видны все статистики сущности: какие опубликованы, когда и какой
   загрузкой (`loading_id`). `supplier` — загрузка, опубликовавшая последней, с её `outcome`.
4. **SLA-алерты** (`alerts` в ответе или `ctl_alerts(workflow)`): строки последнего отчёта
   `pr_mail_ctl_alerts` по потоку — правило, период, `since` (когда проблема началась),
   `closed` (заполнено — алерт снят), `msg` (причина). «Никогда» в причине почти всегда
   значит ошибку в самом правиле: не тот `obj` или `stat`.

Ответ — таблицей цепочки:

```
Поток pc1080.x: последний ok 25.09 09:04, сегодня к 09:00 не отработал (cron 0 9 * * *).
| Событие | Поставщик | Итог поставщика | Когда |
|---|---|---|---|
| HR_Data/941010123/2 | pc1080.parent | ✅ ok, parent_ran_no_stat | 26.09 08:40 |
**Чьё:** воркфлоу / CTL / платформа
```

Потоки категории `p1080.ARCHIVE` — старые: отсутствие у них загрузок норма, «не отработал»
для них не вопрос.

## 3. Что смотреть в ране

Один вызов `diagnose_dag_run(dag_id, dag_run_id)` отдаёт ран с `conf` и `note` и все задачи с
их `note`. Заметки — главный источник: код пишет в них то, что в логах пришлось бы искать.

| Задача | Что делает | Заметки |
|---|---|---|
| `run_prm` | берёт загрузку (ран сенсора) или создаёт новую в CTL; проверяет статус и срок событий | `🔍 Entities`, `Params` (все параметры, `loading_id`, `wfp_retry`) |
| `run_tfs` | только при `wf_tfs_in`: файлы из S3 в таблицы GP | `✅ <файл>` или `❌ Error` |
| `run_exe` | вызывает `pr_swf_start_ctl` в Greenplum | `Run_prm` (что ушло в GP, `timeout`, `⚠️` о потолке), `Result` (`res`, `msg`, `ts` — длительность) |
| `run_out` | только при `wf_tfs_out`: публикует датасет для ТФС | — |
| `run_end` | решает исход по `res`, ставит статус в CTL, публикует датасеты сущностей | `Log` (`action`, `retry`), `Entities` |

Порядок разбора: заметка `Result` у `run_exe` → если её нет, лог упавшей задачи
`get_task_logs(dag_id, dag_run_id, task_id, try_number)` → первая ошибка дословно. Бюджет — как
в `airflow-health` 6.1: не больше шести вызовов сверх первого.

🧪 `exe` вида `'Ok Test work',pg_sleep(N)` в заметке `Run_prm` — **тестовый режим**
(`test_mode` в `ctl_config`, только DEV и IFT): ожидание случайной длины подставляет сам
`run_exe`, а `res` берётся из профиля режима. Это не SQL воркфлоу — не советуй править
воркфлоу в CTL и не сравнивай `pg_sleep` с `wf_timeout` как причину.

Повторная попытка `run_exe` ETL не запускает. Её заметки:

- `Result (ответ подобран из журнала GP)` — прошлая попытка оборвалась, но работа выполнена;
- `Result (прошлая попытка оборвана)`, `res = -9` — ответа нет и запуска в GP нет: работа не
  выполнена, `run_end` отдал загрузку на повтор по `retry.on`. Причина обрыва — в логе
  попытки 1 (чаще всего перезапуск пода воркера);
- failed «Повтор N: … всё ещё выполняется в Greenplum» или «Greenplum недоступен» — исход
  неизвестен, загрузка осталась в `RUNNING`, её разберёт монитор (`reRunned` через 6 ч).

Задача `skipped` в `CTL.<воркфлоу>` — чаще всего штатный пропуск: проверка статуса загрузки
сказала «не мой ход» (загрузку закрыли или перезапустили в CTL). Причина — в заметке задачи.

## 4. Код `res` и исход загрузки

`res` возвращает `pr_swf_start_ctl`, он в заметке `Result`:

| `res` | Что значит |
|---:|---|
| `> 0` | успех (ответ шага начинается с `ok ` или пуст) |
| `0` | нет данных (`no `): успешно, зависимые шаги пропущены |
| `-1` | `empty ` |
| `-2` | `query_canceled` / `statement_timeout` — запрос упёрся в **наш** потолок (раздел 6) или его отменили |
| `-3` | `expire ` — истёк срок |
| `-4` | не прошла проверка уникальности (`pr_chk_uniq`) |
| `-5` | проверка качества: Z-тест или расхождение количества строк (`pr_chk_cnt_delta`) |
| `-7` | необработанное исключение в `pr_swf_start_ctl`; текст — в `msg` |
| `-8` | ошибка сервера PXF |
| `-9` | всё остальное |

⚠️ `-7` — **не** «циклический повтор», как написано в старых документах. Особой обработки у
него нет: это ошибка, как любая отрицательная.

Что делает `run_end`:

- `res > 0` — `ok`, `res = 0` — `no`, `res < 0` — `error`;
- остались попытки (`retry.left > 0`) и исход входит в `retry.on` воркфлоу (по умолчанию
  `error`; можно перечислить и коды) → `ERRORCHECK` → `TIME-WAIT` до времени следующей
  попытки: `delay`, плюс `add` за каждую прошлую;
- иначе — `SUCCESS`, если была хоть одна `ok`/`no`, или `ERROR`; затем загрузка закрывается
  как `Completed`, а при `abortOnFailure` воркфлоу — `Aborted`.

## 5. Монитор: что он делает с загрузками

`CTL.HR_Data.monitor` раз в 15 минут смотрит активные загрузки. Решение — в заметках его
задач: `ctl_action` пишет по заметке на загрузку (`🔗 <loading_id>`: статус, действие,
воркфлоу), сводки — в заметке рана.

| Действие | Когда | Что происходит в CTL |
|---|---|---|
| `New` | загрузка моложе `new_grace` (60 мин) | ничего, её запустит сенсор |
| `Skipped` | всё в порядке или ждёт | ничего |
| `reRunned` | `ERRORCHECK`; `RUNNING` с чужим логом; `RUNNING` с логом `RUN…` дольше `run_stale` (6 ч), но не раньше `wf_timeout` воркфлоу + 10 мин | снова `RUNNING` → сенсор запустит **ту же** загрузку |
| `reStarted` | `PREREQ`/`PARAM`/`START`; `LOCK`/`LOCK-WAIT` дольше `lock_stale` (5 ч); `TIME-WAIT` просрочен больше `wait_grace` (15 мин); `EVENT-WAIT`, чьё событие уже пришло | загрузка закрывается, создаётся **новая — с другим `loading_id`** |
| `Completed` / `Aborted` | `SUCCESS` / `ERROR` висят незакрытыми | закрывается |
| `SLA` | `Skipped` дольше `wf_interval` воркфлоу (по умолчанию сутки) | ничего: только показать |

Заметки рана монитора:

- «🚨 SLA» — загрузки, ждущие дольше срока, но не старше `sla_dead` (30 дней): дежурная работа;
- «🪦 Брошены» — старше: их не ждут, их бросили — вопрос к расписанию, не к платформе;
- «⏸️ ждут снятия паузы» — загрузкам есть куда ехать, а даг на паузе (раздел 7).

`SLA` здесь — сводка монитора. Airflow-SLA не используется.

Правила таблицы — для своих загрузок (`HR_Data` + `dummy`).

## 5а. Потоки UE

Потоки категории UE исполняют другие профили и оркестраторы, но владельцы — мы, и монитор
действует по ним теми же вызовами CTL. Порогов GP у них нет:

| Состояние | Порог | Действие |
|---|---|---|
| `RUNNING` | `wf_timeout` воркфлоу, иначе `ue_run_max` (сутки) | `reStarted` |
| `TIME-WAIT` просрочен, `EVENT-WAIT` с пришедшим событием | `ue_grace` (30 мин) | `reStarted` |
| прочие статусы без изменений | `ue_stale` (сутки) | `reStarted` |
| поток на расписании, активной загрузки нет | `ue_grace` (30 мин) | ▶️ `Started` — новая загрузка |
| поток по событию, событие пришло после старта последней загрузки, загрузки нет | 30 мин после события | ▶️ `Started` (события обрабатывает CTL — он должен был создать загрузку сам) |

Заметка `ctl_action` для `Started` — `▶️ wf <id> <имя>`, загрузки у неё ещё нет. Письма при
ошибках шлёт сам CTL, если они прописаны у воркфлоу.

Заметка рана `CTL.HR_Data.loader`:

- «⚠️ Потоки вне присмотра» — поток дерева `p1080` не `HR_Data` + `dummy` и не в категории
  UE: дага нет, монитор не смотрит, поток потерян. Число — `orphan` в
  `get_variable_value("ctl_workflows_stat")`;
- «⚠️ Потоки и в Airflow, и в UE» — `HR_Data` + `dummy` внутри категории UE (`double`).
  Исполняет Airflow, ветка UE монитора его не трогает.

Оба — вопрос к настройке потока в CTL (**Чьё:** CTL): перевести поток в категорию UE или в
профиль `HR_Data` с оркестратором `dummy`.

## 6. Таймауты

Всё выстроено от одного факта: **Greenplum обрывает запрос через 4 ч 30 мин** — молча, вместе с
соединением, без лога ошибки и без ответа.

| Ступень | По умолчанию | Что видно, когда сработало |
|---|---|---|
| потолок запроса: `wf_timeout` воркфлоу, иначе `gp_timeout` | 4 ч 25 мин | `res = -2` в заметке `Result`; лог ошибки в GP есть |
| `execution_timeout` задачи `run_exe` | потолок + 10 мин | `run_exe` failed с `AirflowTaskTimeout` в логе |
| прочие задачи загрузки | 1 ч | то же |
| санитар (`zombie_after`) | 6 ч | задача failed без ошибки в логе; ран закрыт монитором |
| служебные сенсоры | 6 ч | ран сенсора `skipped` по таймауту — норма |

Как отличить:

- **оборвали мы** — есть заметка `Result` с `res = -2`: запрос шёл дольше потолка;
- **оборвал сервер** — `run_exe` упала без `Result`, в логе `AdminShutdown` с правилом
  «Query Time 4,5H (GLOBAL)» и обрыв соединения. Так бывает,
  когда `wf_timeout` воркфлоу не ниже 4 ч 30 мин: в заметке `Run_prm` и в описании дага стоит `⚠️`
  об этом. Это вопрос к владельцу воркфлоу (раздел 11).

`wf_timeout` задаётся в CTL у воркфлоу, минутами. Мы его не урезаем: раз задан — значит нужен.

## 7. Паузы и санитар

- **Сенсор не запускает запаузенный даг**: ран бы встал в очередь навсегда. Загрузку он
  пропускает, в CTL она остаётся как есть, а в заметке сенсора — кто поставил паузу:
  «поставил `<кто>` `<когда>`», «рубильник тракта» (выключен весь профиль) или «записи в
  журнале нет» (пауза с создания дага либо поставлена кодом — различить нельзя).
- **Монитор** показывает такие загрузки в заметке «⏸️ ждут снятия паузы» с возрастом.
- **Санитар** (`ctl_zombie` в мониторе) — в начале каждого рана монитора (ран кончается, когда
  монитору нашлась работа, иначе по окну 6 ч):
  - задачу в `running`, чей воркер не бьётся дольше 6 ч, помечает failed, ран закрывает,
    загрузку — `ERROR`;
  - ран без живых задач или ран дага, пропавшего из разбора, закрывает, загрузку — `ERROR`;
  - ран запаузенного дага (в очереди старше 6 ч, или в работе без задачи в `running` и без
    движения 6 ч) закрывает, задачи — `skipped`, **загрузку не трогает**: снимут паузу —
    поедет.

## 8. Норма, а не тревога

- `CTL.HR_Data.events`, `.monitor`, `.tfs_sensor` работают до 6 ч одним раном и уходят в
  `skipped` по таймауту — так задумано. Ретраи сенсора (до 10) гасят разовые сбои CTL.
- `CTL.HR_Data.test_conn`: все шесть сенсоров `skipped` — штатный итог. Сенсор час проверяет
  подключения и уходит в `skipped` по своему таймауту. Красный ран означает только
  `dagrun_timeout` (ран не уложился в 90 мин). Сбой подключения виден в заметке задачи
  `chk_*` (❌) и в обнулённом пуле, а не в статусе задачи.
- `Skipped` у большинства загрузок в мониторе — норма.
- Задача `skipped` в `CTL.<воркфлоу>` с заметкой о статусе загрузки — загрузку закрыли или
  перезапустили в CTL, ран больше не её.
- Запаузенные даги `CTL.*` — у воркфлоу, которые не стоят на расписании в CTL, пауза с
  создания обычна.

## 9. Разбор по симптому

| Симптом | Куда смотреть | Частая причина |
|---|---|---|
| `run_exe` failed | заметка `Result` → `res`; нет её — лог `run_exe` | `res < 0` — раздел 4; без `Result` — обрыв соединения или сервер GP (раздел 6) |
| `run_prm` failed | лог `run_prm` | CTL не ответил; загрузка уже не `ACTIVE`/`RUNNING`; истёк срок событий |
| загрузка в CTL `RUNNING`, рана нет | заметка сенсора, «⏸️» у монитора | даг на паузе; дага нет в разборе (заметка сенсора «дага нет»); пул `ctl_pool`/`gp_pool` = 0 |
| ран висит в `queued` | `get_pool`, пауза дага | пул 0 (подключение недоступно, `test_conn`); даг на паузе |
| `run_exe` в `running` часами | заметка `Run_prm` → `timeout` | работает в GP до потолка; дольше потолка + 10 мин — зависло |
| `res = -2` | `Run_prm.timeout`, `Result.ts` | запрос дольше потолка: рост данных или блокировки в GP |
| `res = -5` | `msg` в `Result` | данные не прошли проверку качества — вопрос к данным, не к платформе |
| `res = -7` | `msg` в `Result` | ошибка внутри SQL воркфлоу |
| `res = -8` | `msg` | PXF: внешний источник GP |
| повтор не случился | заметка `Log` у `run_end` → `retry` | `left = 0` или исход не в `retry.on` |
| `loading_id` сменился | заметка `ctl_action` монитора | `reStarted`: монитор закрыл старую загрузку и создал новую |
| `run_exe` failed «Повтор N: …» | заметка задачи, лог попытки 1 | раздел 3: исход прошлой попытки неизвестен |
| у потока нет дага `CTL.*` | «⚠️ Потоки вне присмотра» у загрузчика | не `HR_Data` + `dummy` и не в категории UE (раздел 5а) |

## 10. Чего не советовать

- **Не `clear` и не перезапуск `run_prm`** у ручных и расписанных ранов: задача создаёт
  загрузку в CTL, повтор создаст вторую.
- **Не рассчитывать, что ретрай `run_exe` перезапустит ETL**: повторная попытка только ищет
  готовый ответ в логе Greenplum или сам запуск. Повторы загрузки делает CTL.
- **Не «просто снять паузу»**: у воркфлоу без расписания в CTL снятие паузы включает
  собственное расписание Airflow. Паузу снимает человек, понимая зачем.
- **Не править загрузку через Airflow** (`trigger_dag`, `clear_dag_run`): статус загрузки
  живёт в CTL, повтор или закрытие — там.
- Не называть причину без лога или заметки: «причина не установлена, нужна заметка `Result`
  / лог `<задача>` попытки N».

## 11. Что проверить человеку

Эти места агенту недоступны — назови их, не адреса:

- **Greenplum**, по номеру загрузки: `vw_log_ctl_loading` (одна строка на загрузку: жива ли,
  начало, конец), `vw_swf_ctl_log` (действия движка по загрузке: старт, конец, ошибка, ответ).
- **CTL**: карточка загрузки — статус, лог статуса (`WAIT-AF`, `NEW-AF`, `RUN …`, `END …`),
  настройки повторов воркфлоу, `wf_timeout`.
- Ошибка внутри SQL воркфлоу (`res -4…-9`) — владелец воркфлоу, не платформа.
- **SLA-алерты**, Greenplum: `tb_ctl_alerts` (все заведённые, `close_ts` пустой — открыт),
  дата данных объекта — `tb_log_workflow_stat` (`wf_obj`, `data_max`). Правило потока —
  параметры `wf_alert` / `wf_alert_data` / `wf_alert_group` в CTL.

## 12. Как отвечать

```
### <воркфлоу> · загрузка <loading_id> · попытка <N> · <статус рана>

**Что случилось:** <одна фраза>
**Цепочка:** <ран> → <задача> → <заметка/лог: дословно> → <res и что он значит>
**Чьё:** платформа (Airflow, пулы, воркеры) | воркфлоу (SQL, данные) | CTL (настройки, пауза)
**Что делать:** <кому и что, без советов из раздела 10>
```

Несколько загрузок — таблица: воркфлоу, `loading_id`, `res` / состояние, причина, чьё.

## Допрос: оператор HrpS3ToPgStreamOperator (S3 → GP/PG, CSV и JSON)

- **Вопрос:** новый оператор или расширение `HrpS3ToPostgresOperator2`?
  **Выбор:** новый оператор `HrpS3ToPgStreamOperator` (имя — пользователь 15.10.2026; GP — форк PG), поддержка GP и PG; сначала af_dags `plugins/`, потом etl-core.
  **Почему:** пользователь 15.10.2026 — оператор для систем, где пишущая транзакция не ограничена или
  предел несущественен; `HrpS3ToPostgresOperator2` построен вокруг промежуточных коммитов и инкарнаций.

- **Вопрос:** транзакции — одна на файл или промежуточные коммиты?
  **Выбор:** одна транзакция на загрузку, данные идут потоково (без чтения файла в память целиком).
  **Почему:** пользователь 15.10.2026; предел транзакции целевых систем несущественен.

- **Вопрос:** усечение перед загрузкой?
  **Выбор:** один параметр `truncate` = `None` (по умолчанию, без усечения) | `soft` | `hard` | `auto`:
  `hard` — `TRUNCATE`; `soft` — `DELETE`; `auto` — `LOCK … NOWAIT` + `TRUNCATE`, при занятой таблице
  `DELETE` (логика `s_grnplm_vd_hr_edp_srv_wf.pr_soft_truncate`).
  **Почему:** пользователь 15.10.2026 (один параметр вместо пары true/false + режим). Логика повторяется в операторе (savepoint), а не вызовом функции:
  на PG её нет, у `-read` прав на схемы `*_vd_*` может не быть.

- **Вопрос:** zip?
  **Выбор:** по возможности; если не выходит — без zip.
  **Почему:** пользователь 15.10.2026 «если поддержка zip не получится да и фиг с ней».

- **Вопрос:** JSON — в колонку `jsonb` или раскладка по колонкам?
  **Выбор:** решает формат приёмника. Состав и типы колонок оператор берёт из `select * from <target> limit 0`.
  Приёмник из одной колонки `json`/`jsonb` — COPY элементов прямо в неё. Иначе COPY во временную таблицу
  (`jsonb`), затем `insert … select` с раскладкой по именам колонок приёмника (кандидат —
  `jsonb_populate_record(null::<target>, j)`; есть в GP6/PG 9.4, на контуре проверить).
  Массив под ключом — параметр `root`.
  **Почему:** пользователь 15.10.2026; оператор не требует описания схемы — её задаёт DDL приёмника.

- **Вопрос:** какой объект элемента раскладывать/грузить?
  **Выбор:** параметр `item` — путь к объекту внутри элемента через точку, любой глубины (`item="payload"`,
  `item="payload.value"`), или списком ключей (для ключа с точкой в имени); по умолчанию весь элемент;
  действует и при загрузке в одну колонку `jsonb`. Пути нет или уровень не объект — ошибка с номером
  элемента и уровнем. `root` — один уровень (вложенный — по запросу).
  **Почему:** пользователь 15.10.2026; в `_dia` не тащим повторяющуюся в каждой строке `schema`.

- **Вопрос:** как ключи JSON сопоставляются с колонками приёмника?
  **Выбор:** без учёта регистра; два ключа, различающиеся только регистром, — ошибка. Нет ключа — `NULL`.
  Лишний ключ отбрасывается, список таких ключей — в лог один раз. Значение не приводится к типу
  колонки — падает вся загрузка (одна транзакция, откат вместе с усечением).
  **Почему:** пользователь 15.10.2026; молча искажать данные нельзя, строгость типов задаёт DDL приёмника
  (в `_dia` колонки `text` — ошибки приведения нет).

- **Вопрос:** форматы и сжатие?
  **Выбор:** `format` = `csv` | `json` (массив, `root`) | `jsonl` | `auto` (по умолчанию — по расширению
  после снятия сжатия: `.csv`, `.json`, `.jsonl`/`.ndjson`; незнакомое — ошибка). Сжатие по расширению:
  `.gz` потоково (stdlib), `.zip` через `stream_unzip` — все файлы архива по очереди (если не выйдет — без zip).
  CSV — COPY прямо в приёмник, параметр `options` (по умолчанию `CSV HEADER DELIMITER ','`, как в `gp_from_stream`).
  **Почему:** пользователь 15.10.2026 при условии, что `options` задаётся; поток ТФС переходит без смены настроек.

- **Вопрос:** служебные колонки?
  **Выбор:** время загрузки — `default now()` в DDL приёмника, оператор не пишет. Имя файла — параметр
  `file_name_column` (по умолчанию `None`): ключ S3, для zip — плюс имя внутри архива; для CSV тогда
  COPY через временную таблицу. Номер элемента не пишем.
  **Почему:** пользователь 15.10.2026; время даёт сама база, без параметра CSV идёт прямо в приёмник.

- **Вопрос:** где граница оператора и откуда таймаут?
  **Выбор:** оператор только грузит: один ключ S3 (`s3_key`, шаблонизируемый) → одна таблица (`table`,
  со схемой); число строк — в лог и XCom. Маски, перебор, `.done`, `tfs-archive`/`tfs-errors`, статусы CTL
  остаются в `run_tfs`; подключение к `run_tfs` — отдельная задача после проверки на контуре.
  Параметр `statement_timeout` (минуты), по умолчанию 240 (4 часа) для GP и PG; `gp_timeout` из
  `ctl_worker` оператор не читает — при подключении `run_tfs` передаст `gp_timeout(wf_prm)` явно.
  **Почему:** пользователь 15.10.2026; оператор едет на сигму и в etl-core, где CTL нет; 4 часа — с запасом
  ниже серверного «Query Time 4,5H».

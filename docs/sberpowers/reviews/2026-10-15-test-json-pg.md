# Ревью: tools_test_json_pg — загрузка JSON в PG/GP
*2026-10-15 · новый файл tools/test_json_pg.py, раздел tools/readme.md*

## Итог

Код проверен двумя независимыми моделями-ревьюерами и самопроверкой разбора. Стенд (PostgreSQL 16):
синтетика 100 000 элементов — success, искажённых имён 0; файл S3 30 000 элементов пачками по 7 000 —
success; тестовый файл ИФТ альфы в конверте `{"data": [...]}` с `root=data` — success, 4 элемента,
48 полей; тот же файл без `root` и запуск с `bucket` без `s3_key` — падение с причиной.
На стенде не проверяемо: синтаксис GP6 (`COPY ... WITH (...)`, `DISTRIBUTED RANDOMLY`, `jsonb_each`,
`count(*) filter`) — нужен прогон на контуре.

## Принято

- Соединение psycopg2 не закрывалось (`with conn` закрывает транзакцию) → `contextlib.closing`.
- Тело объекта S3 не закрывалось при обрыве разбора → `closing(body)`; отсутствующий ключ — понятная ошибка.
- Ложный зелёный: счётчики считали то, что отдал разбор → синтетика сверяется с `rows` и числом полей.
- Данные после `]`, лишние и пропущенные запятые принимались молча → строгий разбор.
- Битый элемент копил весь файл в буфере → предел `MAX_ITEM`, дальше ошибка.
- `bucket` без `s3_key` молча уходил в синтетику → параметры задаются вместе.
- `(j->>'id')::bigint` падал на нечисловом id → раскладка по полям без приведения типов.
- Ожидание дочитывания срабатывало на любом элементе в конце куска → только у чисел.
- Самопроверка нашла дефект сверх ревью: `12.` | `5` на границе куска разбиралось как `12`
  → ожидание, пока хвост состоит из символов числа.

## Отклонено

- «COPY с опциями в скобках GP6 не принимает» — GP6 (ядро PostgreSQL 9.4) принимает обе формы; на
  стенде не проверяемо, проверить первым прогоном на контуре.
- «`\x01` в SQL уходит сырым байтом» — в исходнике `\\x01`, в SQL литерал `\x01`.
- «Символы U+0001/U+0002 в строках JSON ломают csv» — `json.dumps` экранирует управляющие символы как `\u0001`.
- «batch 50 000 может не влезть в память» — это параметр, значение под данные выбирает запускающий.

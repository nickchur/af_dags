# Delta-спека: даг `tools_s3_to_zip` — потоковый ZIP-архив из S3 в S3

- Дата: 2026-10-19
- Статус: согласована пользователем 19.10.2026 («Фиксируем, давай план»)
- Baseline: нет; точка отсчёта — текущее поведение `s3_utils` (`s3_path_parse`, `s3_IterStream`, `s3_from_zip`)
- Источник: discover + grill 19.10.2026 (запрос «даг под АФ3 — архив S3 в S3, zip, обязательно потоковый»)

## Мотивация

Нужна ручная выгрузка-копия папки S3 (по умолчанию — логов задач) одним ZIP-файлом, чтобы скачать или передать.
Объёмы — десятки ГБ и сотни тысяч объектов, поэтому сборка обязана быть потоковой: без диска воркера и без
буфера под весь архив. Обратная операция уже есть (`s3_from_zip`); `stream-zip` уже в зависимостях ядра AF3.

## ADDED

- **REQ-s3zip-01** — **источник и приёмник — по одной строке.** Параметры `src` и `dst` — пути формата
  `conn_id://бакет/путь`, как разбирает `s3_path_parse`. По умолчанию `src` — подключение, бакет и префикс
  логов из `[logging]` (`remote_log_conn_id`, `remote_base_log_folder`), `dst` — `<то же подключение>://<бакет
  логов>/archive/`.
- **REQ-s3zip-02** — **отбор объектов.** `src` без маски берёт все объекты под путём; с маской `*`/`?` — объекты,
  чей ключ подходит под маску (fnmatch). «Папки» (ключи на `/`) пропускаются. Число объектов не ограничено
  (нет потолка в 10 000, как у `s3_keys`).
- **REQ-s3zip-03** — **фильтр по дате.** `date_from` / `date_to` (`YYYY-MM-DD`, UTC, обе границы включительно,
  пусто — без границы) отбирают по `LastModified`. Неверный формат даты — падение таска с понятным сообщением.
- **REQ-s3zip-04** — **предохранитель объёма.** Сначала полный обход отобранных ключей; если сумма размеров
  больше `max_size_gb` (по умолчанию 20; 0 — без лимита), таск падает без ретраев до начала записи, в сообщении —
  число объектов и объём. Пустой отбор — тоже падение без ретраев («нечего архивировать»), архив не создаётся.
- **REQ-s3zip-05** — **имя архива.** `dst` на `.zip` — ключ архива как есть. `dst` пустой по ключу или на `/` —
  имя `<последняя папка src>_<YYYYMMDD_HHMMSS>.zip` (время старта, UTC) внутри этой папки.
- **REQ-s3zip-06** — **не затирать.** Существующий ключ архива при `replace=False` (по умолчанию) — падение без
  ретраев до обхода. Ключ архива исключается из отбора, если попадает под `src`.
- **REQ-s3zip-07** — **потоковая сборка.** Объекты читаются из S3 по одному потоком и пишутся в multipart-загрузку
  архива; память воркера не растёт с объёмом архива и числом файлов (ограничена буферами частей), диск не
  используется. Формат — ZIP64 (архивы и файлы > 4 ГБ, > 65 535 записей открываются стандартными
  распаковщиками).
- **REQ-s3zip-08** — **содержимое архива.** Имена записей — ключ относительно префикса `src` (часть до маски),
  в UTF-8; время записи — `LastModified` объекта. `.gz`/`.zip`/`.parquet` не пережимаются (deflate уровня 0:
  режим «без сжатия» в `stream-zip` держит файл целиком в памяти ради CRC), остальное — deflate. Распаковка
  архива даёт побайтно те же объекты.
- **REQ-s3zip-09** — **итог.** На таске — заметка: путь архива, число файлов, сырой объём, объём архива,
  длительность, скорость. Сбой посреди записи не оставляет в приёмнике частичного архива (multipart
  отменяется).
- **REQ-s3zip-10** — **оформление дага.** `dag_id=tools_s3_to_zip`, только ручной запуск (`schedule=None`),
  `max_active_runs=1`, теги `tools`, `s3`; строка версии, `description`, `owner_links`, параметры в
  `Param(description=…)` — по правилам репозитория. Работает на Airflow 3 и Python 3.10.

- **REQ-s3zip-11** — **брошенные части.** Перед записью таск отменяет незавершённые multipart-загрузки `*.zip`
  прямо в папке архива (без подпапок) — хвосты рана, чей под убит жёстко (OOM, SIGKILL) и отмена не успела;
  отменённые ключи — в итоге рана. Безопасно, пока в папку пишет только этот даг (`max_active_runs=1`).
  Добавлено 19.10.2026 по ходу исполнения (замечание: части в квоте, обходу бакета не видны; в правиле
  хранения пункта `AbortIncompleteMultipartUpload` нет).

## Non-goals

- Удаление исходников после архивации (ротация) и долгое хранение: архив живёт по общему сроку бакета логов.
- Нарезка на тома по размеру — вместо неё предохранитель REQ-s3zip-04.
- Другие форматы (tar.gz и т. п.), шифрование и пароль на архив.
- Расписание: только ручной запуск.
- Перенос в AF2 (`master`) — только по слову пользователя.
- Пункт `AbortIncompleteMultipartUpload` в правиле хранения бакетов — в бэклог (затрагивает все бакеты,
  поддержка корп-шлюзом не проверена).

## Критерии приёмки

- Стенд AF3: ран без параметров собирает архив логов в `archive/` бакета логов; `unzip -t` проходит, число
  записей и сырой объём совпадают с заметкой.
- Стенд AF3: `src` с маской и `date_from`/`date_to` — в архиве только подходящие объекты.
- Стенд AF3: `max_size_gb` меньше объёма — ран красный без ретраев, в приёмнике ничего нет.
- Стенд AF3: повторный ран с тем же `dst.zip` и `replace=False` — красный без ретраев; с `replace=True` — архив
  перезаписан.
- Тест без сети (moto или заглушка клиента): архив из нескольких объектов, в том числе > части multipart,
  распаковывается в исходные байты; пустой отбор и превышение лимита — исключения.

# Delta-спека: загрузчик берёт из CTL только своё поддерево сущностей, а не весь реестр

- Дата: 2026-10-21
- Статус: подтверждена пользователем 21.10.2026
- Baseline: `ctl-worker-baseline.md` (ветка `master`; в `develop_3` baseline-спек нет)
- Источник: разбор перезапусков воркеров альфы dev 21.10.2026 (логи подов `zw25z`, `lgb7d`, `tqjqw`,
  отбивки `system_health/`), снимок `ctl_entities_all.json`, ответы пользователя 21.10.2026, проверка
  `tools_ctl_check_api` на контуре 21.10.2026 10:48 UTC

## Мотивация

21.10.2026 четыре воркера альфы dev по очереди убиты SIGKILL (`137`, без SIGTERM); каждый раз за 1–7 с до
смерти на поде стартовали `load_entities` и `load_events`/`load_profile` загрузчика. `load_entities` каждые
5 минут тянет весь реестр CTL `/v4/api/entity` — 402 477 сущностей, 57 МБ JSON — ради 694 сущностей нашего
поддерева; разбор, журнал в GP, сериализация для S3 и заметка дают пик ~0,8 ГБ на задачу, а `load_events`
параллельно читает те же 80 МБ из S3 ради проверки «есть ли такой id». При фоне воркера ~2,1 ГБ две такие
задачи упираются в лимит 3 GiB.

## MODIFIED — изменённое поведение

- **REQ-ctl-worker-39** — было: перечень `ctl_entities` строится обходом плоского реестра `/v4/api/entity` от
  корня `root_entity`; в заметке — размер поддерева и число сущностей того же диапазона id вне поддерева;
  полный список запрашивается раз за прогон и переиспользуется проверкой ссылок →
  станет: **перечень `ctl_entities` строится из одного ответа CTL «все потомки корня»
  (`/v4/api/entity/{root_entity}/child?direct=false`, дерево `{entity, kidz}` вместе с самим корнем).**
  Полный реестр сущностей загрузчик не запрашивает. Состав и порядок `ctl_entities` детерминированы (тот же
  набор при том же состоянии CTL даёт тот же объект и тот же хэш). В заметке прогона — размер поддерева.
- **REQ-ctl-worker-35** — было: сущность в ссылке на событие считается отсутствующей, если её нет в полном
  реестре CTL → станет: **сущность существует, если она есть в `ctl_entities`; сущность вне поддерева
  проверяется адресным запросом к CTL по её id.** Ответ 404 — сущности нет, ключ висячий (причина «сущности
  N нет в CTL», как раньше). Прочие 4xx (401/403 — сбой авторизации, а не отсутствие), 5xx, таймаут — сущность
  висячей НЕ считается, сбой пишется в лог задачи; отдельной заметки «Ошибка API» на каждую сущность нет. Каждая сущность вне поддерева спрашивается не больше одного раза за прогон. Отсев по профилям и
  порог 25 % — без изменений.
- **Имена сущностей `ctl_enames`** (уточнение при исполнении 21.10.2026: на имени стоит Asset события
  `CTL/<профиль>/<id>/<имя>`, оно обязано совпадать с прежним) — было: имена поддерева, сущностей событий и их
  родителей из полного реестра → станет: **те же ключи и те же имена**; записи вне поддерева (сущности событий и
  родители — свои и родитель корня) берутся тем же адресным запросом, каждая не больше раза за прогон. Сбой CTL
  по сущности — имя остаётся от прошлого прогона (не `_Not_found_`); 404 — `_Not_found_`, как раньше.

## REMOVED — удаляемое поведение

- **REQ-ctl-worker-39 (часть)** — счёт сущностей «того же диапазона id вне поддерева» в заметке прогона и
  соответствующий сценарий приёмки «Сущность заведена мимо корня». Решение пользователя 21.10.2026: без
  полного реестра посчитать нечем; потребителей у числа нет, кроме заметки.
- **Объект `ctl_entities_all` в S3** — загрузчик его больше не пишет и не читает. Других читателей нет
  (проверено поиском по af_dags и etl-core 21.10.2026). Лежащий объект уходит по сроку жизни бакета.

## Ограничения и контракты

- Форма ответа `child?direct=false` (с контура 21.10.2026, `tools_ctl_check_api`):
  ```json
  {"entity": {"id": 941000000, "name": "HR", "path": "...", "storage": "HDFS", "parentId": 0},
   "kidz": [{"entity": {...}, "kidz": [...]}, ...]}
  ```
  Записи `entity` по полям совпадают с записями плоского реестра.
- Гейт полноты пройден 21.10.2026: для корня 941000000 ответ — 716 узлов, ровно поддерево по плоскому
  реестру того же дня, без пропусков и лишних, поля совпадают у всех. Синхронность с созданием новых
  сущностей (дефект поисковой ручки 17.09) снимком не доказана — проверяется приёмкой после выкладки.
- Код обязан работать на Python 3.10; ветка `develop_3` (AF3), AF2 не трогаем.

## Non-goals

- Рост памяти простаивающего воркера 1,1 → 2,1 ГБ за 2–3 часа — отдельный разбор.
- Лимит памяти воркера в gitops и `worker_concurrency`.
- Сравнение MD5 с ETag в `ctl_obj_save` для multipart-объектов и журнал GET в GP (`pr_log_ctl`) — с уходом
  80-мегабайтного ответа теряют остроту, отдельной задачей.
- Удаление уже лежащего `ctl_entities_all` из S3 вручную.

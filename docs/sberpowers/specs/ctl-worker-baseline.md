# Baseline-спека: ctl-worker

- Дата: 2026-10-04
- Статус: реализована
- Источник: openspec/specs/ctl-worker/spec.md, перевод 2026-10-04

## Назначение

Оркестрация ETL-загрузок Greenplum через внешнюю систему CTL: динамическая генерация DAG'а на каждый workflow, опрос очереди активных загрузок, выполнение SQL в Greenplum, возврат результата и статистики в CTL, публикация событий для зависимых DAG'ов и надзор за зависшими загрузками. Каталог `ctl_worker/` — единственное место, где Airflow разговаривает с CTL API от имени загрузки.

## Требования

- **REQ-ctl-worker-01** — **Один DAG на каждый workflow профиля.** Система создаёт ровно один DAG с идентификатором `CTL.{wf_name}` на каждый workflow из `ctl_workflows`, принадлежащий текущему профилю, исполняемый оркестратором `dummy` и не помеченный удалённым (`deleted = true`). Ошибка сборки одного DAG'а не прерывает сборку остальных: исключение логируется, генерация продолжается со следующего workflow, а модуль импортируется без ошибки. Workflow с категорией, совпадающей с `archive_category`, получают тег `CTL_archive` вместо `CTL`.
- **REQ-ctl-worker-02** — **Расписание берётся из метаданных workflow.** Система строит расписание DAG'а из метаданных CTL, поддерживая Dataset-события, cron, их комбинацию (`DatasetOrTimeSchedule`) и условие запуска с логикой AND/OR. Если расписание собрать или разобрать не удалось, DAG создаётся без расписания (`schedule = None`) и с тегом ошибки `AF_error`, а причина сбоя записывается в лог. Кому именно строится расписание, определяет режим оркестрации: требование описывает состав и разбор расписания, а не распределение его между DAG'ами.
- **REQ-ctl-worker-03** — **Пайплайн загрузки.** Система выполняет загрузку строгой последовательностью тасков `run_prm → run_exe → run_end`. При заданном `wf_tfs_in` перед выполнением добавляется таск приёма файлов `run_tfs`, а DAG получает тег `tfs-in`. При заданном `wf_tfs_out` после выполнения добавляется таск передачи файлов `run_out`.
- **REQ-ctl-worker-04** — **Неидемпотентные шаги не повторяются автоматически.** Таски, чьё повторение создаёт дублирование работы — `run_prm` (POST `/loading` создаёт новый `loading_id`) и `run_exe` (`pr_swf_start_ctl` запускает ETL), — объявляются без автоматических повторов Airflow: повторами загрузки управляет CTL через статус `TIME-WAIT`. Повторная попытка `run_exe` сначала опрашивает лог Greenplum: если атомарная процедура закоммичена и ответ найден в логе, он возвращается как результат без повторного вызова `pr_swf_start_ctl`. Отсутствие ответа само по себе не означает, что работы не было: при обрыве соединения запрос в базе продолжается, поэтому повторная попытка проверяет занятость серверного процесса прошлой попытки и ждёт завершения работы в пределах потолка времени загрузки, а не объявляет её несостоявшейся, иначе второй ETL пойдёт параллельно первому. Работа считается несостоявшейся только тогда, когда ответа нет в логе и серверный процесс свободен; при исчерпании времени ожидания, недоступности базы или неизвестном процессе таск завершается ошибкой без повторного запуска ETL. Запрос статуса процесса выполняется с коротким ожиданием, чтобы не блокировать дефицитный пул.
- **REQ-ctl-worker-05** — **Трактовка кода результата.** Система интерпретирует поле `res` результата `pr_swf_start_ctl` однозначно: `res > 0` означает успех, `res = 0` — отсутствие данных (загрузка завершается успешно с пометкой `no`, таск `run_exe` переводится в `skipped`), `res < 0` — ошибку (таск `run_exe` помечается `failed`, `run_end` фиксирует статус в CTL и падает). Отсутствующее поле `res` приравнивается к ошибке со значением `-99`.
- **REQ-ctl-worker-06** — **Повтор загрузки по списку условий.** Система назначает повтор загрузки, если остаток попыток больше нуля и список `retry_on` содержит словесный итог (`ok`, `no`, `error`) либо строковое представление числового кода `res`. При совпадении условий загрузка переводится в CTL в статус `TIME-WAIT` с расчётом времени следующего запуска (к базовой задержке `delay` добавляется `add` на каждую предыдущую попытку), а таск `run_end` завершается пропуском (`skipped`), а не падением. При исчерпании попыток повтор не назначается, а загрузка финализируется по результату последней попытки.
- **REQ-ctl-worker-07** — **Финальный статус загрузки.** Система завершает загрузку статусом `SUCCESS` и действием `Completed`, если хотя бы одна попытка вернула `ok` или `no`. Если все попытки завершились ошибкой, загрузка получает статус `ERROR`, а действие выбирается по настройке: `Aborted` при включённом `faultTolerance.abortOnFailure` и `Completed`, если флаг снят.
- **REQ-ctl-worker-08** — **Публикация статистики и событий по успеху.** Система публикует Dataset `CTL/{profile}/{eid}/{ename}` по каждой сущности загрузки только при успешном завершении (`res > 0`), передавая в метаданных события ссылку на загрузку в CTL, метку времени и собранную статистику. Метрики `cdc`, `hub` и `dataBusiness` отправляются в CTL только при успехе, тогда как произвольные метрики из `stat` передаются независимо от кода результата. Если сущность отсутствует в outlets DAG'а, публикация для неё пропускается с предупреждением в лог, не прерывая остальные сущности. При наличии в ответе поля `html` сформированный отчёт отправляется в CTL как статистика первой сущности.
- **REQ-ctl-worker-09** — **Проверка состояния загрузки перед каждым шагом.** Каждый таск пайплайна загрузки перед началом работы проверяет актуальное состояние загрузки в CTL (активность, нахождение в ожидаемом статусе) и немедленно прекращает выполнение по решению `ctl_chk_status` / `raise_status`, если загрузка была отменена или переведена в неактивный статус извне.
- **REQ-ctl-worker-10** — **Сенсор запускает загрузки из очереди CTL.** Сенсор с периодичностью один раз в минуту запрашивает в CTL загрузки в статусах `RUNNING`, `TIME-WAIT` и `EVENT-WAIT`, отбирает готовые к старту (наступление событий, истечение срока ожидания, отсутствие активного дублирующего запуска) и инициирует выполнение соответствующего DAG'а через `trigger_dag` либо публикацией Dataset согласно конфигурации. Перед запуском загрузке в CTL присваивается статус `RUNNING` с пометкой `WAIT-AF` и идентификатором запуска. Загрузки в иных статусах, загрузки с ещё не наступившим временем ожидания или уже имеющие запущенный run пропускаются без повторного создания запуска.
- **REQ-ctl-worker-11** — **Загрузчик метаданных пишет только изменения.** Загрузчик метаданных запрашивает из CTL профиль, категории, сущности, имена сущностей, workflows и события, сохраняя их в S3 и Airflow Variables. Запись в хранилище и обновление переменных происходят исключительно при обнаружении изменений по сравнению с ранее сохранённым содержимым, контролируемом по хэшу.
- **REQ-ctl-worker-12** — **Монитор разбирает зависшие загрузки.** Монитор периодически анализирует активные загрузки и назначает управляющие действия исходя из их статуса и длительности нахождения в нём: `ERRORCHECK` переводится в `reRunned`; `LOCK` и `LOCK-WAIT` старше порога `lock_stale` (по умолчанию 5 часов) — в `reStarted`; `RUNNING` с признаком выполнения старше `run_stale` (по умолчанию 6 часов) — в `reRunned`; `TIME-WAIT` с временем старта, просроченным более чем на `wait_grace` (по умолчанию 15 минут) — в `reStarted`; `ERROR` завершается действием `Aborted` при включённом `abortOnFailure` и `Completed` при выключенном. Загрузки моложе `new_grace` (по умолчанию 60 минут) признаются новыми и не затрагиваются, а загрузки с активным выполнением в Airflow пропускаются. Порог для `RUNNING` не опускается ниже потолка запроса загрузки `wf_timeout` плюс 10 минут, предотвращая перезапуск ещё выполняющихся запросов.
- **REQ-ctl-worker-13** — **Время старта TIME-WAIT определяется из нескольких источников.** Назначенное время старта загрузки в статусе `TIME-WAIT` определяется по первому доступному источнику в строгом приоритете: собственный лог вида `{'time': …}`; условие запуска `startCondition` самой загрузки; текстовая строка CTL `Start scheduled on …`; ближайшее срабатывание расписания воркфлоу от момента фиксации статуса. Если у загрузки задан `startCondition`, расписание воркфлоу не применяется, так как CTL игнорирует его. Состояние условия берётся в готовом виде из ответа CTL (`state.satisfied`, `state.satisfiedDttm`) без самостоятельного вычисления предикатов. Если ни один источник не даёт времени, загрузка не отменяется, а пропускается, оставаясь на усмотрение CTL, а её превышение SLA фиксируется отдельным списком.
- **REQ-ctl-worker-14** — **Конфигурация меняется только с PIN-кодом.** DAG изменения конфигурации сохраняет параметры в Airflow Variable `ctl_config` исключительно при точном совпадении введённого PIN-кода со значением секрета `AIRFLOW__CTL_PIN`. При несовпадении сохранение отменяется с уведомлением в заметке, а значение PIN-кода удаляется из структуры сохраняемых данных при любом исходе.
- **REQ-ctl-worker-15** — **Непрерывный контроль подключений.** DAG проверки подключений содержит по одному сенсору на каждое сконфигурированное подключение, выполняет проверки в режиме `reschedule` без удержания слота пула между опросами и не приводит к аварийному завершению DAG'а: недоступность подключения завершает задачу мягким пропуском (`soft_fail`), сохраняя выполнение остальных проверок.
- **REQ-ctl-worker-16** — **Пропавший даг не роняет сенсор.** Если при попытке запуска DAG не обнаруживается в базе, сенсор определяет точную причину — отсутствие воркфлоу в `ctl_workflows`, признак удаления, принадлежность чужому профилю либо наличие строки в таблице `dag` при её отсутствии в `serialized_dag`, — фиксирует причину в заметке и пропускает загрузку без необработанных исключений. Статус загрузки в CTL остаётся неизменным, обеспечивая автоматический запуск после восстановления DAG'а.
- **REQ-ctl-worker-17** — **Усохший список воркфлоу не доходит до фабрики.** Загрузчик не перезаписывает переменную `ctl_workflows`, если ответ CTL пуст или оказался короче предыдущего на величину, превышающую порог `wf_shrink_pct` (по умолчанию 10 %): в такой ситуации таск завершается ошибкой, а сохранённые метаданные остаются нетронутыми. При успешном сохранении обновляется контрольный счётчик `ctl_workflows_stat` с количеством воркфлоу профиля. Фабрика DAG'ов сверяет прочитанный набор с этим счётчиком и при обнаружении пустого или усохшего списка прерывает разбор файла ошибкой импорта, предотвращая удаление ранее сериализованных DAG'ов из базы.
- **REQ-ctl-worker-18** — **Монитор добивает зависшие таски, раны и загрузки.** Монитор находит в метабазе задачи в состоянии `RUNNING`, чей job не зарегистрирован, не активен или не обновлял хартбит дольше порога `zombie_after` (по умолчанию 6 часов), и переводит их в статус упавших. Минимальный допустимый порог составляет пять минут: санитар с околонулевым порогом закрывает живые раны, поэтому такое значение роняет таск санитара без выполнения уборки. Вся цепочка таймаутов строго согласована: `gp_timeout` ниже `gp_server_limit`, `zombie_after` больше `gp_timeout` плюс 10 минут, а `run_stale` не меньше `zombie_after`; нарушение согласованности приводит к ошибке таска санитара с объяснением без изменения данных. Тем же порогом закрываются раны без живых задач (состояние `up_for_reschedule` обязательно считается живым, иначе санитар закрывал бы ждущие сенсоры вместе с их ранами) и раны в `RUNNING` или `QUEUED`, чей DAG пропал из `serialized_dag`: связанная загрузка в CTL переводится в `ERROR` с описанием причины и закрывается как незавершённая. Раны запаузенных DAG'ов закрываются тем же порогом в `QUEUED`, а в `RUNNING` — только при отсутствии выполняющихся задач (планировщик запаузенный DAG не разбирает, и `dagrun_timeout` на него не действует, поэтому без санитара он висит вечно; незаконченные задачи переводятся в `skipped`, как при `dagrun_timeout`); загрузки запаузенных DAG'ов при этом не изменяются, поскольку пауза — это плановые работы, а не смерть (снимут паузу — сенсор запустит загрузку заново), а закрытие загрузки привело бы к потере работы из-за окна обслуживания. Количество закрываемых ранов за один прогон лимитировано, а режим «только показать» сообщает полное число находок отдельно от показанного списка (иначе накопленный бэклог закрывается одним заходом, а его размер виден только после закрытия) и разделяет находки по исходу (что закрывается вместе с загрузкой, а что — без неё) без внесения изменений в метабазу и CTL.
- **REQ-ctl-worker-19** — **Сенсор TFS опрашивает все источники независимо.** Сенсор TFS опрашивает каждый источник `tfs-in` независимо, поэтому сбой или недоступность одного источника не прерывает опрос остальных. Причина недоступности фиксируется понятным текстом с указанием имени бакета, подключения и ответа шлюза, а стек ошибки сохраняется в логе. Если файлы обнаружены хотя бы в одном источнике, они передаются на обработку, а проблемные источники выводятся в заметке таска. Таск падает со сводным списком ошибок только в том случае, когда файлы не найдены нигде и были сбои опроса; если все источники доступны, но не содержат файлов, сенсор продолжает штатное ожидание.
- **REQ-ctl-worker-20** — **Симулятор существует не на всех контурах.** DAG симулятора нагрузки создаётся исключительно на контурах DEV, IFT и PSI. На боевом контуре (`PROM`), при неизвестном имени контура либо при отсутствии переменных `ENV_STAND` и `ENVIRONMENT` файл импортируется без создания DAG'а с записью в лог. Перечень разрешённых контуров зафиксирован в коде и не переопределяется из конфигурации тракта или параметров воркфлоу CTL.
- **REQ-ctl-worker-21** — **События в CTL создаёт только DEV.** Режим симуляции с записью значений событий в CTL функционирует только на контуре DEV. На других поддерживаемых симулятором контурах (IFT, PSI) выполнение этого режима завершается пропуском с поясняющей заметкой, тогда как публикация Dataset-сигналов и запуск DAG'ов продолжают работать в штатном порядке.
- **REQ-ctl-worker-22** — **Тестовый режим доступен только на DEV и IFT.** Фиктивное выполнение загрузки (замена реального SQL-выражения ожиданием и подстановка кода результата) доступно исключительно на контурах DEV и IFT. На остальных контурах, включая боевой, PSI, а также при неизвестном или незаданном окружении, тестовый режим игнорируется, а загрузка выполняется реально с явной фиксацией причины игнорирования в логе и заметке таска.
- **REQ-ctl-worker-23** — **Тестовый режим не включается из CTL.** Тестовый режим активируется только через общую конфигурацию тракта. Параметры конкретного воркфлоу, поступающие из CTL, не могут включать фиктивное выполнение и игнорируются при попытке активации режима.
- **REQ-ctl-worker-24** — **Исход фиктивного выполнения задаётся профилем.** Тестовый режим поддерживает три профиля исхода: только успех, успех и «нет данных», а также успех, «нет данных» и ошибка. Подставляемые коды строго следуют контракту `pr_swf_start_ctl` (положительный — успех, ноль — нет данных, отрицательный — ошибка, включая код циклического повтора). Профиль с ошибками делает неуспешный исход достижимым, а факт подстановки кода явно отображается в заметке результата, иначе тестовую ошибку не отличить от настоящей.
- **REQ-ctl-worker-25** — **Итог загрузки сохраняется отдельно от состояния на входе.** После выставления финального статуса загрузки в CTL воркер фиксирует в хранилище итоговый снимок состояния (статус в CTL, лог результата, признак завершения, время пробуждения для повторов) до перехода таска к пропуску или падению. Исходный снимок состояния на входе в шаг сохраняется отдельно и не подменяется итоговым. Снимки различных попыток одной и той же загрузки изолированы и не затирают друг друга. Ошибка записи снимка в хранилище не отменяет результат загрузки в CTL и отражается в логе и заметке.
- **REQ-ctl-worker-26** — **Симулятор запускает только то, что способно стартовать.** Перед запуском DAG'а симулятор проверяет его готовность к старту: отсутствие паузы, активность и наличие в `serialized_dag`. Неспособные стартовать DAG'и не запускаются, исключая образование зависших в очереди ранов. Если готовых DAG'ов нет, таск завершается пропуском, а в заметке раздельно отображается количество кандидатов, отсеянных по свойствам воркфлоу и по состоянию DAG'а. Воркфлоу чужих профилей исключаются из подсчёта отсеянных.
- **REQ-ctl-worker-27** — **Неудачный запуск виден в заметке.** При неудаче создания рана причина сбоя фиксируется в заметке таска с указанием имени воркфлоу и характера отказа, а сам запуск исключается из списка созданных. Наличие уже существующего рана не трактуется как отказ — воркфлоу остаётся среди запущенных, но факт обнаружения существующего рана выводится отдельной строкой в заметке.
- **REQ-ctl-worker-28** — **Запаузенный даг не запускается молча.** Если DAG воркфлоу запаузен, сенсор не запускает его (запуск паузу не проверяет и создаёт ран, который не поедет до снятия паузы), сохраняя статус загрузки в CTL без изменений и формируя запись пропуска с указанием источника паузы. Происхождение паузы определяется достоверно: при наличии записи в журнале метабазы указываются автор и время; если пауза вызвана ключом массовой паузы в конфигурации тракта, называется рубильник; при отсутствии записей в журнале происхождение не угадывается, а указываются оба возможных варианта (пауза при создании либо выставление через REST/код), поскольку уверенно названная не та причина хуже отсутствия ответа (оператор снимет паузу, поверив, что за ней ничего не стоит). Сенсор самостоятельно паузу не снимает, так как у DAG'а воркфлоу, не стоящего на расписании в CTL, снятие паузы включает и его собственное расписание Airflow, о котором CTL не просил. Факт пропуска регистрируется с временным прореживанием для статистического учёта, при этом ошибка записи следа не отменяет сам пропуск.
- **REQ-ctl-worker-29** — **Загрузки, ждущие снятия паузы, видны в мониторе.** Монитор отображает отдельным блоком рядом со сводкой SLA загрузки, которым есть куда двигаться прямо сейчас, но чей DAG запаузен, указывая имя воркфлоу и возраст ожидания от последней смены статуса. Загрузки, которым пауза не мешает (выполняющиеся, доигрывающие, ожидающие своего срока), в список не включаются, так как паузы они не ждут, и заметка о них воспитывает привычку её не читать; загрузка выпавшего из воркфлоу DAG'а также не включается, поскольку ей нужна диагностика пропавшего DAG'а, а не ожидание. При большом числе ожидающих в заметке показываются их количество и старейшие инциденты, а полный список остаётся в логе таска, иначе длинный список вытесняет из заметки сводки, записанные тем же проходом.
- **REQ-ctl-worker-30** — **Режим оркестрации задаётся явно.** Режим оркестрации явно задаётся в конфигурации тракта одним из трёх значений: `ctl`, `mixed` или `af` (по умолчанию `mixed` при отсутствии ключа — поведение, сложившееся к моменту введения режима, чтобы выкладка кода ничего не меняла сама по себе). Режим определяет, строит ли фабрика DAG'у собственное расписание Airflow: в режиме `ctl` расписание не создаётся (расписаниями и зависимостями владеет CTL), в `mixed` создаётся только для воркфлоу без расписания в CTL, в `af` создаётся всегда. Запуск DAG'а по загрузке из CTL работает во всех режимах, поскольку ручной запуск не зависит от того, у кого расписание.
- **REQ-ctl-worker-31** — **Источник события живёт там, где событие происходит.** Режим оркестрации делит между CTL и Airflow расписания и зависимости, но не переносит источники внешних событий: ТФС и Kafka остаются за Airflow в любом режиме, так как CTL про них не знает, файлы приносят сенсор ТФС и приёмник Kafka, и поднимающий DAG датасет сохраняется в его расписании независимо от режима, тогда как события сущностей во всех режимах поступают из CTL. Воркфлоу, запускаемый только приходом файла, не остаётся без триггера ни при каком режиме.
- **REQ-ctl-worker-32** — **Пауза при создании — отдельная настройка.** Создание DAG'а запаузенным управляется собственной настройкой, а не выводится из наличия расписания в CTL. По умолчанию в режиме `ctl` DAG'и создаются незапаузенными, а в остальных режимах (`mixed`, `af`) — запаузенными, потому что DAG с собственным расписанием не должен стартовать сам, пока его не взвели. Ключи массовой паузы и массового снятия паузы имеют безусловный приоритет над этой настройкой: они применяются к уже созданному DAG'у при каждом запуске, тогда как настройка действует только в момент создания (разные слои — умолчание и ручной рубильник).
- **REQ-ctl-worker-33** — **Расписание в CTL не ставится из Airflow, когда им владеет Airflow.** В режиме оркестрации Airflow форма воркфлоу блокирует установку расписания в CTL (как немедленную, так и отложенную при создании загрузки) с обязательной фиксацией причины в заметке во избежание двойного запуска. При этом операция снятия существующего расписания в CTL остаётся доступной во всех режимах для обеспечения беспрепятственной миграции.
- **REQ-ctl-worker-34** — **Режим «оркестрирует Airflow» предупреждает о двойном запуске.** В режиме `af` фабрика проверяет, не остались ли в CTL воркфлоу на расписании, и выводит в лог разбора предупреждение с их числом, поскольку иначе их будут запускать обе системы параллельно. Проверка не роняет разбор файла и строит DAG'и штатно, иначе переключение режима становилось бы опасным.
- **REQ-ctl-worker-35** — **Висячие ссылки на события не опрашиваются.** Загрузчик метаданных исключает из `ctl_events` ссылки на события, сущности или профили которых отсутствуют в актуальных реестрах CTL, фиксируя исключённые ключи в заметке прогона с указанием воркфлоу, ссылки и причины. Отсев по профилю не выполняется при отсутствии списка профилей или своего профиля в нём. Если под исключение попадает более 25 % ключей, загрузчик оставляет список `ctl_events` без изменений и выводит предупреждение о подозрительном ответе CTL.
- **REQ-ctl-worker-36** — **Сбой одного ключа не роняет опрос событий.** Сенсор событий опрашивает каждый ключ `ctl_events` автономно: сбой запроса или разбора по отдельному ключу логируется, не прерывая опрос остальных ключей. Проверка завершается падением только в случае, если ошибкой завершились абсолютно все ключи. Значение статистики с пустым или `null` идентификатором `loading_id` трактуется как корректное событие без загрузки, а не как ошибка.
- **REQ-ctl-worker-37** — **Пул задачи — по внешнему ресурсу, размеры пулов меняет только сторож подключений.** Задача агента занимает слот пула того внешнего ресурса, который она тратит: вызовы API CTL — `ctl_pool`, нагрузка на Greenplum — `gp_pool`, переносы ТФС — `files_pool`, а задачи без внешних ресурсов (заметки, публикация Dataset) сидят в `default_pool`. Размер пулов подключений меняет только сторож подключений (`CTL.<profile>.test_conn`), сидящий в необнуляемом пуле: сбой проверки не останавливает сторожа — пул закрывается обнулением слотов, а проверка продолжается, чтобы вернуть размер, когда подключение оживёт. Пул `ctl_pool` имеет фиксированный размер, а не растёт вслед за очередью. Сенсор не останавливает приём загрузок из-за недоступности подключения, которое ему не нужно.
- **REQ-ctl-worker-38** — **Сводка SLA делится по возрасту нарушения.** Монитор разделяет нарушения SLA на две группы по возрасту с последней смены статуса загрузки: нарушения не старше `sla_dead` (по умолчанию 30 дней) попадают в заметку задачи и прогона как дежурная работа, а нарушения старше этого срока показываются отдельным списком только в заметке задачи, поскольку такая загрузка не опаздывает, а брошена, и в заметке прогона вытеснила бы сводки действий и статусов того же прохода. Списки упорядочиваются по возрасту нарушения, а не по идентификатору загрузки (при порядке по ID видимость нарушения не связана с его возрастом), и при нехватке места показывают общее число и старейшие инциденты, сохраняя полный перечень в логе задачи.
- **REQ-ctl-worker-39** — **Список сущностей полон и берётся из плоского списка.** Загрузчик формирует перечень `ctl_entities` путём обхода плоского реестра сущностей CTL (`/v4/api/entity`) вниз по `parentId` от корня `root_entity`, исключая использование поиска по дереву из-за задержек обновления поискового индекса. Порядок обхода строго детерминирован для корректного хэширования. В заметке прогона отражаются размер собранного поддерева и количество сторонних сущностей того же диапазона ID вне поддерева. Полный список сущностей запрашивается из CTL не более одного раза за прогон и повторно используется задачей контроля ссылок.
- **REQ-ctl-worker-40** — **Усечение при приёме файлов — одно на таблицу за прогон.** Приём файлов очищает целевую таблицу не более одного раза за прогон, так как маска даёт несколько объектов, а очистка идёт отдельной транзакцией и при очистке на каждый файл стирала бы загруженное предыдущими файлами. Когда целевая таблица определяется из имени файла, очистка выполняется для каждой уникальной таблицы, поэтому счёт ведётся по таблицам, а не по числу файлов. Файл, упавший до этапа очистки, не лишает следующий файл права очистить таблицу.
- **REQ-ctl-worker-41** — **Таймауты выстраиваются от лимита Greenplum.** Потолок запроса загрузки в Greenplum (`statement_timeout` сессии) берётся из `wf_timeout` воркфлоу, а при его отсутствии — из `gp_timeout` конфигурации (по умолчанию 4 ч 25 мин, что на 5 минут ниже серверного лимита `gp_server_limit` в 4 ч 30 мин по правилу GPCC «Query Time 4,5H (GLOBAL)»): сервер обрывает запрос вместе с соединением, и ни лог ошибки, ни ответ функции записаться не успевают, тогда как собственный таймаут ловится обработчиком и оставляет следы. Индивидуальный `wf_timeout` воркфлоу не урезается, а если он не ниже серверного лимита, выводится предупреждение в лог и заметку задачи. Разбор потолка централизован в единой функции для воркера и монитора. Таск выполнения получает `execution_timeout` на 10 минут больше потолка, остальные таски воркера используют `task_timeout`. Механизм Airflow-SLA не применяется, так как в AF2 он считается от следующего по расписанию рана и у DAG'ов без расписания Airflow не срабатывает, а в AF3 отсутствует.
- **REQ-ctl-worker-42** — **Повтор run_exe находит запуск по номеру загрузки.** Повторная попытка `run_exe` определяет, выполняется ли ещё запуск загрузки в Greenplum, по номеру загрузки в тексте запроса (`pg_stat_activity`), а не по данным прошлой попытки в XCom, так как Airflow стирает XCom задачи в начале каждой попытки. Если ответа в журнале нет и запуска нет, работа достоверно не выполнена, и `run_exe` возвращает в `run_end` результат-ошибку (`res = -9`), чтобы повторы воркфлоу применились сразу. Если Greenplum недоступен или запуск не закончился за потолок ожидания, `run_exe` завершается ошибкой, оставляя загрузку монитору.
- **REQ-ctl-worker-43** — **Процедура загрузки вызывается одной попыткой.** Вызов процедуры `pr_swf_start_ctl` из `run_exe` не повторяется внутри попытки таска: обрыв соединения запрос в Greenplum не останавливает, и повтор дал бы второй ETL параллельно.
- **REQ-ctl-worker-44** — **Итог загрузки уходит в CTL первым.** Таск `run_end` имеет повышенный абсолютный вес приоритета 900, благодаря чему первоочередно получает свободный слот в `ctl_pool` относительно стандартных задач и минимизирует задержку перевода статуса загрузки из `RUNNING` в CTL.
- **REQ-ctl-worker-45** — **Отчёты выполняются по-настоящему и в тестовом режиме.** Потоки, чьи имена начинаются с префиксов из списка `test_real` конфигурации `ctl_config` (по умолчанию `pc1080.mail_`, `pc1080.check_`), выполняют реальное SQL-выражение `wf_exe` даже при активном параметре `test_mode`, а их код результата не подменяется. Данный список задаётся исключительно через `ctl_config`.
- **REQ-ctl-worker-46** — **Полная копия отчёта сохраняется в бакет логов.** Если результат выполнения содержит поле `html`, таск `run_end` до отправки в CTL сохраняет полный отчёт в бакет логов по пути `ctl/ctl_reports/{loading_id}.json`. Если размер раздела превышает лимит CTL (`max_html` × 10), он не отправляется в CTL, а в заметке таска указываются его размер и путь к сохранённой копии. Ошибка сохранения копии в S3 не влияет на исход финализации загрузки.
- **REQ-ctl-worker-47** — **Лимит частоты CTL — повтор, а не отказ.** Клиент CTL держит частоту запросов не выше `ctl_rps` из `ctl_config` (по умолчанию 10 в секунду) внутри процесса. Ответ CTL 429 повторяется после паузы (1–4 с), а не трактуется как отказ, так как запрос, отвергнутый по лимиту, CTL не выполнял, и повтор безопасен в том числе для записи. Эмулятор CTL на стенде отвечает 429 сверх того же порога суммарно по всем клиентам.
- **REQ-ctl-worker-48** — **Монитор ведёт потоки ue_category.** Монитор разбирает две группы загрузок: свои (профиль контура и оркестратор `dummy`) по правилам Airflow и Greenplum, и потоки `ue_category` (любой профиль и оркестратор, кроме своих) по собственным порогам: статус без изменений дольше `ue_stale` переводит загрузку в `reStarted`; статус `RUNNING` дольше `wf_timeout` воркфлоу или `ue_run_max` (сутки) — в `reStarted`; просрочка `TIME-WAIT` больше `ue_grace` — в `reStarted`; пришедшее событие без запуска — в `reStarted`; `ERROR` и `SUCCESS` потоков UE закрываются как у своих. Поток UE на расписании без активной загрузки дольше `ue_grace` получает новую загрузку (`Started`), если CTL перед созданием подтвердил отсутствие активной загрузки. Писем монитор не рассылает, так как их отправляет CTL.
- **REQ-ctl-worker-49** — **Каждый поток дерева под присмотром.** Загрузчик проверяет, что каждый неудалённый и неархивный workflow дерева `root_category` прикреплён к Airflow (профиль контура и движок `dummy`) либо входит в `ue_category`. Воркфлоу вне обеих категорий (`orphan`) и входящие в обе одновременно (`double`) фиксируются в заметке рана и учитываются в счётчиках `ctl_workflows_stat` без падения загрузчика. Архивные потоки из `archive_category`, стоящие на расписании, отображаются отдельно как `archive_live`.
- **REQ-ctl-worker-50** — **Импорт модулей CTL не ходит в сеть и не требует Airflow Variables.** Модули каталога `ctl_worker/` (`ctl_core`, `ctl_utils`) выполняют сетевые вызовы и считывание конфигурации исключительно в момент первого функционального обращения, а не при импорте. Модули импортируются единообразно от корня каталога DAG'ов (`ctl_worker.ctl_utils`) и исключаются из разбора dag-processor как самостоятельные DAG-файлы.
- **REQ-ctl-worker-51** — **Решатели возвращают статус, а не бросают исключение.** Функции-решатели (`ctl_chk_status`, `ctl_chk_new`, `ctl_chk_wait`, `ctl_chk_expire` и аналогичные) возвращают кортеж `(status, payload)`, где `status` принимает значения `ok`, `skip` или `fail`. Трансляция полученного статуса в логику управления потоком выполнения выполняется вызывающим таском с помощью функции `raise_status` (порождающей `AirflowSkipException` или ошибку), тогда как исключения сохраняются только для низкоуровневых транспортных операций (HTTP, SQL, S3).
- **REQ-ctl-worker-52** — **Обращения к CTL API ограничены по темпу и повторяются при обрыве.** Функция `ctl_api` ограничивает частоту вызовов внутри процесса задачи (не более 100 обращений в секунду с добором недостающего интервала ожиданием) и повторяет запрос до трёх раз с экспоненциальной паузой при таймауте, обрыве соединения и ответе 5xx. Одновременность обращений к CTL между задачами ограничивается размером пула `ctl_pool`. GET-запросы, кроме `statval` и `tmpl`, записываются в журнал Greenplum через `pr_log_ctl`, когда пул `gp_pool` открыт; значения передаются параметрами запроса, а сбой записи не роняет вызов.
- **REQ-ctl-worker-53** — **Запросы к Greenplum и PostgreSQL переживают обрыв соединения.** Функция `gp_exe` и вспомогательные методы выполнения запросов повторяют выполнение до трёх раз с экспоненциальной задержкой при возникновении ошибок `OperationalError`, `InterfaceError` или обрыве соединения, и ограничивают длительность запроса переданным таймаутом. Ошибки синтаксиса SQL повторам не подвергаются и передаются вызывающему немедленно.
- **REQ-ctl-worker-54** — **Объекты читаются из Variable, а хранятся в S3.** Функция `ctl_obj_load` сначала ищет объект в Airflow Variable и обращается к S3 только при её отсутствии (при отсутствии объекта в обоих местах возвращается пустой словарь); `ctl_obj_save` пишет объект в S3 и обновляет Variable по требованию, а для проверки изменений хэш объекта в S3 определяется без загрузки тела (`ctl_obj_etag`). Переменная Variable обновляется независимо от того, изменился ли объект в S3: совпадение хэшей означает только то, что загружать тело не нужно, тогда как переменная может отставать и догнать сама не сможет, так как читатели берут её первой.
- **REQ-ctl-worker-55** — **Конфигурация повторов восстанавливается из нескольких источников.** Функция `ctl_get_retry` определяет параметры повторов по приоритетной цепочке: явно переданный словарь → параметры загрузки → восстановление из лога статуса CTL → генерация новой конфигурации на основе `wf_retry_cnt` либо `faultTolerance.numAttempts`. При отсутствии настроек повторов во всех источниках возвращается пустой словарь.
- **REQ-ctl-worker-56** — **Ожидание событий по стратегиям AND и OR.** Функция `ctl_events_mon` сравнивает метку времени публикации каждого включённого события со временем старта: при стратегии AND ожидание заканчивается, когда наступили все события, при OR — когда наступило хотя бы одно. Выключенные события пропускаются, а событие, наступившее меньше 30 минут назад относительно проверки, продлевает ожидание.
- **REQ-ctl-worker-57** — **Единая проверка доступности подключений.** Функция `chk_any_conn` проверяет доступность подключений типов `Postgres`, `S3` и `KerberosHttp` через единую библиотечную функцию `chk_conn` без дублирования логики проверок. Успешная проверка оставляет заметку, а недоступность формирует заметку и возбуждает исключение. Размер пула изменяется только при флаге `manage_pool` сторожем подключений (успех выставляет фиксированный размер из конфига, сбой обнуляет слоты); в остальных случаях запись в пул запрещена, а чтение слотов не создаёт пул и не изменяет метабазу.
- **REQ-ctl-worker-58** — **Усечение таблицы — одно на объект S3.** Потоковая загрузка объекта S3 в Greenplum с усечением очищает целевую таблицу один раз на объект, а не на каждый файл внутри архива: усечение идёт своей транзакцией, и файл за файлом оно стирает уже загруженное.
- **REQ-ctl-worker-59** — **Неразобранная часть дельты — ошибка, а не тишина.** Разбор временной дельты завершается исключением с текстом неразобранной части и всей дельты, если часть не опознана; молча пропускать её нельзя, так как из дельты считается время следующей попытки, и пропуск даёт неверное время без единого следа. Пустые значения параметров (`hours=`, лишняя запятая) пропускаются, так как применять их не к чему.
- **REQ-ctl-worker-60** — **Снимки CTL — в папке ctl/ бакета логов.** Функции работы со снимками `ctl_obj_save`, `ctl_obj_load` и `ctl_obj_etag` используют префикс `ctl/<ключ>.<ext>` в общем бакете логов через системное подключение логов Airflow (`[logging] remote_log_conn_id`) без собственной настройки S3, с приоритетным чтением данных из Airflow Variable.

|---|---|
| REQ-ctl-worker-01 | Workflow чужого профиля или удалённый: дано в `ctl_workflows` присутствует запись с другим значением `profile` либо с флагом `deleted = true` → действие сборка DAG'ов профиля фабрикой → результат DAG для данной записи не создаётся, остальные DAG'и формируются штатно |

| REQ-ctl-worker-01 | Битые метаданные одного workflow: дано при сборке DAG'а для одного workflow возникает исключение из-за некорректных метаданных → действие разбор файла фабрики DAG'ов → результат исключение логируется, генерация продолжается со следующего workflow, а модуль импортируется без ошибок |

| REQ-ctl-worker-02 | Условие запуска не разобралось: дано при разборе `startCondition` или параметров расписания возникает ошибка → действие построение расписания DAG'а → результат DAG создаётся с параметром `schedule = None` и тегом `AF_error`, а причина ошибки фиксируется в логе |

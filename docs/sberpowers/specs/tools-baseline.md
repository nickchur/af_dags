# Baseline-спека: tools

- Дата: 2026-10-04
- Статус: реализована
- Источник: openspec/specs/tools/spec.md, перевод 2026-10-04; дельта 2026-10-07-test-connections-host-port

## Назначение

Проверка и обслуживание самого контура: аудит и доступность подключений, регрессионный стенд платформенных операторов, надзор за метабазой Airflow и сериализацией DAG'ов, очистка метабазы и бакета логов, ручные проверки Kafka. Каталог отвечает на вопрос «работает ли платформа», а не «правильно ли посчитаны данные», и потому обязан отличать «сломалось» от «не проверялось» — иначе его отчётам перестают верить.

## Требования

- **REQ-tools-01** — **Список подключений собирается один раз и переиспользуется.** DAG проверки доступности первым таском собирает подключения из secret backend и проверяет именно этот список в том же ране; разбор файла не читает список подключений. Собранный список, сгруппированный по типу (имя, хост, порт, схема, описание подключения), сохраняется в Airflow Variable — для выпадающих списков других дагов — и в XCom таска сбора под ключом `connections`, а полной таблицей пишется в лог таска сбора; заметка таска сбора остаётся строкой на тип с именами подключений. Не собранный список даёт ошибку здоровья.
- **REQ-tools-02** — **Каждое подключение проверяется своей задачей.** Проверка доступности проверяет каждое подключение отдельным экземпляром задачи, подписанным группой по типу, именем подключения и адресом `хост:порт`; строка сводки о непрошедшей проверке несёт ту же подпись. Группа, отмеченная своим сохраняемым флагом пропуска, не проверяется. Способ проверки выбирается по типу: чтение бакетов для S3, запрос к базе для Postgres, вызов информационного метода для CTL, версия для ClickHouse, список топиков для Kafka, сессия для Trino, ping для Redis. Сбой одного подключения не влияет на проверку остальных. Задача недоступного подключения падает. Подключения делятся на жизненно важные и вспомогательные; список важных задается шаблонами имён в параметре, сохраняемом в Variable, и по умолчанию включает метабазу, CTL, основной S3 и подключение бакета логов. Недоступное важное подключение даёт ошибку здоровья (ран красный), недоступное вспомогательное — предупреждение (ран зелёный).
- **REQ-tools-03** — **Сводка по трём состояниям.** DAG'и проверки завершаются сводкой со статусами ✅ success, ❌ failed и ☮️ skipped, помещаемой в заметку DAG-run таском `report`: строка на проверку, без таблицы, упавшие — первыми. Сводка строится и тогда, когда часть задач упала. Заметки служебных дагов не содержат markdown-таблиц: заметка ограничена 1000 символами, и таблица вытесняет строки.
- **REQ-tools-04** — **Регрессионный стенд операторов убирает за собой.** Стенд платформенных операторов выполняет полный цикл «подготовка → проверки → уборка» и удаляет созданные таблицы и объекты S3 независимо от исхода проверок. Подготовка идемпотентна: повторный запуск не зависит от мусора, оставшегося от предыдущего.
- **REQ-tools-05** — **Недоступность системы гасит её проверки, а не роняет прогон.** Проверки включаются флагами по системам (Postgres, ClickHouse, S3), а проверки на стыке двух систем — только при обоих включённых флагах. Если система недоступна на этапе подготовки, её флаг гасится, и зависящие проверки уходят в ☮️, а не падают каскадом.
- **REQ-tools-06** — **Тестовые объекты соответствуют требованиям качества.** Таблицы, создаваемые стендом, получают комментарии на таблицу и на каждую колонку, как того требует принятый на контуре Quality Gate. Данные проверок включают граничные случаи: `NULL`, массивы, спецсимволы, разные виды сжатия.
- **REQ-tools-07** — **Сохраняемые параметры вместо выкладки.** DAG'и обслуживания берут значения по умолчанию из своей Airflow Variable, а при её отсутствии — из кода. Запись Variable происходит только при явно выставленном флаге сохранения и только при изменившихся значениях. Расписание является таким же сохраняемым параметром.
- **REQ-tools-08** — **Очистка метабазы защищена от неосторожного запуска.** DAG очистки метабазы поддерживает режим подсчёта без удаления, отвергает срок хранения меньше допустимого минимума и удаляет большие таблицы порциями: по первичному ключу, если индекса по дате у таблицы нет, а целочисленный ключ есть, иначе по диапазону дат. Строки задач, чей ран моложе срока хранения, не удаляются. Вакуум после очистки включается отдельным флагом. Переиндексацию DAG выполняет только по разовой галке ручного запуска и не в режиме подсчёта, каждый индекс отдельной командой; отказ индекса убирает его недостроенную копию и делает задачу красной. Задачи и параметры, которым нужна админская учётка метабазы (вакуум, переиндексация, удаление индексов), не создаются без неё, а при её наличии права владельца проверяются до первой команды.
- **REQ-tools-09** — **Целостность метабазы проверяется каждую ночь.** DAG очистки метабазы проверяет целостность метабазы по каталогу PostgreSQL без блокировок таблиц и является плагином здоровья. Остатки прерванной переиндексации (`*_ccnew`, `*_ccold`) дают `error`; невалидные индексы, дубли индексов, приближение к переполнению счётчика транзакций или последовательностей, отставание автовакуума, долгие транзакции и непроверенные ограничения дают `warn`, а переполнение близко к пределу — `error`. Горизонт вакуума таблиц (возраст xmin у физических слотов реплик и сессий) старше 100 тыс. транзакций даёт `warn`, старше 1 млн — `error`, с именем того, кто его держит. Логические слоты проверяются отдельно — по WAL, который мастер держит для них: больше 5 ГБ или потребитель не подключён — `warn`, больше 20 ГБ — `error`; их `catalog_xmin` держит только вакуум каталога и в горизонт таблиц не входит. Проверка не перестраивает индексы. Удаляет остатки только разовая галка ручного запуска — отдельным таском сразу после сохранения параметров, до чистки, вакуума и перестройки (с остатками каждая запись и вакуум обновляют все лишние индексы), — и только тот остаток, у которого исходный индекс есть и валиден. Удаление идёт одной командой с коротким ожиданием блокировки и повтором, а не по одному индексу с `CONCURRENTLY`.
- **REQ-tools-10** — **Надзор за сессиями метабазы.** Сторож метабазы периодически снимает активность и разбирает находки по трём категориям: зависшие транзакции, долгие запросы и ожидание блокировок, каждая со своим порогом. Находка по возможности сопоставляется с задачей Airflow, которой она принадлежит, и несёт её состояние: саму задачу, её состояние и свежесть хартбита. Владелец считается живым, только если задача выполняется и хартбит не старше порога; порог по умолчанию совпадает с зомби-детектором Airflow. Ответы «владельца не опознали» и «владелец мёртв» различаются в отчёте, а не сливаются в общий пустой список. Находки дают вердикт здоровья, а не падение снятия: параметр `alert` задаёт его уровень — `error` (ран красный) при включённом, `warn` (ран зелёный) при выключенном.
- **REQ-tools-11** — **Убийство сессий не становится настройкой по умолчанию.** Прекращение найденных сессий выполняется только при явном флаге запуска, по умолчанию работает в режиме показа кандидатов и не сохраняется в Variable вместе с остальными параметрами. Кандидатом является только сессия без живого владельца: сессию работающей задачи сторож не прекращает ни при каких настройках, независимо от возраста транзакции.
- **REQ-tools-12** — **Проверка сериализации никогда не роняет прогон.** DAG контроля сериализации ищет DAG'и, чья сериализация переписывается на каждом разборе файла. Сбор и сводка не падают из-за находок: одного замера мало, чтобы отличить дрожание от выкладки, поэтому результат попадает в сводку и в вердикт здоровья. Перепроверка одного DAG'а падает на подтверждённом дрожании — её клетка называет DAG. Подтверждённое дрожание (DAG переписывается и при перепроверке) даёт ошибку здоровья; не отчитавшиеся сравнения — предупреждение. Число изменившихся DAG'ов не влияет на исход прогона: версии записываются всем изменившимся, а сравнение ограничивается потолком за прогон, с остатком числом в сводке.
- **REQ-tools-13** — **Разбор файлов контролируется по времени.** Контроль сериализации измеряет время разбора файлов DAG'ов, отмечает выбросы относительно среднего и отдельно называет файлы, перешагнувшие половину таймаута обработчика.
- **REQ-tools-14** — **Ручные проверки Kafka предупреждают об обходе очереди.** DAG'и ручной проверки Kafka позволяют отправить одно сообщение в топик и посмотреть сообщения из топика, задавая подключение и топик параметрами. Документация DAG'а прямо предупреждает, что отправка идёт мимо очереди тракта: файл не попадает в счётчики лимитов маршрута и не занимает пул отправителя.
- **REQ-tools-15** — **Секретов в репозитории нет.** Скрипт подготовки локального хранилища секретов для стенда берёт логины, пароли и адреса из переменных окружения, а в коде держит заведомо нерабочие заглушки. Файл безопасен для разбора Airflow: вся работа выполняется под условием запуска как программы.
- **REQ-tools-16** — **Расхождение между построенными и сериализованными DAG'ами видно.** Контроль сериализации сверяет DAG'и, полученные разбором файлов, с содержимым `serialized_dag` и показывает по каждому файлу, сколько DAG'ов построено и сколько не доехало до таблицы, с примерами имён. Для пропавших указываются их позиции в порядке построения и признак того, что они занимают хвост файла, а также состояние их строк в таблице `dag` — активность и время последнего разбора рядом с временем разбора самого файла. Сверка не роняет прогон: её собственный сбой записывается в лог и не мешает остальным проверкам.
- **REQ-tools-17** — **Короткая диагностика не ждёт и не занимает слот бесконечно.** Проверки, работающие секунды — надзор за метабазой, отчёты по её журналу, аудит и проверка подключений, — имеют приоритет выше тяжёлых регрессионных прогонов того же пула и ниже агента загрузок: тот двигает боевые загрузки, и обгонять его диагностика не должна. Тем же проверкам задаётся потолок времени на задачу. Потолок заведомо больше их собственных сетевых таймаутов: он ловит зависание, а не медленный ответ. Тяжёлые регрессионные прогоны приоритет не получают: они длинные и несрочные, и обгонять ими что-либо означает удлинять чужое ожидание.
- **REQ-tools-18** — **Сбои доставки задач видны числом.** Каталог проверок периодически считает по журналу метабазы события, которыми планировщик сообщает о проблемах доставки задач: перезапрос застрявшей в очереди задачи, исчерпание перезапросов, потерю хартбита и расхождение состояния с исполнителем. Отчёт показывает число событий за окно, разбивку по дагам и задачам, разбивку по дням и число запусков за то же окно — без него счётчик не читается: одно и то же число на четырёх тысячах запусков и на сорока означает разное. Рядом с числом событий отчёт показывает число различных задач, которых эти события касаются. Задачи считаются различными, если различаются даг, задача, прогон, индекс отображения или номер попытки. Доля от запусков считается по задачам, и порог сравнивается с ними же: о зависшей задаче планировщик пишет не однажды, а на каждом круге проверки, поэтому доля по событиям меряет частоту его опроса, а не здоровье контура, и осмысленного порога у неё нет — одна мёртвая задача перекрывает любое значение, а десяток настоящих смертей воркера не дотягивает. Разбивка по дням считается в тех же единицах, что и сводка, иначе тренд остаётся в тиках, от которых отчёт как раз уходит. Доля считается в попытках с обеих сторон: в знаменателе — запуски попыток за то же окно. Совпадение при этом неполное, и отчёт не выдаёт его за строгое: часть сбоев доставки относится к попыткам, которые так и не стартовали, а значит в знаменатель не попали. Доля читается как оценка порядка, а не как часть целого. Отдельно от них отчёт считает события, которые пишет код тракта, — например пропуск загрузки из-за запаузенного дага. В число сбоев доставки они не входят и порог не трогают: это не поломка инфраструктуры, а решение человека. Но и молчать о них нельзя: из-за такой паузы загрузка стоит, и «сколько раз за сутки» — ответ на «часто ли». Время в снимке московское — и момент сбора, и время последнего события, иначе их нельзя сравнить глазами. Пояс задаёт сам отчёт, и он не зависит от настроек соединения с метабазой: от них же зависит граница суток в разбивке по дням, так что смена настройки на сервере сдвинула бы её молча, оставив цифры правдоподобными. Отчёт только читает журнал и не изменяет его. Превышение порога даёт ошибку здоровья (`health_errors`, ран красный, уведомление); сбои ниже порога — предупреждение; нулевой порог означает «только показывать» — предупреждение без ошибки. Сам сбор и сводка не падают из-за числа сбоев.
- **REQ-tools-19** — **Состояние контура снимается раз в час.** Служебный DAG раз в час снимает то, что объясняет, почему задачи не идут: запись, чтение и удаление в бакете логов задач с замером времени; пулы без свободных слотов, в которых ждут задачи; свежесть разбора файлов и ошибки импорта; раны в `queued`, раны запаузенных и раны деактивированных дагов (с ошибкой импорта файла); задачи, давно ждущие в `scheduled`, с признаком лимита своего дага; свежесть отчётов остальных плагинов здоровья. Компоненты, celery, control-канал, метабазу и задержку доставки снимает пульс раз в 5 минут. Число тасков DAG'ов проверяет ночной DAG проверки DAG'ов, а не часовой. Каждая проверка изолирована: её сбой даёт её собственную строку, а не обрывает остальные. Итог пишется в лог, XCom и заметку. Таск снятия не падает из-за статусов проверок: `error` роняет `health_errors` (ран красный), `warn` даёт зелёный `health_warn` с заметкой. Причины исключений в XCom и заметке не содержат адреса, пользователей и пароли. Файлы DAG'ов проверка не разбирает: полный разбор остаётся ночной проверкой.
- **REQ-tools-20** — **Даги-проверки завершаются вердиктом здоровья.** Даг-проверка с тегом `health` отделяет «проверка сломалась» от «проверка нашла неисправность». Таски сбора и сводки не падают из-за находок: их вердикты (`healthy`, `warn`, `error` с пояснением) передаются дальше, а итог подводится двумя последними тасками дага, которые запускаются при любом исходе предыдущих. Исключение — таск на один проверяемый объект (подключение, перепроверка одного DAG'а): он может падать, чтобы красная клетка называла объект; его находку учитывает сводка, а не правило «упавший таск — ошибка». `health_warn` пропускается, если предупреждений нет, и завершается успешно с заметкой ⚠️ и их списком, если они есть; `health_errors` пропускается, если ошибок нет, и падает с заметкой ❌ и их списком, если они есть: ран при этом красный, уведомление приходит штатно. Проверочный таск, упавший сам, считается ошибкой с его названием и причиной: проверка, которая не выполнилась, не может означать «здорово». Отчёт плагина для `get_system_health` записывается один раз за прогон — из `health_errors`, со всеми вердиктами, включая здоровые, — и указывает навык агента своего дага.
- **REQ-tools-21** — **Разбор очереди каждый час.** Разбор очереди запускается по расписанию каждый час (по умолчанию `10 * * * *`, расписание — сохраняемый параметр) и является плагином здоровья. Его вердикт не бывает выше `warn`: очередь — не авария. Предупреждение выдаётся, когда доля мусора в брокере не ниже порога, когда есть голодающие даги и когда раны закрыты по `dagrun_timeout` без единого старта. Плановый прогон не удаляет сообщения из брокера: удаление остаётся разовой галочкой ручного запуска.
- **REQ-tools-22** — **Пульс контура раз в 5 минут.** Служебный DAG раз в 5 минут проверяет, лежит ли контур: компоненты `/api/v1/health`, celery-воркеров (по отбивкам воркеров, без них — опросом брокера), control-канал celery и брокер, метабазу и задержку доставки своей задачи. Проверки и пороги те же, что у часового снятия. DAG является плагином здоровья со сроком отчёта 15 минут. `dagrun_timeout` меньше интервала, а `max_active_runs` равен 1, чтобы на больном контуре раны не копились в очереди.
- **REQ-tools-23** — **Зависшие раны запаузенных дагов закрываются по возрасту.** Служебный даг находит раны в состояниях `running` и `queued` (выбор — параметр) у дагов на паузе, старше заданного порога. Возраст рана в `queued` считается от постановки в очередь, рана в `running` — от последнего движения его задач. Ран, у которого задача в состоянии `running`, не закрывается. Закрытие выполняется только при явно выставленном параметре `close` и помечает ран `failed`, а незавершённые задачи — `skipped`, как кнопка Mark failed. Пауза дага не снимается.
- **REQ-tools-24** — **Мусор в очереди брокера определяется по задаче, названной в сообщении.** Чистка очереди celery считает сообщение мусорным только тогда, когда задача, которую сообщение называет, отсутствует в метабазе либо находится в терминальном состоянии. Сообщение, чью цель разобрать не удалось, остаётся в очереди. Возраст сообщения признаком не является: в протоколе celery времени постановки нет. Идентификатор задачи celery, записанный у задачи в метабазе, признаком живости не является: у завершившейся задачи он совпадает с идентификатором того самого сообщения, которое и подлежит удалению. Его расхождение с разметкой показывается в отчёте отдельным числом — как мера соответствия модели действительности.
- **REQ-tools-25** — **Ключи брокера сверяются до всякого удаления.** Перед разметкой чистка сверяет длину очереди с числом фактически прочитанных сообщений по каждому ключу и прекращает работу при расхождении, не переходя к удалению. Отчёт называет действующий префикс ключей.
- **REQ-tools-26** — **Удаление из очереди защищено от неосторожного запуска.** Удаление выполняется только при явном флаге запуска, по умолчанию работает в режиме подсчёта и не сохраняется в Variable вместе с остальными параметрами. Чистка отказывается удалять, если доля мусора в очереди ниже заданного порога или его абсолютное число выше заданного предела. Плановый запуск не удаляет: флаг удаления разовый, и расписание у DAG'а разбора возможно только потому, что удалить без человека он не может.
- **REQ-tools-27** — **Чистка отчитывается при любом исходе разбора.** Сводка выдаётся и тогда, когда разметка не отработала, и называет, что именно произошло с ней. Своим падением сводка не сообщает о чужом: два разбора по одной причине скрывают причину. Очередь, которую не получается прочитать целиком, приводит к отказу до чтения — по её длине, а не по исходу чтения. Молчаливое чтение без предела не допускается: тела нужны разметке в памяти, и предел здесь дешевле, чем разбор по OOM.
- **REQ-tools-28** — **Удалённое из очереди можно вернуть.** Перед удалением чистка сохраняет полные тела удаляемых сообщений вместе с ключами их очередей во внешнее хранилище, переживающее перезапуск пода, и называет адрес сохранённого в отчёте. Дамп сохраняется и при подсчёте без удаления.
- **REQ-tools-29** — **Разбор очереди называет причину ожидания.** Разбор очереди для каждой живой задачи в `scheduled` (даг не на паузе, ран в `running`), ждущей дольше порога, называет одну причину в порядке проверки: лимит `max_active_tasks` дага, исчерпанный пул, приоритет (вес ниже медианы задач, ушедших в работу за последний час), прочее. Задачи запаузенных дагов и ранов не в `running` считаются отдельно и в причины не входят. Отчёт содержит вывод словами по каждой найденной картине.
- **REQ-tools-30** — **Разбор не меняет состояния без человека.** Разбор только читает метабазу и брокер. Удаление из брокера выполняется отдельным таском и только по разовому флагу, который не сохраняется с параметрами; плановый запуск поэтому удалить не может.
- **REQ-tools-31** — **Навыки агента из репозитория дагов публикуются в метабазу.** Служебный даг находит файлы навыков `*/skill/*.md` в каталоге дагов, кроме `testbed/` и скрытых каталогов, и публикует каждый в Airflow Variable `mcp_skill__<имя>`, где имя — имя файла без `.md`, а оглавление — в Variable `mcp_skills`. Переменная навыка переписывается только при изменении файла; навык, чей файл исчез, снимается вместе с переменной. Оглавление записывается последним. Два файла с одним именем роняют таск без записи.
- **REQ-tools-32** — **Документация дагов публикуется в метабазу.** Служебный даг публикует `.md`-файлы каталога дагов, кроме навыков агента (`*/skill/*.md`), файла правил агента в репозитории, `CONTEXT.md`, каталогов `openspec/`, `docs/` (спеки и планы), `testbed/` и скрытых, в Airflow Variable `af_doc__<путь с / заменённым на __>`, а оглавление с заголовками — в Variable `af_docs`. Переменная переписывается только при изменении файла; документ, чей файл исчез, снимается. Оглавление записывается последним.
- **REQ-tools-33** — **Бакет логов обслуживается одним сроком.** DAG обслуживания логов берёт бакет из конфигурации логирования Airflow, а не из параметров запуска. Срок хранения один на весь бакет (параметр `days`, по умолчанию 120 дней); своих сроков у папок нет. DAG выставляет правило жизненного цикла на корень бакета и снимает правила на отдельные папки, оставшиеся от прошлых версий: у объекта срабатывает самый короткий срок. На правила DAG не полагается: удаление выполняется обходом, а отчёт показывает, сколько объектов старше срока дожило до обхода. Отказ выставить правило не прерывает прогон. Статистика и уборка выполняются одним обходом по папкам верхнего уровня, папка логов задач — последней. Отчёт содержит по каждой папке объекты, объём, возраст самого старого объекта и число удалённых, и попадает и в заметку, и в XCom.
- **REQ-tools-34** — **Заполнение бакета логов проверяется каждый прогон.** DAG обслуживания логов является плагином здоровья (`health_warn` / `health_errors`, отчёт плагина со сроком 26 ч), а отчётный таск не падает находками. Проверки строятся по итогам того же обхода, без второго: `fill` — занятое всеми бакетами учётки S3 к квоте учётки: `warn` от 80 %, `error` от 95 %. Лимит выдаётся на учётку, и учётка видит только свои бакеты, поэтому занятое является суммой по всем бакетам из `list_buckets`, а не объёмом бакета логов. Квота и объёмы берутся из заголовков хранилища, если оно их отдаёт; иначе квота — параметр `quota_gb`, бакет логов меряется тем же обходом, прочие бакеты листаются только ради суммы и не дольше `max_minutes`. Неполный подсчёт помечается как нижняя оценка. Квота неизвестна — проверки `fill` нет, и чужие бакеты не листаются; `ttl` — доля объектов старше срока среди осмотренных: `warn` больше 10 %, `error` больше 50 %; `sweep` — обход не закончен за `max_minutes`: `warn`. Обход пишет строку на папку и на бакет учётки в заметку сверху по мере обхода, отчёт — строку на проверку над таблицей по папкам.
- **REQ-tools-35** — **Заполнение учётки S3 с дагами проверяется каждую ночь.** Проверка DAG'ов отдельным таском считает заполнение учётки S3 подключения `s3`, из которой ядро синхронизирует DAG'и, к её квоте по тем же правилам, что `fill` у бакета логов: сумма по всем бакетам учётки, квота из заголовков хранилища или параметра `quota_gb` (сохраняемого), `warn` от 80 %, `error` от 95 %. Квота неизвестна — таск пропускается, не листая бакеты. Находкой таск не падает: вердикт уходит в `health_warn` / `health_errors`.
- **REQ-tools-36** — **Живое не уходит по сроку бакета.** Последнюю версию снимка неизменившегося DAG'а, записанную раньше 7 дней назад, `tools_test_dags` переписывает на месте, без новой версии. Документ дагов `tools_mcp_skills` переписывает в `docs/<путь>` бакета логов при смене файла и когда его запись в оглавлении старше 7 дней.
- **REQ-tools-37** — **Результаты celery без даты завершения тоже вычищаются.** Очистка `celery_taskmeta` удаляет и строки, у которых даты завершения нет вовсе: возраст такой строки определяется по её возрастающему первичному ключу, а граница — как минимум ключа среди строк, ещё не вышедших за срок хранения. Строка работающей задачи остаётся нетронутой. Когда таких строк нет вовсе, не удаляется ничего.
- **REQ-tools-38** — **Размер сета привязок ответных очередей виден.** Пульс контура в проверке control-канала показывает число записей в сете привязок ответных очередей control-канала celery и даёт предупреждение от тысячи записей с советом очистки. Ошибка чтения сета не роняет проверку: поле показывает причину.
- **REQ-tools-39** — **Разбор очереди показывает и по запросу чистит сет привязок ответов.** `tools_queue_analyze` показывает размер сета привязок ответных очередей и несколько записей для примера независимо от того, пуста ли очередь задач. От порога `max_reply_bindings` выдаётся вывод и предупреждение плагина здоровья (не выше `warn`). Удаление сета выполняется только по разовой галочке `purge_pidbox`, которая не сохраняется в Variable; плановый прогон сет не удаляет.
- **REQ-tools-40** — **Пульс показывает приросты счётчиков брокера.** Пульс считает прирост вытесненных ключей брокера и размера сета привязок ответных очередей от своего прошлого отчёта и даёт предупреждение, когда брокер вытесняет ключи. Если узел брокера другой или перезапускался за интервал, прирост не считается. Ошибка чтения прошлого отчёта не роняет проверку.
- **REQ-tools-41** — **Пульс видит задачи, застрявшие между шедулером и воркером.** Пульс показывает возраст самой старой задачи в `queued` и число задач в `queued` дольше `task_queued_timeout`, а также ёмкость исполнителя шедулера (`parallelism` × живые шедулеры против `queued` + `running`). Предупреждение выдаётся, когда есть задачи старше `task_queued_timeout`, и когда исполнитель заполнен при свободных слотах воркеров.
- **REQ-tools-42** — **Адрес подключения определяется одним правилом и виден везде одинаково.** У каждого подключения проверки доступности есть адрес — хост и порт. Хост заполнен в подключении — адрес берётся из хоста и порта подключения как есть. Хост пуст — адрес берётся из первого непустого параметра extra по порядку `endpoint_url`, `bootstrap.servers`. Значение без запятой раскладывается на хост и порт (вид `схема://хост:порт` или `хост:порт`); порта в значении нет — порт пуст. Значение с запятой даёт хосты без портов через запятую и порт первого из них. Адреса нет нигде — хост и порт пусты. Непригодный адрес из extra даёт пустой адрес и предупреждение в логе таска сбора, а не падение сбора. Один и тот же адрес показывается в подписи задачи проверки, в строке сводки, в логе сбора списка, в XCom и в Variable.

## Ограничения и контракты

- Сохранение сгруппированного по типу списка подключений в Airflow Variable (REQ-tools-01).
- Подключение к ClickHouse с `conn_type = sqlite` в secret backend отображается как ClickHouse в отчёте и Variable (REQ-tools-01).
- XCom `connections` таска сбора и Variable `local_connections` — один словарь `{тип: [{conn_id, host, port, schema, description}]}`, ClickHouse под типом `clickhouse`, отсутствующее описание — `No description`; основной XCom таска сбора — список проверок для раскрытия задач проверки (REQ-tools-01).
- Variable `local_connections` читают ручная проверка Kafka и выпадающий список ТФС — только имена подключений (REQ-tools-01).
- Подпись экземпляра проверки не длиннее 250 символов, длиннее — обрезается с «…» (REQ-tools-02).
- Ключи extra, где ищется адрес, по приоритету: `endpoint_url`, `bootstrap.servers`; разбор `хост1,хост2` + порт первого повторяет формат, который secret backend строит для Postgres с несколькими хостами (REQ-tools-42).
- Непригодный адрес из extra: extra не объект; значение ключа не строка; не разбирается как адрес; порт любого хоста не число или вне 1–65535; хотя бы один хост пуст. Пустая строка и `null` в ключе — отсутствие значения, берётся следующий ключ. Предупреждение одно на подключение: имя подключения, ключ extra и постоянный текст причины, само значение в лог не пишется (REQ-tools-42).
- В адрес, лог, XCom и Variable не попадают логин, пароль и прочие параметры extra — только хост и порт (REQ-tools-42).
- Способы проверки доступности по типам: чтение бакетов для S3, запрос к базе для Postgres, информационный метод для CTL, версия для ClickHouse, список топиков для Kafka, сессия для Trino, ping для Redis (REQ-tools-02).
- Шаблоны имён жизненно важных подключений по умолчанию: метабаза, CTL, основной S3, подключение бакета логов (REQ-tools-02).
- Статусы сводки проверок: ✅ success, ❌ failed, ☮️ skipped с выводом упавших первыми (REQ-tools-03).
- Лимит длины заметки DAG-run в 1000 символов и запрет markdown-таблиц в заметках служебных дагов (REQ-tools-03).
- Требование Quality Gate: наличие комментариев на таблицу и на каждую колонку для всех создаваемых тестовых таблиц (REQ-tools-06).
- Граничные случаи тестовых данных: `NULL`, массивы, спецсимволы, различные виды сжатия (REQ-tools-06).
- Сохранение параметров и расписания в Airflow Variable только при явном флаге сохранения и изменившихся значениях (REQ-tools-07).
- Минимальный допустимый срок хранения при очистке метабазы: 30 дней (REQ-tools-08).
- Порционная очистка больших таблиц: по первичному ключу при наличии целочисленного `id` без индекса по дате, иначе по диапазону дат (REQ-tools-08).
- Запрет удаления строк задач, чей ран моложе срока хранения (REQ-tools-08).
- Разовая галка ручного запуска для переиндексации метабазы: берётся из кода, а не из переменной, не в режиме подсчёта (REQ-tools-08).
- Обязательная проверка прав владельца схемы `main` для админской учётки метабазы до выполнения команд (REQ-tools-08).
- Проверка целостности метабазы без блокировок таблиц: остатки прерванной переиндексации (`*_ccnew`, `*_ccold`) дают `error` (REQ-tools-09).
- Пороги целостности метабазы: невалидные индексы, дубли, отставание автовакуума, долгие транзакции и непроверенные ограничения — `warn` (REQ-tools-09).
- Пороги горизонта вакуума таблиц (xmin физических слотов и сессий): старше 100 тыс. транзакций — `warn`, старше 1 млн — `error` (REQ-tools-09).
- Пороги логических слотов по WAL: больше 5 ГБ или отсутствие потребителя — `warn`, больше 20 ГБ — `error`; исключение `catalog_xmin` из горизонта таблиц (REQ-tools-09).
- Удаление остатков переиндексации только по разовой галке `drop_leftovers` отдельным таском до чистки, вакуума и перестройки, и только при наличии валидного исходного индекса (REQ-tools-09).
- Порог времени жизни хартбита задачи по умолчанию совпадает с зомби-детектором Airflow (REQ-tools-10).
- Уровень вердикта сторожа сессий метабазы: параметр `alert` задаёт `error` при включении и `warn` при выключении (REQ-tools-10).
- Прекращение сессий метабазы: только при явном флаге, режим показа кандидатов по умолчанию, запрет сохранения флага в Variable, запрет прекращения сессий работающих задач (REQ-tools-11).
- Потолок числа сравниваемых DAG'ов за один прогон контроля сериализации с фиксацией версий всем изменившимся (REQ-tools-12).
- Исключение самопереписывающихся DAG'ов нагрузки из контроля сериализации по префиксу идентификатора (REQ-tools-12).
- Порог времени разбора файла DAG'а: фиксация превышения половины таймаута обработчика (REQ-tools-13).
- Предупреждение в документации DAG'ов ручной проверки Kafka об отправке сообщений в обход очереди тракта и лимитов маршрута (REQ-tools-14).
- Запрет секретов в коде репозитория: параметры подключения только из переменных окружения, нерабочие заглушки в коде (REQ-tools-15).
- Приоритет коротких диагностических проверок в пуле: выше тяжёлых регрессионных прогонов и ниже агента загрузок (REQ-tools-17).
- Потолок времени выполнения задач диагностики с контролем зависаний (REQ-tools-17).
- Учёт сбоев доставки задач: число событий, число уникальных задач (`dag_id`, `task_id`, `run_id`, `map_index`, `try_number`), доля от запусков попыток за окно (REQ-tools-18).
- Единый московский часовой пояс для всех меток времени в отчёте сбоев доставки независимо от настроек сессии метабазы (REQ-tools-18).
- Изоляция событий кода тракта (пауза загрузки): отдельный счётчик без влияния на порог сбоев доставки (REQ-tools-18).
- Нулевой порог сбоев доставки означает режим «только показывать» (предупреждение без ошибки) (REQ-tools-18).
- Периодичность часового снятия контура: 1 раз в час (REQ-tools-19).
- Запрет вывода адресов, учётных записей и паролей в текстах исключений в XCom и заметках (REQ-tools-19).
- Завершение проверок с тегом `health`: таск `health_warn` пропускается при отсутствии предупреждений и успешен при их наличии; таск `health_errors` пропускается при отсутствии ошибок и падает при наличии ошибок (REQ-tools-20).
- Запись отчёта плагина для `get_system_health` один раз за прогон из таска `health_errors` с указанием навыка агента (REQ-tools-20).

## Non-goals

- Результат задачи проверки подключения (её XCom) адреса не несёт: адрес есть в XCom `connections` таска сбора (REQ-tools-01, REQ-tools-42).
- Таблица адресов в заметке таска сбора не показывается: заметка ограничена 1000 символами (REQ-tools-01).
- Адрес не проверяется и не нормализуется — только показывается (REQ-tools-42).
- Ключи extra, кроме `endpoint_url` и `bootstrap.servers`, адресом не считаются (REQ-tools-42).

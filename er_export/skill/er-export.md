# Выгрузки ЕР на сигме

*2026-09-26 10:37 MSK · v1.4 · Nick Churkin · [NSChurkin@sber.ru](mailto:NSChurkin@sber.ru)*

Навык для агента GigaCode с MCP-сервером Airflow сигмы (`af-sigma-*`). Дополняет навык
`airflow-health`: тот видит Airflow целиком, этот объясняет, что стоит за дагами `export_er*`.
Отправку файлов в ТФС и квитанции ведёт общий тракт — для него навык **`tfs-kafka`**
(`airflow://skill/tfs-kafka`). Источник правды — каталог `er_export/` репозитория `af_dags`
(`README.md`); при расхождении прав код.

У тебя только чтение через MCP. В ClickHouse и S3 ты не ходишь — там говоришь, **что
проверить человеку** (раздел 9).

Настройки выгрузок читай MCP-инструментом `get_variable_value(key, item)`: `datalab_er_wfs` —
группы и таблицы, из которых собраны даги (`item="export_er__<реплика>__<группа>"`),
`datalab_er_wf_meta` — список для формы `export_er_setup`, `datalab_er_config` — общие
настройки, `datalab_er_wf_hash` — когда и с чем прошла последняя синхронизация. Это копия
таблицы `export.er_wf_meta` на момент синка, а не сама таблица.

## 0. Когда этот навык

- Даги `export_er__<реплика>__<группа>` (пакеты) и `export_er_setup` (настройка) — сюда.
- Красный `wait_confirm` пакета — начни здесь, продолжи навыком `tfs-kafka`: ожидание
  квитанции — последний шаг пакета, но причина почти всегда в тракте.
- Общий вопрос «что с сигмой» — сначала `get_system_health` по навыку `airflow-health`.
- Альфа: дагов ЕР там нет; контуры независимы (навык `airflow-health`, раздел 0): ключи и
  объекты бакета ищи только сервером своего контура, а нет инструмента — пакет на контуре
  старее, сервером другого контура его не подменяй.

## 1. Устройство за минуту

```
export.er_wf_meta (ClickHouse) ──export_er_setup: sync──► Variable datalab_er_wfs ──► даги export_er__*

export_er__<реплика>__<группа>:
            ┌─ <db>__<tbl>: init → [build_meta, export_to_s3] → pack_zip ─┐
  make_ts ──┤                                                             ├─► make_summary → wait_confirm → save_status → schedule_next
            └─ <db>__<tbl>: init → [build_meta, export_to_s3] → pack_zip ─┘         │
                                                                         очередь отправки → тракт tfs_kafka → ТФС
```

- **Один даг = одна группа = один пакет = один тикет ЕР.** Группа — пара колонок `replica` +
  `dag_group` в `export.er_wf_meta`. Внутри — TaskGroup на каждую поставку (таблицу).
- **Пакет уходит целиком.** `make_summary` с `trigger_rule=none_failed`: упала одна таблица —
  тикета нет у всего пакета. Неполный тикет — расхождение данных у получателя.
- **Сам даг ничего не отправляет.** `make_summary` кладёт тикет и архивы в очередь отправки с
  `RqUID` на файл, везёт их `tfs_kafka_snd`, квитанции собирает `tfs_kafka_rcv`.
- **Режимы поставки:** дельта (окно из `export.er_extract_history`, шаг `increment`, по
  умолчанию 60 мин), recent (скользящее окно), `full_export` (без окна), разовая выгрузка за
  период (`date_from`/`date_to` в форме запуска — состояние не двигает).
- **Пулы:** `datalab_export_er` (все таски выгрузки, 20 слотов) и
  `datalab_export_er_ts__<реплика>` — **один слот** на базовую реплику, его берёт только
  `make_ts`, чтобы группы одной реплики получали разные секунды метки.
- **Лимит строк:** на `DEV`, `IFT`, `QA`, `UAT` — 100 строк на поставку, на `PROM` — без
  ограничений (`ENV_STAND`).
- **Ретраи:** до трёх повторов через 5 минут у каждой задачи; `config_error` не повторяется.

## 2. Что смотреть в ране

`diagnose_dag_run(dag_id, dag_run_id)` отдаёт ран с `conf` и `note` и задачи с их `note`.
Заметки — главный источник; XCom тебе недоступен.

| Задача | Что делает | Заметка |
|---|---|---|
| `make_ts` | метка времени пакета | `🕐 метка времени пакета: <YYYYMMDDHHMISS>` |
| `<tg>.init` | окно дельты поставки | `⚙️ Delta State · <схема>.<таблица>`: `time_from`, `time_to`, `is_current`, `increment`, `отставание`, `циклов до текущего времени`; `⏭️ …` — поставка пропущена |
| `<tg>.build_meta` | `.meta` и сверка колонок с `fields` | `🗂️ build_meta · <таблица>` — список колонок |
| `<tg>.export_to_s3` | выгрузка ClickHouse → S3 | — (лог) |
| `<tg>.pack_zip` | архивы | `📦 pack_zip · <таблица>` с `rows=… files=…`; «пусто, send_empty=0 — архив не создан» |
| `make_summary` | тикет, постановка в очередь | `🧾 <тикет>.tkt` — архивы, «в очереди: N»; «пакет пуст — тикет не создан» |
| `wait_confirm` | ждёт квитанции по своим `RqUID` | `📨 TFS confirm`: `✅ Квитанции получены` / `❌ Квитанции с ошибкой` (`StatusCode`, описание) / `⏸️ Отправка на паузе` |
| `save_status` | одна вставка состояния на пакет | `💾 save_status` — окна и строки по таблицам; `📅 разовая выгрузка за период — состояние не сохранено` |
| `schedule_next` | автозапуск следующего цикла | `⏭️ next run scheduled at … UTC`, «отстают: …» / `✅ delta is current` |

Порядок разбора: заметка упавшей задачи → её лог `get_task_logs(dag_id, dag_run_id,
task_id, try_number)` — у задач в TaskGroup `task_id` составной: `<db>__<tbl>.export_to_s3` →
первая ошибка дословно. Бюджет — как в `airflow-health` 6.1.

## 3. Как найти пакет

| Что знаешь | Как найти |
|---|---|
| реплику и группу | даг `export_er__<реплика>__<группа>`; пустая группа — `0` |
| имя архива `<реплика>__<ts>__<группа>__<таблица>__…zip` | тот же даг; ран — по метке `<ts>` в заметке `make_ts` |
| имя тикета `<реплика>__<ts>.tkt` | группы в нём нет: даги `export_er__<реплика>__*`, ран с этой меткой |
| только таблицу | теги дага содержат реплику и схемы поставок; `explore_dag` показывает поставки в описании |

Описание дага (`doc_md`) содержит групповые параметры пакета и по строке на поставку: формат,
стратегия, число колонок.

## 4. Заглушка `BROKEN`

Ошибка в метаданных группы ломает **весь пакет**: вместо рабочего дага с тем же `dag_id`
появляется заглушка — тег `BROKEN`, `❌` в описании, одна задача `config_error`, которая по
расписанию группы падает с перечнем причин в заметке `❌ Пакет <реплика> сломан (N)`.

Частые причины (из `export_er_setup`, таск `sync`): нет строки-дефолта группы; нет или битый
`schedule` в её `params`; пустой `sql_from` или `schema_name` у поставки; `__` или запрещённые
символы в `replica`, `dag_group`, `schema_name`, `extract_name`; реплики нет в `TFS_MAP`;
`fields` пуст или со `*`; неизвестный `format`; одна поставка активна в двух группах реплики.
Лечится правкой записи через `export_er_setup` — это делает человек.

## 5. Разбор по симптому

| Симптом | Куда смотреть | Частая причина |
|---|---|---|
| новый пакет не ходит | пауза дага | **новые пакеты создаются на паузе**; `is_paused=1` у группы синк держит на паузе |
| `make_ts` висит в `queued` | `get_pool("datalab_export_er_ts__<реплика>")` | пула нет — его заводит синк; после пересоздания метабазы нужен прогон `export_er_setup` с «Синхронизировать принудительно». Ошибки при этом нет — молча стоит |
| задачи ждут в `scheduled` | `get_pool("datalab_export_er")`; `get_system_health` → `platform.scheduled` | пул выгрузок занят другими пакетами; пул свободен — шедулер отдаёт задачи по убыванию `priority_weight`, и чужие даги с большим весом забивают очередь (навык `airflow-health`). С 23.09.2026 у выгрузок вес 950 (`weight_rule: absolute`) |
| `config_error` | заметка задачи | раздел 4 |
| `init` failed | заметка, лог | нет коннекта `dlab-click` / `s3-tfs-hrplt` или бакета; сняты флаги всех таблиц; `date_from`/`date_to` заданы не парой или не по формату |
| `build_meta` failed | лог | колонки запроса разошлись с `fields`; квалификатор таблицы в имени колонки (в ошибке — готовая строка замены); описание в `descriptions` для несуществующей колонки |
| `export_to_s3` failed | лог | ошибка SQL в ClickHouse; таймаут `export_timeout` (по умолчанию 120 мин) |
| `wait_confirm` failed «ТФС отверг файлы» | заметка `❌ Квитанции с ошибкой` | отказ ТФС по файлу — коды в навыке `tfs-kafka` |
| `wait_confirm` failed «не пришли за N мин» | текст ошибки; `auto_confirm` в `conf` рана | «Ещё не отправлены (очередь стоит)» — тракт не везёт, `tfs_kafka_snd`; «Отправлены, ответа нет» — молчит ТФС или приёмник, `tfs_kafka_rcv`. Дальше — навык `tfs-kafka` |
| `wait_confirm` ☮️ | заметка / причина скипа | `auto_confirm=1` (по умолчанию), `notify_kafka=0`, пакет пуст, **пауза отправки** |
| дельта не двигается | заметки `init`, `save_status` | разовая выгрузка за период; снятый флаг таблицы (`⏭️`); `full_export`; поставка на паузе (`is_paused`) |
| окно дельты в 1970 году: `init` — `time_from 1970-01-01…`, отставание десятки тысяч дней, «циклов до текущего времени» — сотни тысяч; `pack_zip` `rows=0` | `init`, параметры поставки (`lower_bound`) | новая поставка без начальной точки: при первом запуске `time_from = lower_bound`, а `lower_bound` пуст → `1970-01-01`. С `increment=60` пакет годами выгружает пустые часы 1970-го и не догонит никогда. Это не «экспорт прошёл нормально». Лечится `lower_bound` в `er_wf_meta` (синк `export_er_setup`) или разовой выгрузкой за период, не ожиданием. Сигма 24.09.2026: `learning.lc_items_opened` |
| пакет «догоняет» бесконечно | `init`: «циклов до текущего времени» | окно шагает на `increment` за ран; отставание в неделю — сотни циклов. Лечится разовой выгрузкой за период или временно большим `increment`, не ожиданием |
| на стенде 100 строк | — | лимит стенда, раздел 1 |

## 6. Норма, а не тревога

- `wait_confirm` ☮️ при `auto_confirm=1` — это умолчание. Поэтому падение `wait_confirm` бывает
  только у ранов с `auto_confirm=0` (обычно ручных): по одному такому падению не делай вывод
  «все пакеты падают» — у прочих подтверждения просто нет; при паузе отправки ☮️ задуман:
  дельта сдвигается, `save_status` пишет `confirmed = null`, пакет уедет после снятия паузы.
- `schedule_next` с `✅ delta is current` — следующего цикла нет, пакет идёт по расписанию.
  У `full_export` и recent автозапуска не бывает.
- Ран, запущенный `schedule_next` (не по расписанию), — штатный цикл догоняющей дельты.
- `sync` в `export_er_setup` ☮️ — контрольная сумма не изменилась, синхронизировать нечего.
- `make_ts` держит слот пула на секунду дольше работы — так разводятся метки групп.

## 7. Чего не советовать

- **Не `clear` всего рана.** Перезапустится `make_ts`: пакет поедет с новой меткой, архивы
  прошлой попытки останутся в S3 сиротами. Метка живёт в XCom `make_ts`, поэтому `clear`
  упавших задач одной таблицы (с downstream: `make_summary` и дальше) имена файлов не меняет.
  Перелить одну таблицу новым раном — запуск с одним отмеченным флагом `tbl_<db>__<table>`;
  у пропущенных таблиц дельта остаётся на месте.
- **Не править `export.er_wf_meta` мимо `export_er_setup`**: форма проверяет запрос на живом
  ClickHouse и синхронизирует Variable; прямая правка всплывёт ночью заглушкой.
- **Не задавать `export_path` при включённом `notify_kafka`**: уведомление уйдёт, дельта
  сдвинется, а ТФС пакет в чужом месте не подтвердит.
- **Не снимать паузу пакета** «чтобы поехал» — новый пакет стоит на паузе намеренно, включает
  его владелец.
- Не называть причину без заметки или лога.

## 8. Настройка: `export_er_setup`

Только ручной запуск. Поле «Поток» — ключ записи `реплика/группа/схема/выгрузка` или новая
запись, «Патч» — JSON только изменяемых полей. Задачи: `prepare` → `check` (запрос с
`LIMIT 0` на живом ClickHouse, сверка `.meta`) → `apply` → `sync`; параллельно `config` —
общие настройки (Variable `datalab_er_config`). Не прошла проверка — в таблицу ничего не
записано; галка «Записать несмотря на проверку» превращает ошибки в предупреждения.
Правка общих настроек применяется со следующего разбора файла (~30 с).

## 9. Что проверить человеку

Эти места агенту недоступны — назови их:

- **ClickHouse**: запись поставки в `export.er_wf_meta` (читать с `FINAL`); состояние дельты
  `export.er_extract_current_vw`; судьба пакета — `export.er_sent_files` с `export.tfs_receipts`
  по `rq_uid` (запрос «Судьба одного пакета» в `er_export/README.md`).
- **S3**: лежат ли архивы и тикет пакета в бакете маршрута.
- **Форма `export_er_setup`** с пустым патчем — просмотр записи и проверка запроса.
- Ошибка в SQL поставки или в данных источника — владелец поставки, не платформа.

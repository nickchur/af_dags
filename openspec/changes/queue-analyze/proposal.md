# Разбор очереди: почему задачи ждут — вместо одной чистки брокера

## Why

23–24.09.2026 на сигме в `scheduled` набралось 297 задач. Первая версия причины — «текут
слоты executor'а» — оказалась неверной: лог шедулера показал `slot_reconciler gap=0` и
1874 отказа «>= max_active_tasks limit» у дагов `raw_to_stable_*`. Там же `tfs_kafka_snd` с
весом 1 проигрывал дагам с весом 22–1921 (`weight_rule=downstream`) и закрывался по
`dagrun_timeout` без единой запущенной задачи. Всё это выяснялось руками по логам и ответам
health. `tools_queue_cleanup` смотрел только брокер — и на этот случай ответа не давал.

## What Changes

- `tools_queue_cleanup` → `tools_queue_analyze` (`tools/queue_analyze.py`).
- Новые таски `scheduler` и `capacity`: причина ожидания каждой давно ждущей задачи (лимит
  дага, пул, приоритет, прочее), раны, закрытые без старта, раны запаузенных дагов;
  `queued`+`running` против `parallelism` × живые шедулеры, слоты воркеров из отбивок.
- `report` — **выводы словами** по правилам из разбора.
- Разметка и чистка брокера переносятся без изменений; удаление — один таск по разовой
  галочке `purge`.
- Параметры — общий механизм `saved_params` (Variable `tools_queue_analyze_params`, пороги
  прежней `tools_queue_cleanup_cfg` — значениями по умолчанию). Расписание — параметр,
  по умолчанию пусто.

## Impact

- После выкладки `tools_queue_cleanup` пропадает из UI; его раны и переменную удалять не нужно.
- Дампы — в прежней папке `queue_cleanup/` бакета логов.

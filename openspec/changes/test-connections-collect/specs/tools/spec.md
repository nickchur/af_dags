## MODIFIED Requirements

### Requirement: Список подключений собирается один раз и переиспользуется

DAG проверки доступности SHALL первым таском собирать подключения из secret backend и
проверять именно этот список в том же ране; разбор файла MUST NOT читать список подключений.
Собранный список SHALL сохраняться в Airflow Variable, сгруппированным по типу, — для
выпадающих списков других дагов. Не собранный список SHALL давать ошибку здоровья.

#### Scenario: Новое подключение появилось в secret backend

- **WHEN** подключение добавлено перед прогоном проверки
- **THEN** его проверяет этот же прогон, отдельного аудита и перечитывания файла не нужно

#### Scenario: Подключение удалено

- **WHEN** подключение убрано из secret backend
- **THEN** прогон его не проверяет и не падает из-за него

#### Scenario: Список не собран

- **WHEN** secret backend не отдал подключения
- **THEN** проверок нет, `health_errors` красный, ран красный

#### Scenario: ClickHouse под чужим типом

- **WHEN** подключение к ClickHouse заведено с `conn_type = sqlite`, как того требует
  secret backend
- **THEN** в отчёте и в Variable оно показано как ClickHouse, а не как SQLite

### Requirement: Каждое подключение проверяется своей задачей

Проверка доступности SHALL проверять каждое подключение отдельным экземпляром задачи,
подписанным группой по типу и именем подключения. Группа, отмеченная своим сохраняемым
флагом пропуска, SHALL NOT проверяться. Способ проверки SHALL выбираться по типу: чтение бакетов для S3, запрос к базе
для Postgres, вызов информационного метода для CTL, версия для ClickHouse, список топиков для
Kafka, сессия для Trino, ping для Redis. Сбой одного подключения MUST NOT влиять на проверку
остальных.

Задача недоступного подключения SHALL падать. Подключения SHALL делиться на жизненно важные
и вспомогательные; список важных SHALL задаваться шаблонами имён в параметре, сохраняемом в
Variable, и по умолчанию SHALL включать метабазу, CTL, основной S3 и подключение бакета
логов. Недоступное важное подключение SHALL давать ошибку здоровья (ран красный),
недоступное вспомогательное — предупреждение (ран зелёный).

#### Scenario: Группа в списке пропуска

- **WHEN** у группы включён флаг пропуска
- **THEN** экземпляры её подключений ☮️, это не ошибка и не предупреждение, ран зелёный

#### Scenario: Тип, для которого проверки нет

- **WHEN** подключение имеет тип вне списка поддерживаемых
- **THEN** задача помечается ☮️ как непроверяемая, а не считается упавшей

#### Scenario: Провайдер не установлен

- **WHEN** для проверки нужен провайдер, отсутствующий на контуре
- **THEN** результат — ☮️ с указанием, чего не хватает: это состояние окружения, а не
  недоступность подключения

#### Scenario: Хост не резолвится

- **WHEN** имя хоста подключения не разрешается в адрес
- **THEN** результат — ☮️ с текстом ошибки: проверять нечего, подключение указывает в никуда

#### Scenario: Упало важное подключение

- **WHEN** недоступно подключение из списка важных
- **THEN** его задача красная, `health_errors` красный с его именем, ран красный

#### Scenario: Упало вспомогательное подключение

- **WHEN** недоступно подключение не из списка важных
- **THEN** его задача красная, `health_warn` зелёный с его именем, `health_errors`
  пропущен, ран зелёный, в Health — предупреждение

# Служебные даги (`tools/`): проверка и обслуживание
*2026-10-01 18:00 MSK · v1.68 · Nick Churkin · [NSChurkin@sber.ru](mailto:NSChurkin@sber.ru)*

> До 24.09.2026 каталог назывался `check/`. На сигме он всегда был `tools/` (`CI06932748/tools/…`),
> теперь и в репозитории так же. S3-инструменты альфы переехали в [`s3_tools/`](../s3_tools/readme.md).

Данная директория содержит инструменты и DAG'и для верификации работоспособности кастомных операторов и системных компонентов платформы.

**Навыки агента** — индекс [`skill/tools.md`](skill/tools.md) (какой даг на какой вопрос,
общее устройство) и навыки дагов: [`tools-system-health`](skill/tools-system-health.md),
[`tools-pg-activity`](skill/tools-pg-activity.md), [`tools-log-events`](skill/tools-log-events.md),
[`tools-test-connections`](skill/tools-test-connections.md), [`tools-test-dags`](skill/tools-test-dags.md),
[`tools-queue-analyze`](skill/tools-queue-analyze.md), [`tools-paused-runs`](skill/tools-paused-runs.md).
На MCP — `airflow://skill/<имя>` (публикует `tools_mcp_skills`). Поле `skill` в отчёте плагина
здоровья называет навык своего дага. При правке дага, его параметров или расписания по
умолчанию навык правится в том же коммите.

## Этапы и итог

Имена тасков одинаковы у всех дагов: `params` → `collect` → действие (`clean`, `close`,
`purge`, `terminate`, `sweep`, `layout`, `publish`, `save`) → `report` → у плагинов здоровья
`health_warn` / `health_errors`. `params` — через общий
`store_params_task` у всех дагов с расписанием; без него — `dummy` (нечего сохранять), ручные
`test_kafka_*` и `@once` `test_hrp_operators`: сохранять им нечего.

**Даг-проверка находками не падает.** Сбор и сводка кладут вердикты в XCom `health`
(`push_health`), итог подводят два последних таска из `health_tasks` (`plugins/utils.py`),
оба `ALL_DONE`:
*   `health_warn` — есть `warn`: ✅ с ⚠️ в заметке; нет — ☮️;
*   `health_errors` — пишет отчёт плагина (`report_health`, единственное место записи); есть
    `error`: ❌, ран красный, уведомление через `on_callback`; нет — ☮️.

Отчёт плагина и файлы разборов в бакете (`*_analyze.json`, дамп мусора брокера, снимки
`pg_activity`) несут `platform` (`alpha` / `sigma`, `env_platform()`) и `stand`: файл, отданный на
разбор, не спутать с файлом другого контура (`ENV_SPACE` на альфе тоже `sigma`).

Красный таск сбора или сводки — сломалась сама проверка: `health_errors` назовёт его «не
выполнился». Исключение — таск на один объект (подключение в `test_connections`, перепроверка
DAG'а в `test_dags`): красный, чтобы клетка называла объект; вердикт по нему считает сводка.

| Тег | Что значит | Даги |
|---|---|---|
| `health` | **плагин здоровья — контракт с core**: `get_system_health` ждёт от каждого активного дага с этим тегом отчёт `system_health/checks/<dag_id>.json`, иначе пишет «плагин X: нет отчёта», а просроченный по `ttl_sec` — «последний отчёт N назад». | `AutoQA` | регрессия и проверка «работает ли» | `dummy` (раз в час), `test_connections`, `test_dags`, `test_hrp_operators`, `test_kafka_*` |

Тег-роль один на даг (плюс `AutoQA`); предметные теги (`conn`, `dag`, `mcp`, `operators`,
`kafka`, `dummy`, `check`) сняты 28.09.2026 — отбирать по ним нечего.

Вердикты плагинов: `system_health` — по проверкам; `pg_activity` — находки `error` при `alert`,
иначе `warn`; `log_events` — сбои `warn`, выше порога `alert_after` — `error`;
`test_connections` — упало важное (`critical`) — `error`, вспомогательное — `warn`;
`test_dags` — дрожащая сериализация `error`, немые сравнения `warn`; `queue_analyze` — не выше

`log_cleanup` — заполнение учётки S3 (все её бакеты) к квоте, объекты старше срока, неполный обход.

## Состав

### [test_connections.py](test_connections.py)
**Мониторинг и проверка всех Airflow Connections.**

DAG автоматически обнаруживает все подключения и проверяет их доступность.
*   **Список в том же ране**: первый таск `collect` снимает подключения из secret backend
    (заметка — таблица по типам) и пишет Variable `local_connections` — из неё строят выпадающие
    списки kafka-подключений `test_kafka` и `ctl_tfs`. Разбор файла Variable не читает. До
    29.09.2026 список снимал отдельный даг `show_connections`.
*   **Один mapped-таск `check`** по списку рана, экземпляр на подключение подписан «группа ·
    `conn_id`» (`tfs`, `postgres`, `s3`, `ctl`, `clickhouse`, `kafka`, `trino`, `redis`,
    `other`). Упал `collect` — ❌ `health_errors`.
*   **`skip_<группа>`** (`skip_tfs`, `skip_kafka`, …; секция формы «Пропуск групп») —
    подключения группы не проверяются (☮️, не ошибка); сохраняются с `save_params`.
*   **Стандартизация**: Статус пропущенных проверок помечается символом `☮️`.
*   **Отчетность**: таск `report` — сводная таблица ✅/❌/☮️ (⭐ — важное) в заметке рана.
*   **Важные подключения** — параметр `critical` (шаблоны `conn_id`, fnmatch; по умолчанию
    `airflowdb`, `ctl`, `s3` и подключение бакета логов). Упавшее подключение роняет свой таск,
    но ран краснеет (`health_errors`) только из-за важного; вспомогательное — ⚠️ `health_warn`.

**Группы проверок:**

| Группа | Условие (conn_id / type) | Описание проверки |
|---|---|---|
| **tfs** | `tfs` в ID **и** тип `aws` | Проверка S3-бакетов через `list_buckets()` |
| **s3** | тип `aws` (без tfs) | Проверка прав доступа к объектному хранилищу |
| **postgres** | тип `postgres` | `SELECT current_user, current_database()` |
| **ctl** | тип `http`, `ctl*` или FQDN | Вызов `GET /v5/api/info` (Kerberos Auth) |
| **clickhouse** | тип `sqlite` / `clickhouse` | Проверка версии через `ClickHouseHook` |
| **kafka** | тип `kafka` | Листинг топиков через `KafkaAdminClientHook` |
| **trino** | тип `trino` | Валидация сессии через `TrinoHook`; нерезолвящийся хост → `☮️` |
| **redis** | тип `redis` | Проверка доступности через `redis.Redis(...).ping()` |
| **other** | прочие | Помечаются символом `☮️` (пропуск) |

### [test_hrp_operators.py](test_hrp_operators.py)
**Регрессионный стенд операторов HRP (`test_hrp_operators`).**

Config-driven стенд для пакета `sber_app_dataplatform_etl_core.hrp_operators`: прогон на каждом
релизе и хотфиксе, при обновлении Airflow и зависимостей (встраивается в пайплайн dpm).

**Что покрывается** (по группам)

- `to_s3` — `PostgresToS3(List)`, `Clickhouse{Table,Query}ToS3`, `ClickNativeToS3(List)`:
  все сжатия (`gzip`/`zip`/`tar.gz`/`None`), `xstream_sanitize`, массивы, NULL, спецсимволы.
  Каждый оператор с `post_file_check=True` сам перечитывает файл и сверяет хэш.
- `s3_to_db` — `S3ToClickhouseTable` (CSV и TSV-семейство): end-to-end PG→S3→CH, сверка row count.
- `db_to_db` — `PostgresToPostgres`, `ClickhouseToPostgres`, `PostgresToClickhouse`,
  `*Incarnation*`: прямые переливки, сверка count и содержимого.
- `s3_utils` — `S3ToS3`, `S3Archive`, `CheckS3FileHash`, `PostgresDDL`: перепаковка сжатий,
  ZIP-архив, сверка MD5, генерация DDL.
- `viewers` — `S3ListKeys`, `S3FileRead`, `S3BucketViewer`: листинг ключей/бакетов, чтение строк.
- `cluster` — `ClickHouseClusterOperator`: DDL на ноды кластера (за флагом `run_known_broken`).

**Инфраструктура**
- Postgres: таблицы в `airflowdb` (схема `public`); на таблицу и каждую колонку ставится
  `COMMENT` (требование Quality Gate).
- ClickHouse: таблицы в схеме `technical`, имена по имени теста.
- S3: connection `s3-archive`, бакет `test_operators`, префикс `hrp_tests/`.

**Методология**
1. **Setup** — DROP/CREATE источников и таргетов (PG + CH) с данными (NULL, спецсимволы, массивы);
   `setup_s3` проверяет соединение/бакет и чистит S3-префикс (идемпотентность). Каждый setup
   скипается при выключенном флаге своей системы (`setup_pg`→`test_pg` и т.д.) ИЛИ при
   недоступности системы: ошибка соединения гасит флаг (проверки уходят в ☮️, а не ❌ каскадом).
2. **Execution** — операторы под тестом во всех поддерживаемых сжатиях.
3. **Validation** — сверка row count и (где формат детерминирован) содержимого.
4. **Summary** — markdown-таблица статусов `✅/❌/☮️` в заметках DAG (как в `test_connections`).
5. **Cleanup** — гарантированное удаление таблиц и S3-ключей (`trigger_rule=ALL_DONE`).

**Флаги выбора проверок**
- `test_pg` / `test_ch` / `test_s3` (по умолчанию `True`) — включают проверки по системам.
  Каждая проверка гейтуется по всем задействованным ею системам (**AND**): `pg→s3` идёт только
  при `test_pg И test_s3`, `s3→ch` — при `test_s3 И test_ch`, `ch→pg` — при `test_ch И test_pg`.
  Выключение системы уводит все её проверки (в т.ч. кросс-системные) в ☮️ skipped.
- `run_known_broken` (по умолчанию `False`) — «карантин» поверх системных флагов для проверок,
  пока не проходящих на текущей сборке пакета / требующих кластера `datalab`: `pg_to_s3_list`,
  `ch_native_list`, `ch_table_query_s3`, `s3_to_ch_tsv`, `pg_incarnation`, `cluster`.
- `run_cleanup` (по умолчанию `True`) — операционный флаг: `False` оставляет таблицы/S3-ключи
  для отладки упавшего прогона.

Примечание: `max_active_runs=1` — имена таблиц фиксированы, параллельные прогоны не поддержаны.
`ClickhouseTableToS3`/`ClickhouseQueryToS3` считают строки через `clusterAllReplicas(datalab,
system.query_log)` — в окружении без кластера `datalab` они не работают, поэтому держатся за
`run_known_broken`.

### [db_cleanup.py](db_cleanup.py)
**Очистка метадаты Airflow (`tools_db_cleanup`).**

Удаляет устаревшие записи из метабазы прямыми SQL-запросами, без CTAS-архивирования.
*   **Параметры**: `retention_days` (180 по умолчанию, минимум 30), `dry_run`, `vacuum`, `reindex`,
    `drop_leftovers`, `custom` (ещё `dag_code` и `dag_pickle`), `schedule` (`0 5 * * *`), `save_params`.
*   **Порционность**: таблицы больше 50 000 строк чистятся порциями. Где индекса по дате нет,
    а целочисленный `id` есть (`task_reschedule`, `task_fail`, `job`, celery-таблицы), порция
    берётся по первичному ключу: порция по датам там была полным проходом таблицы. У
    `task_instance` и `xcom` такого `id` нет — они остаются на диапазонах дат.
*   **Условия квалифицированы именем таблицы (v1.14)**: неквалифицированный `dag_id` в
    `EXISTS` по `dag_run` сравнивался сам с собой, и защита «ран старше cutoff» не работала
    (стенд: 231 669 строк `task_reschedule` вместо 188 028); `dag_code` по той же причине не
    чистился вовсе.
*   **Порядок таблиц** строится по внешним ключам из `pg_constraint`: ребёнок раньше родителя.
    В алфавитном порядке Airflow `dag_run` идёт пятым, а `task_instance` тринадцатым, и с
    `ON DELETE CASCADE` батч ранов утягивает детей в свою транзакцию. Замер на стенде
    (в откатанной транзакции): 493 рана старым порядком — 6.71 с и «удалено 0» у
    `task_instance`, новым — 3.83 с на детей и 0.07 с на раны.
*   **`celery_taskmeta` чистится по своему возрасту**, без связи с `task_instance`:
    `external_executor_id` хранит id только последней попытки, и связь по нему оставляла
    результаты ретраев навсегда — на стенде под старое условие не попала ни одна строка из
    59 602 старше 30 дней. Но и `date_done < cutoff` (v1.9) хватило не на всё: эта дата
    появляется **только** при переходе задачи в терминальное состояние, а у строки,
    застрявшей в `STARTED`, её нет никогда. Замер 18.09.2026: дата стоит у всех `SUCCESS`
    и `FAILURE` и отсутствует у обеих `STARTED`; на альфе такого осадка накопился 91 при
    94 в карточке Health. С v1.10 возраст такой строки берётся по `id` — он растёт вместе
    с `date_done`, — а граница считается как **минимум `id` среди ещё не устаревших** строк:
    всё, что вставлено раньше самой ранней «свежей» строки, заведомо старое. Максимум среди
    уже старых для этого не годится: сирота, оказавшаяся верхней в старом диапазоне, сама
    выпадает из множества, по которому он считается, и не удаляется никогда — проверено
    симуляцией полного цикла на стенде. Живую задачу граница не заденет: её `id` выше, и обе
    живые `STARTED` на стенде остались нетронутыми.
*   **Переиндексация по одному индексу (v2.1).** С v1.11 до v2.0 её не было: `REINDEX SCHEMA
    CONCURRENTLY` при обрыве оставлял копии всех индексов (сигма dev 01.10.2026: 551 на
    `dag_run`). Теперь разовая галка `reindex`: `REINDEX INDEX CONCURRENTLY` по одному, от
    меньших к большим, бюджет 3 ч; отказ сразу убирает свою копию `*_ccnew` и красит таск.
*   **Админская учётка (v2.1).** Берётся `af_admin_available`: в Vault есть `DB_ADM_USER_1_1`,
    `DB_USER_OWNER_1` или `DB_USER_1_2`. Без неё нет ни `vacuum`/`reindex`/`drop_leftovers`, ни их
    галок: штатный пользователь Airflow таблицами не владеет, а не владельцу PG 16 и `VACUUM`, и
    `ANALYZE` молча пропускает (`WARNING … skipping it`, стенд 01.10.2026) — статистику тогда
    ведёт автовакуум. Учётка есть — права всё равно проверяются перед первой командой
    (`owner_problem`): не владеет таблицами — таск ☮️ с её именем и списком таблиц.
*   **Таски:** `params` → `drop_leftovers` → `clean` → `vacuum` → `reindex` → `report` и
    `integrity` → `health_warn` / `health_errors`; без админской учётки — `params` → `clean` →
    `report` и `integrity`. `integrity` идёт последним, чтобы не принять копию идущей
    перестройки за остаток. `dry_run` управляет только `clean`: у `vacuum`, `reindex` и
    `drop_leftovers` свои галки (v2.9). `reindex` и `drop_leftovers` разовые, в Variable не
    сохраняются; ключ `reindex` в `tools_db_cleanup_params` от v1.10 галку не включит.
*   **Отчётность**: заметка `clean` дописывается сверху строкой на таблицу (v2.2, раньше переписывалась целиком на каждой порции), итоговая таблица — сверху в конце; финальный отчёт по размерам схемы `main` с delta к предыдущему запуску.
*   **Целостность метабазы (v2.0, таск `integrity`)** — плагин здоровья: остатки прерванного
    REINDEX (`*_ccnew`/`*_ccold`) — ❌, невалидные индексы и дубли, возраст транзакций
    (wraparound), заполнение последовательностей, мёртвые строки ключевых таблиц, транзакции
    дольше часа, непроверенные ограничения — ⚠️; горизонт вакуума (xmin слотов репликации и
    сессий, v2.7) — ⚠️ от 100 тыс., ❌ от 1 млн транзакций. Только каталог PG, без блокировок. Повод —
    сигма dev 01.10.2026: 551 остаток на `dag_run` (4 ГБ) тормозил каждую запись в него.
    Разовая галка `drop_leftovers` удаляет остатки с живым исходным индексом — с v2.6 отдельным
    таском сразу после `params`, до `clean`, `vacuum` и `reindex`; с v2.8 — одной командой
    `DROP INDEX` (секунды; блокировку ждёт 3 с и повторяет), а не `CONCURRENTLY` по одному (2 мин на индекс):
    3 с ожидания и до 20 повторов через 15 с, чтобы не держать очередь запросов к таблице.
    Удаляется только остаток, у которого исходный индекс (имя без суффиксов) есть и валиден,
    остальное — строкой в заметке. С остатками каждая запись и VACUUM обновляют все лишние
    индексы — поэтому таск идёт до `clean`. `amcheck` не используется: читает индексы целиком.

    | Проверка | Что смотрит | ⚠️ warn | ❌ error |
    |---|---|---|---|
    | `indexes` | индексы схемы `main` | невалидный индекс, дубль (те же колонки, классы, выражения, условие) | остатки прерванного REINDEX `*_ccnew`/`*_ccold` — по таблицам, штук и размер |
    | `wraparound` | `age(datfrozenxid)` базы, три старейшие таблицы | > 1 млрд | > 1,5 млрд (PG встаёт у 2 млрд) |
    | `sequences` | доля израсходованного у последовательностей `main` (`job`, `log`, `celery_taskmeta` — int4) | > 70 % | > 90 % |
    | `vacuum` | мёртвые строки `dag_run`, `task_instance`, `job`, `log`, `xcom`, `celery_taskmeta` | > 20 % и > 100 тыс. | — |
    | `long_tx` | транзакции дольше часа (держат вакуум; чужие без `pg_read_all_stats` не видны) | есть | — |
    | `xmin_horizon` | возраст xmin у слотов репликации и сессий: с `hot_standby_feedback` горизонт держит и запрос на реплике | > 100 тыс. транзакций | > 1 млн |
    | `constraints` | ограничения `NOT VALID`, так и не проверенные | есть | — |

    Отчёт плагина пишет `health_errors`, срок 26 ч.
*   **Внимание**: `dry_run=False` по умолчанию — это реальное удаление.

### [log_cleanup.py](log_cleanup.py)
**Обслуживание бакета логов (`tools_log_cleanup`).**

Ежедневно (`17 8 * * *`, 08:17 MSK) обслуживает **весь** бакет логов: один срок хранения на весь бакет
(120 дней, на деве 30 через `save_params`), уборка и статистика. Бакет и подключение берутся
из `[logging] remote_base_log_folder` и `remote_log_conn_id`, а не прописаны именем.
*   **Параметры**: `days` — срок всего бакета; `quota_gb` — квота учётки S3, если хранилище её не отдаёт; `lifecycle` — выставлять ли правило жизненного
    цикла на корень; `max_minutes` — потолок обхода; `dry_run` — посчитать, ничего не меняя.
*   **Таски**: `params` → `layout` → `sweep` → `report` → `health_warn` / `health_errors`; `sweep`
    пишет строку на папку сверху по ходу обхода, `report` — строку на проверку над таблицей.
*   **Здоровье** (v2.5, навык [`tools-log-cleanup`](skill/tools-log-cleanup.md)): `fill` — занято всеми
    бакетами учётки к её квоте (⚠️ 80 %, ❌ 95 %): лимит S3 выдаётся на учётку, а видит учётка
    только свои бакеты (`s3` и `s3-archive` — разные учётки). Квота и объёмы — из заголовков
    `HEAD bucket` (Ceph RGW), иначе квота — `quota_gb`, бакет логов меряется обходом, прочие
    листаются ради суммы; нет квоты — `fill` не проверяется и чужие бакеты не листаются. `ttl` —
    доля объектов старше срока (⚠️ > 10 %, ❌ > 50 %), `sweep` — обход не закончен (⚠️).
*   **Один срок на всё** (решение 25.09.2026): под префиксом логов только логи задач, в корне —
    `ctl/`, `tfs/`, `docs/`, `system_health/`, `dag_snapshots/`, `pg_activity/`,
    `queue_cleanup/`. Своих сроков у папок нет; правила на папки от прошлых версий DAG-а
    `layout` снимает. Что должно жить дольше срока, владелец переписывает сам: `test_dags`
    освежает копию неизменившегося дага, `tools_mcp_skills` — документы. Неотправленное из
    `tfs/queue/` за срок уже не нужно.
*   **Отчётность**: таблица по папкам верхнего уровня (объекты, объём, старейший, удалено) в
    заметку таска и DAG-а, та же сводка — в XCom. Логи задач обходятся последними.
*   ⚠️ **Правило жизненного цикла работает само и асинхронно.** Уменьшили срок — хранилище
    удалит лишнее своим сканером, без обхода и без отчёта (проверено на стенде 16.09.2026:
    прогон с `days=7` стоил 23,5 тыс. объектов). Экспериментируйте с `dry_run=True`.

*   **Правилу не доверяем**: оно ставится на корень (`DeleteAfter`), но через корпоративный шлюз
    правила раньше не работали (см. `tools/pg_activity.py`), поэтому уборка всё равно идёт
    обходом, а отчёт показывает, сколько объектов старше срока нашлось.
*   **Квота без заголовков**: заголовки квоты отдаёт Ceph RGW (`x-rgw-quota-user-size`,
    `x-rgw-bytes-used`); в стандартном S3 такого запроса нет, MinIO отдаёт квоту только admin API.
    Строка на бакет (📦) — в заметке `sweep`.
*   `ttl` после уменьшения `days` разово краснеет: старое обход удаляет в том же прогоне, но
    считает. Падение `layout` или `sweep` — `health_errors` «таск не выполнился».

### [log_events.py](log_events.py)
**Сбои доставки задач по журналу метабазы (`tools_log_events`).**

Считает по таблице `log` события, которыми планировщик сообщает, что задача не доехала до
воркера или не доработала: `stuck in queued reschedule` (пролежала в очереди дольше
`task_queued_timeout`), `stuck in queued tries exceeded` (перезапросы исчерпаны),
`heartbeat timeout` (процесс перестал биться — так выглядит внезапная смерть, а не
медленный запрос), `state mismatch` (исполнитель отрапортовал об окончании задачи, пока
она числилась в очереди).
*   **Зачем**: в интерфейсе эти события видны по одной задаче за раз, поэтому вопрос «это
    у нас или у всех» без отчёта ответа не имеет. Все четыре — про доставку и жизнь
    процесса, а не про логику дага: у сенсора ТФС на alpha за 18 часов набралось двенадцать
    перезапросов очереди, две потери хартбита и расхождение состояния.
*   **Событие и задача — разные вещи**: о зависшей задаче планировщик пишет на каждом
    круге проверки, поэтому одна мёртвая задача даёт тысячи записей. Рядом с числом
    событий всегда стоит число различных попыток (даг, задача, прогон, индекс отображения,
    номер попытки), и доля с порогом считаются по ним. Замер на боевом контуре 04.09:
    26 806 событий, из них 87% — пять пар «даг · задача», давно молчащих; доля по событиям
    выходила 346%.
*   **Знаменатель обязателен**: рядом со счётчиком всегда стоит число запусков за то же
    окно и доля. Десять сбоев на четыре тысячи запусков и десять на сорок — разные новости,
    а «ноль сбоев» при нуле запусков — это простой, а не здоровье. Вложенность неполная:
    попытка, застрявшая в очереди и не стартовавшая, в числитель попадёт, а в знаменатель
    нет, — поэтому доля читается как оценка порядка.
*   **Время — московское**, и момент сбора, и время последнего события. Пояс задаёт сам
    запрос (`AT TIME ZONE INTERVAL '+03:00'`), а не настройка соединения: от неё же
    зависит граница суток в разбивке по дням, и смена настройки на сервере сдвинула бы её
    молча. Слово `INTERVAL` обязательно и убирать его нельзя: замер на PostgreSQL 16 для
    `2026-09-04 12:20:30+00` даёт `15:20:30` с `INTERVAL` и `09:20:30` без него —
    текстовая форма разбирается как POSIX-спецификация зоны, где знак смещения
    инвертирован. Цифры при этом остаются правдоподобными, поэтому ошибка тихая.
*   **Параметры**: `hours` (окно, 24), `days` (разбивка по дням, 7), `top` (строк «даг ·
    задача», 10), `alert_after` (порог: **задач** больше — краснеть; `0` — только
    показывать),
    `schedule`, `save_params`; хранятся в Variable `tools_log_events_params`.
*   **Сторож имён — два, и дорогой платится только по делу**: имя события Airflow может
    переехать, и тогда счётчик молча станет нулём. Бесплатная половина сверяет наше имя с
    константой `TASK_STUCK_IN_QUEUED_RESCHEDULE_EVENT` самого Airflow. Дорогая ищет по
    журналу похожие события вне наших списков — `ILIKE '%…%'` индексом по `event`
    воспользоваться не даёт и перебирает все строки окна (2,5 с за сутки, 16 с за неделю
    на журнале в миллион строк), поэтому выполняется только когда сбоев не нашлось вовсе:
    ровно тогда её ответ и нужен.
*   **Наши события — отдельной строкой**: `ctl dag paused` пишет сенсор, когда пропускает
    загрузку из-за запаузенного дага. В число сбоев доставки не входит и порог не трогает
    (это решение человека, а не поломка), но считается и показывается: из-за паузы
    загрузка стоит, и «сколько раз за сутки» — ответ на «часто ли».
*   **Только чтение**: журнал не правится и не чистится — чистит его `db_cleanup`, и от его
    `retention_days` зависит глубина разбивки по дням.

| Событие | Что оно значит |
|---|---|
| `stuck in queued reschedule` | Задача пролежала в `queued` дольше `task_queued_timeout` (600 с) и возвращена в `scheduled`: её отдали celery, а воркер не начал |
| `stuck in queued tries exceeded` | Перезапросов было больше `num_stuck_in_queued_retries` — планировщик сдался и пометил задачу упавшей |
| `heartbeat timeout` | Процесс задачи перестал слать хартбит (`scheduler_zombie_task_threshold`, 300 с) — так выглядит внезапная смерть процесса, а не медленный запрос |
| `state mismatch` | Исполнитель отрапортовал об окончании задачи, пока она числилась `queued` — классика для воркера, убитого сигналом |

| Событие | Кто пишет | Что значит |
|---|---|---|
| `ctl dag paused` | `ctl_sensor` | загрузка пропущена: даг воркфлоу на паузе, запускать нечего |

**Параметры:**

| Параметр | Описание |
|---|---|
| 🕐 `hours` | Окно отчёта, часов *(default: `24`, максимум `168` — см. замеры в коде)* |
| 📈 `days` | Глубина разбивки по дням *(default: `7`, максимум `30`)* |
| 🔝 `top` | Сколько строк «даг · задача» показать *(default: `10`)* |
| 🚨 `alert_after` | Порог: **задач** больше — ❌ `health_errors`, ран красный; `0` — только показывать (⚠️) *(default: `0`)* |
| ⏰ `schedule` | Расписание (МСК): cron или пресет, пусто — только вручную *(default: `30 6 * * *`)* |
| 💾 `save_params` | Сохранить параметры запуска как значения по умолчанию *(default: `False`)* |

### [system_health.py](system_health.py)
**Состояние контура: пульс раз в 5 минут (`tools_system_pulse`) и снимок раз в час
(`tools_system_health`).**

Два DAG'а в одном файле, проверки и пороги общие. Итог — в лог, XCom `return_value` (строка
на прогон) и заметку. У карточки Health истории нет; здесь сетки DAG'ов — лента здоровья: ❌ —
был `error`. До 28.09.2026 всё снимал один часовой DAG.
*   **Пульс** (`tools_system_pulse`, `2-59/5 * * * *`) — «лежит ли контур»: компоненты
    `/api/v1/health` через `get_airflow_health()` (`components`), celery с воркера (воркеры и
    слоты по отбивкам `health_beacon`, как у карточки; нет отбивок — `broadcast` брокеру с
    ожиданием 2 с; очереди, застрявшее), control-канал (`control`), метабаза (`SELECT 1`, соединения),
    задержка доставки самой задачи (`delivery`). Секунды на прогон; таски `collect` (с
    заметкой) → `health_warn` / `health_errors`, без `params` и `report`: 288 прогонов в сутки,
    лишний таск на каждом — лишний поход через воркер. Срок отчёта 15 мин.
*   **Час** (`tools_system_health`, `7 * * * *`) — «почему задачи не идут»: бакет логов на
    запись-чтение-удаление (`s3_logs`), забитые пулы, свежесть разбора файлов и ошибки импорта
    (`parsing`); перенесённые из etl-core (до 1.2.1 их считал `get_system_health`): раны в
    `queued`, у запаузенных и у деактивированных дагов — с ошибкой импорта файла (`runs`), задачи в `scheduled` по дагам с `at_limit`
    (`scheduled`); сторож плагинов (`plugins`).
*   **Сторож плагинов** (`plugins`): у каждого живого дага с тегом `health` отчёт в
    `system_health/checks/` есть и не старше своего `ttl_sec`. Плагин на паузе, без отчёта или
    с просроченным — warn. Находки плагинов не повторяет — о них плагин сообщает сам через
    `health_errors`; у кого сейчас warn/error, в строке справкой. core видит то же, но только на
    запрос `get_system_health`; здесь — в ленте раз в час.
*   **Куда ушли `dag_size` и `tables`** (28.09.2026): размер DAG'ов — в ночной `tools_test_dags`
    (меняется только с выкладкой, а запрос самый тяжёлый из часовых); строки таблиц метабазы
    убраны — размеры с разницей к прошлому прогону показывает `report` в `tools_db_cleanup`.
*   **Control-канал celery** (`control`): задачи идут через списки Redis, а `ping`/`inspect` —
    через pub/sub, и второе может молчать при живом первом. Так было на dev с 27.09.2026
    ~11:10 UTC: воркеры работали, на inspect отвечало 20–40 % опросов, liveness-проба
    перезапускала поды, карточка Health показывала `workers: 0`. Проверка шлёт `ping`
    (5 с) и сверяет число ответивших с числом подов, где задачи идут прямо сейчас (`LocalTaskJob`
    в `running` с хартбитом за 2 мин). Сверяются числа, а не имена: `job.hostname` у платформы —
    IP пода (etl-core `hostname_callable`), узел celery — `celery@<имя пода>`; на узле брокера — права на каналы (`ACL GETUSER`), подписки-шаблоны
    (`PUBSUB NUMPAT`: kombu подписывается шаблоном, `PUBSUB CHANNELS` их не видит) и петля
    pub/sub самому себе. `ping` возвращается, как только ответили все (`limit`), — его время
    и есть задержка самого медленного ответа (`reply_sec`). Часть молчит или все ответили,
    но дольше 2 с (столько ждут карточка и отбивки) — warn; не ответил никто, петля не
    вернулась или подписок нет — error. На dev 28.09.2026 ответы именно опаздывали: `list-workers`
    (1 с) пуст, `ping` с 5 с — все 8; `ACL` и `PUBSUB NUMPAT` там пользователю брокера
    закрыты, в итоге это строка «не прочитаны», а не сбой проверки.
*   **Где набегает задержка** (`control`): три звена по порядку — команда брокеру (`cmd_ms`,
    медиана трёх `PING` к узлу, куда ходит celery), доставка pub/sub самому себе (`pubsub_ms`),
    ответ воркеров (`reply_sec`). Предупреждение — по первому медленному звену: команда
    > 100 мс — узел или сеть; pub/sub > 500 мс при быстрых командах — рассылка брокера; оба
    быстрые, а ответы > 2 с — «медлят сами воркеры», брокер ни при чём. Рядом `INFO` узла:
    роль, uptime (сброс — был рестарт или failover), клиенты и заблокированные, подписки,
    ops/s, память, отказы в соединении, вытеснение.
*   **Плагины здоровья** (тег `health`, оба DAG'а): итог ещё и отчётом в бакет логов,
    `system_health/checks/<dag_id>.json` (`report_health` из `plugins/utils.py`), его
    читает `get_system_health` — раздел `plugins`. Срок отчёта у часового 2 ч 10 мин, у пульса
    15 мин: пропущенные прогоны — и core пишет «последний отчёт N назад». Сбой записи задачу не роняет. Все SQL —
    из таска в метабазу: в AF3 их придётся перевести на REST.
*   **Статус:** таски `params` → `collect` → `report` + `health_warn` / `health_errors`
    (до 28.09.2026 — один `check`); `error` роняет `health_errors`, `warn` — ⚠️ в `health_warn`,
    `collect` находками не падает. Причины исключений наружу — без адресов и паролей.
*   **Новая ошибка импорта — по id строки, не по её времени.** Разбирая битый файл заново,
    Airflow обновляет ту же строку `import_error` и ставит `timestamp = utcnow`
    (`dag_processing/processor.py:653`), поэтому по времени новыми выходили все ещё не
    починенные файлы — каждый прогон. Починенный файл строку теряет, новый битый получает
    новую из sequence; база сравнения — наибольший видённый id, и лежит она в `return_value`
    прошлого прогона. Нет прошлого прогона (или он старой версии) — про новые ошибки прогон
    молчит, общее число ошибок при этом видно всегда.
*   **Разбор файлов не делает.** Полный `DagBag` — это ночной `parse_time` в `test_dags`
    (11 с на альфе, больше 2,5 мин на сигме); здесь — его последний итог справкой и
    свежесть `dag.last_parsed_time`. Отставший файл — старше и
    `min_file_process_interval + dag_file_processor_timeout`, и тройной медианы: на стенде
    круг разбора дольше их суммы.
*   **Celery отсюда виден и там, где карточка серая**: брокер опрашивается с воркера, а не
    из вебсервера.
*   **Параметры**: `schedule` (`7 * * * *`), `s3_slow_sec` (5), `save_params`; хранятся в
    Variable `tools_system_health_params`.

**Проверки и пороги** (в скобках — чей DAG: пульс или час):

| Проверка | Что смотрит | ⚠️ warn | ❌ error |
|---|---|---|---|
| `components` (пульс) | `get_airflow_health()` — та же функция, что за `/api/v1/health` | triggerer `unhealthy` | метабаза, шедулер или dag-processor `unhealthy` |

| `s3_logs` (час) | бакет логов задач: запись, чтение со сверкой, удаление | всё прошло, но дольше `s3_slow_sec` | любая операция упала или прочитано не то |

| `pools` (час) | `Pool.slots_stats()`: пулы без свободных слотов, в которых ждут задачи | такой пул есть | — |
| `metabase` (пульс) | время `SELECT 1`, соединений против `max_connections` | > 1 с или > 80 % | > 95 % |
| `parsing` (час) | свежесть разбора файлов, DAG'и без сериализации, ошибки импорта, итог ночного `parse_time` | новые ошибки импорта, файл выбился из круга разбора (старше и `min_file_process_interval + dag_file_processor_timeout`, и тройной медианы), разбор стоит целиком, DAG без сериализации, у `parse_time` находки | — |
| `runs` (час) | раны в `queued` дольше 30 мин, раны `queued`/`running` у запаузенных и у деактивированных дагов (поимённо, 10 самых старых; у деактивированных — сколько шедулер не смотрел на ран и ошибка импорта файла) | есть раны у запаузенных или деактивированных дагов | — |
| `scheduled` (час) | даги с задачами в `scheduled` дольше 5 мин: сколько, как давно, упёрлись ли в свой `max_active_tasks` (`at_limit`) | застряли даги **не** на своём лимите | — |
| `plugins` (час) | отчёты дагов-плагинов (тег `health`) в `system_health/checks/`: есть ли и не старше ли своего `ttl_sec`. Находки плагинов не повторяет — о них сообщает их `health_errors`; у кого сейчас warn/error, в строке справкой | плагин на паузе, без отчёта или с просроченным отчётом | — |

**Вывод:** строка на проверку в логе; XCom `return_value` таска `collect` — одна строка на
прогон, `{status, reasons, checks, took_sec}` (до v2.0 таск звался `check`); заметка
`report` — нездоровые проверки по строке, здоровые одной строкой с временами.

**Чего этот DAG не увидит:**

- Когда воркеры не берут задачи, он и сам не запустится. Сигнал тогда — пропуски в сетке
  обоих DAG'ов и растущая `delivery` у пульса.
- Пока на контуре нет etl-core PR #35, висящий S3 может подвесить и лог этой задачи
  (выгрузка из `emit` синхронная). Её снимет `execution_timeout`, и падение по таймауту
  само будет сигналом.
- Длительность разбора по файлам: в метабазе 2.11 её нет. Её меряет ночной `parse_time`
  в `tools_test_dags` (полный `DagBag`, 11 с на альфе и больше 2,5 мин на сигме — поэтому
  не здесь), его последний итог показывается справкой.

### Приоритет и потолок времени у коротких проверок

`pg_activity`, `log_events`, `system_health`, `system_pulse` и `test_connections` работают секунды, а
нужны ровно тогда, когда контуру плохо. Поэтому у них:

*   **`priority_weight: 900` с `weight_rule: 'absolute'`.** Все проверки живут в общем
    `tools_pool` на 16 слотов, а `test_dags` разбирает до двенадцати задач разом — то есть
    способен занять пул почти целиком, и короткий отчёт ждал бы за ним. Приоритет решает
    ровно эту гонку: планировщик ставит задачи в очередь по убыванию веса
    (`scheduler_job_runner.py`, `order_by(-TI.priority_weight, …)`).
    `absolute` обязателен: правило по умолчанию складывает вес вниз по цепочке, и первая
    задача получала бы 2700 вместо 900 — сравнение с соседями зависело бы от длины
    цепочки. Проверено на стенде: с `absolute` у всех задач ровно 900.
    Значение ниже агента CTL (999/1000) намеренно: тот двигает боевые загрузки.
*   **`execution_timeout`** — 5 минут, у проверки подключений 3, у пульса 2. Потолок заведомо больше
    собственных таймаутов проверки (у соединений это 15 секунд), то есть ловит зависание,
    а не медленный ответ: зависшая проверка иначе держит слот пула до конца суток.
*   **`dagrun_timeout`** — 30 минут (у пульса 4 — меньше его интервала): `execution_timeout`
    ограничивает таск, а при `max_active_runs=1` зависший прогон закрывает дорогу всем следующим.

Тяжёлые прогоны — `test_dags`, `test_hrp_operators` — приоритета не получают намеренно:
они длинные и несрочные. Чистильщики (`db_cleanup`, `log_cleanup`, `paused_runs_cleanup`) —
получают те же 900: с весом по потомкам (единицы) их вытесняли большие даги с весом в сотни —
планировщик берёт верхушку `scheduled` по весу и кончает цикл, как только в ней нашлось что
запустить. Сигма dev 01.10.2026: `db_cleanup.clean` полчаса в `scheduled` при пустом пуле.

Потолки есть у всех дагов `tools` (с 28.09.2026 — и у долгих), и каждый заведомо больше
штатной длительности — ловит зависание:

| Даг | `execution_timeout` | `dagrun_timeout` |
|---|---|---|
| `db_cleanup` | 4 ч (VACUUM по таблице сам ограничен часом) | 6 ч |
| `log_cleanup` | 2 ч (обход ограничен `max_minutes`) | 4 ч |
| `test_dags` | 1 ч (перепроверка ждёт парсинг до 20 мин) | 3 ч |
| `test_hrp_operators` | 30 мин | 2 ч |
| `test_kafka_*` | 15 мин | 30 мин |
| `queue_analyze`, `paused_runs_cleanup` | 10 мин | 30 мин |
| `mcp_skills` | 5 мин | 15 мин |
| `dummy` | 5 мин | 50 мин |
| `system_pulse` | 2 мин | 4 мин (меньше интервала в 5 мин) |

⚠️ Приоритет действует только на шаге «планировщик выбирает, что поставить в очередь». На
очередь celery он не влияет — сообщение уезжает без приоритета
(`celery_executor_utils.py`: `apply_async(args=args, queue=queue)`), — и не вытесняет уже
работающие задачи. Если задача застряла в `queued`, потому что воркеру плохо, приоритет не
поможет: это видно в отчёте `log_events`, а лечится отдельной очередью или самим воркером.

### [pg_activity.py](pg_activity.py)
**Сторож метабазы: зависшие сессии, долгие запросы, блокировки (`tools_pg_activity`).**

Каждые 10 минут снимает `pg_stat_activity` метабазы и разбирает находки на `idle in transaction`,
долгие активные запросы и блокировки (`pg_blocking_pids()`).
*   **Опознание владельца**: pid из `application_name` (`app-dataplatform-etl-worker_<pid>`)
    сопоставляется с `task_instance.pid`, поэтому против сессии в отчёте стоит `dag_id.task_id`.
*   **Жив ли владелец** (`owner_alive`): `task_instance.state` отвечает только «числится в
    работе», а бьётся `LocalTaskJob` — поэтому смотрим ещё и `job.latest_heartbeat`. Хартбит
    свежее `zombie_after_sec` (умолчание 300 с, как у зомби-детектора Airflow) — владелец жив
    (`true`); протух или таск уже кончился — не жив (`false`); pid ни с чем не сошёлся —
    не опознан (`null`). Разница не косметическая: у живого таска транзакция закроется сама,
    у брошенной сессии — никогда. Число находок без живого владельца идёт в сводку счётчиком
    `orphan`.
*   **Параметры**: пороги `idle_tx_sec` / `long_query_sec` / `lock_wait_sec` / `zombie_after_sec`,
    `alert`, `save_s3`, `dry_run` и расписание `schedule` (`*/10 * * * *`);
    хранятся в Variable `tools_pg_activity_cfg`, галка `save_params` (до 24.09.2026 —
    `save_to_var`) перезаписывает её значениями формы. Сохраняет отдельный таск `params`.
*   **Убийство сессий**: параметр `terminate` (по умолчанию выключен и в Variable **не сохраняется**),
    при `dry_run=True` только показывает кандидатов. Кандидат — только сессия без живого
    владельца: прекратить сессию работающего таска значит уронить чужую работу — он получит
    обрыв соединения с метабазой, провалит хартбит и умрёт зомби. Суточная транзакция живого
    таска остаётся находкой, но не кандидатом; это вопрос к владельцам дага.
*   **Почему сессии живут так долго**: таймауты сессии метабазе намеренно не ставятся из кода
    (`etl-core`, `utils/pg_settings.py`): `options` уезжает в стартовом пакете соединения, и
    отказ на `connect` — это провал хартбита и упавший таск, а не медленный запрос. Серверный
    `idle_in_transaction_session_timeout` на метабазе — вопрос к сопровождению PG; пока его
    нет, брошенная транзакция висит до перезапуска процесса и держит `xmin`, мешая autovacuum.
*   **Снимки**: при находках пишутся в бакет логов, папка `pg_activity/<дата>/<время>.json`;
    старые убирает `tools_log_cleanup` общим сроком бакета.
*   **Отчётность**: сводка в заметку; находки при `alert=True` — ❌ `health_errors` (ран
    красный, уведомление), без него — ⚠️ `health_warn`.

| `owner_alive` | Что это | Что делать |
|---|---|---|
| `true` | таск идёт и бьётся (хартбит `job` свежее `zombie_after_sec`) | ничего: транзакция закроется вместе с таском. Висит сутками — вопрос к владельцам дага |
| `false` | таск числится в работе, но хартбит протух, либо уже завершился | сессия брошена: процесса нет, соединение осталось |
| `null` | владельца не опознали (чужой pid, не разобрался `application_name`) | то же, но без имени |

**Параметры:**

| Параметр | Описание |
|---|---|
| `idle_tx_sec` | Порог для `idle in transaction`, сек *(default: `300`)* |
| `long_query_sec` | Порог для активного запроса, сек *(default: `300`)* |
| `lock_wait_sec` | Порог ожидания блокировки, сек *(default: `60`)* |
| `zombie_after_sec` | Хартбит старше — владелец не жив, сек *(default: `300`, как у зомби-детектора Airflow)* |
| `alert` | Находки — `error` (ран красный через `health_errors`), иначе `warn` *(default: `True`)* |
| `save_s3` | Писать снимки в S3 *(default: `True`)* |
| `dry_run` | При `terminate=True` только показать кандидатов *(default: `True`)* |
| `schedule` | Расписание: cron или пресет, пусто — только вручную *(default: `*/10 * * * *`)* |
| `save_params` | Записать значения формы в Variable `tools_pg_activity_cfg` *(default: `False`)* |
| `terminate` | Убивать найденные сессии. **В Variable не сохраняется** *(default: `False`)* |

Пустые снимки не пишутся — счётчики и так уходят в лог каждый запуск.

### [paused_runs_cleanup.py](paused_runs_cleanup.py)
**Зависшие раны запаузенных дагов (`tools_paused_runs_cleanup`, раз в час, создаётся на паузе).**

Шедулер запаузенный даг не разбирает, а `trigger_dag` паузу не смотрит: ран в `queued` /
`running` у такого дага не начнётся и не кончится (`plugins.tools_system_health.checks.runs` в `get_system_health`).
Даг находит такие раны старше `older_than_hours` (24 ч) и при `close=True` помечает их
failed — как кнопка Mark failed: незавершённые задачи → `skipped`.

*   **Возраст**: `queued` — от `queued_at`; `running` — от последнего движения задач
    (`max(end_date)`), иначе от `start_date`. Ран с задачей в `running` не трогается: она
    доработает, и ран попадёт в следующий проход. Правило то же, что у санитара `ctl_monitor`.
*   **Отчёт** (`collect`, до 28.09.2026 `find`) — заметка на ран: даги, раны, возраст, задачи по состояниям и
    последняя запись о паузе в журнале `log` (UI, API, CLI; пауза из кода записи не оставляет).
*   **Закрытие** (`close`) — только при `close=True` и числе ранов не больше `max_runs` (200),
    иначе таск красный и не закрыто ничего. Без сериализованного дага — запросом к метабазе.
    На ран — заметка, в журнал — событие `paused_run_failed`. Паузу даг не снимает.
*   **Параметры** `older_than_hours`, `states`, `dag_id_like`, `close`, `max_runs`, `schedule`
    сохраняются в `tools_paused_runs_cleanup_params`. `close` сохраняемый: чтобы закрывали и
    плановые запуски, один раз запустить с `close` и `save_params`.

**Почему они висят.** Шедулер запаузенный даг не разбирает вовсе: не ставит задачи, не
проверяет `dagrun_timeout` (AF 2.11.2, `models/dagrun.py:412`,
`scheduler_job_runner.py:1665`). А `trigger_dag` (кнопка, API, наш сенсор) паузу не смотрит
и создаёт ран сразу в `queued`. Такой ран не начнётся и не кончится, пока паузу не снимут, —
а сняв её, человек получит пачку старых запусков разом. В `get_system_health` это
`runs.paused_active`.

| Ран | Возраст считается от | Не трогаем |
|---|---|---|
| `queued` | `queued_at` (у старых ранов без него — `execution_date`) | — |
| `running` | последнего движения: `max(end_date)` задач, иначе `start_date` | ран, где задача в `running`: она доработает (запрос в GP не рвём), и ран уйдёт в следующий проход |

**Закрытие** (`close=True`) — результат как у кнопки: незавершённые задачи → `skipped`, ран →
`failed`. Делается одним запросом в одной сессии на ран, а не вызовом кнопки
`set_dag_run_state_to_failed` (`airflow/api/common/mark_tasks.py`). У того два дефекта,
оба пойманы на сигме 24.09.2026:

* ищет каждую задачу рана в текущем коде дага — у старого рана задачи, которых в коде уже
  нет, дают `KeyError` (`reload_adapt_1_pers_static_data_daily`, ран от 05.05);
* ставит `skipped` каждой задаче своей сессией. В таске пул соединений выключен, то есть
  это новое подключение к метабазе на задачу; одно повисло на переборе хостов, и таск
  упал по `execution_timeout`.

**Параметры:**

| Параметр | Описание |
|---|---|
| `older_than_hours` | Порог возраста, ч *(default: `24`)* |
| `states` | Какие раны брать *(default: `running`, `queued`)* |
| `dag_id_like` | Фильтр `dag_id`, SQL `LIKE` (`CTL.%`); пусто — все *(default: пусто)* |
| `close` | Закрывать найденное; иначе только отчёт *(default: `False`)* |
| `max_runs` | Предохранитель: найдено больше — не закрываем ничего, таск красный *(default: `200`)* |
| `schedule` | Расписание: cron или пресет, пусто — только вручную *(default: `0 * * * *`)* |
| `save_params` | Записать форму в Variable `tools_paused_runs_cleanup_params` *(default: `False`)* |

Даг создаётся на паузе: закрывающий инструмент не должен включиться сам после выкладки.

### [queue_analyze.py](queue_analyze.py)
**Разбор очереди: почему задачи ждут, и мусор в брокере (`tools_queue_analyze`, каждый час в :10).**

До 24.09.2026 — `tools_queue_cleanup` (`queue_cleanup.py`), только брокер. Теперь даг прежде
всего разбирает очередь, а чистка брокера — один таск по разовой галочке `purge`. Таски:
после `params` параллельно `broker`, `scheduler`, `capacity`, `pidbox`; `purge` ждёт `broker`, `purge_pidbox` — `pidbox`, `report` —
всех. Дампы убирает `tools_log_cleanup` общим сроком бакета.

*   **`scheduler`** — каждая живая задача в `scheduled` (даг не на паузе, ран `running`),
    ждущая дольше `stale_min` (5 мин), получает одну причину по порядку: **лимит дага**
    (`queued`+`running` ≥ `max_active_tasks`) → **пул** исчерпан → **приоритет** (вес ниже
    медианы задач, ушедших в работу за час) → **прочее**. Отдельно: задачи на парковке (даг на
    паузе или ран не `running`), раны за сутки, закрытые без единого старта (след
    `dagrun_timeout` при голодании), раны запаузенных дагов (→ `tools_paused_runs_cleanup`).
*   **`capacity`** — `queued`+`running` против `parallelism` × живые шедулеры (`job`,
    хартбит свежее `scheduler_health_check_threshold`); слоты воркеров из снимка отбивок
    (etl-core `health_beacon`), если он есть на контуре. `parallelism` — из конфига
    воркера: у шедулера он может быть другим, его значение даёт MCP `get_config_value`.
*   **`pidbox`** — сет привязок ответных очередей control-канала celery
    (`_kombu.binding.reply.celery.pidbox`): сколько записей и пять для примера. Отвечая на
    ping/inspect, воркер читает сет целиком в главном цикле; на раздутом сете он минутами не
    берёт задачи и молчит на ping (сигма dev 30.09.2026, стек `kill -USR1`). От
    `max_reply_bindings` (1000) — вывод 📮 и ⚠️; разовая галочка `purge_pidbox` удаляет сет отдельным таском `purge_pidbox`
    (`DEL`, а если брокер его не выполнил — пачками `SREM`, до 5 минут; альфа dev 30.09):
    задачи не теряются, живые опрашивающие вернут свою запись при следующем опросе. Размер
    сета раз в 5 минут показывает и пульс (`control.reply_bindings`).
*   **`report`** — заметка на ран, сначала **выводы словами**, потом таблица по разделам.
    Правила вывода — в таблице ниже; они из разбора 23–24.09.2026 на сигме: 297 задач в
    `scheduled` были лимитом `max_active_tasks` дагов `raw_to_stable_*`, а не утечкой слотов;
    `tfs_kafka_snd` с весом 1 проигрывал весам 22–1921 и закрывался по `dagrun_timeout` без
    старта. Разбор целиком — `queue_cleanup/<дата>/<время>_analyze.json` в бакете логов.
*   **Параметры**: `stale_min`, `queues`, `min_junk_share`, `max_delete`, `max_reply_bindings`,
    `schedule` (по умолчанию `10 * * * *`, каждый час; плановый прогон брокер не чистит) сохраняются в `tools_queue_analyze_params`;
    пока её нет, умолчания берутся из прежней `tools_queue_cleanup_cfg`. `purge` и `purge_pidbox` не сохраняются.

**`broker` и `purge`** — прежняя разметка и чистка, перенесены без изменений:

*   **Что считается мусором**: сообщение, чья задача отсутствует в метабазе или уже в
    терминальном состоянии (`success`, `failed`, `skipped`, `upstream_failed`, `removed`).
    Задача берётся не из заголовков, а из тела сообщения: там лежит команда
    `airflow tasks run <dag_id> <task_id> <run_id> [--map-index N]`, то есть первичный ключ
    `task_instance` целиком, и состояние спрашивается по индексу, а не сканом.
*   **Почему не по `external_executor_id`**: у завершившейся задачи там стоит идентификатор
    того самого сообщения, которое и надо удалить, — как признак живости он сохраняет ровно
    мусор. Индекса по нему к тому же нет. В отчёте он остаётся счётчиком расхождений: это
    мера того, насколько разметка по состоянию расходится с памятью метабазы.
*   **Гонки нет**: состояние `queued` коммитится шедулером до того, как сообщение уходит в
    брокер — `send_task` идёт отдельной фазой цикла, в `executor.heartbeat()`. Поэтому у
    любого сообщения «в полёте» задача в метабазе уже не терминальна, и возраст сообщения
    признаком не нужен (в протоколе celery его и нет).
*   **Сверка ключей**: длина очереди и её содержимое читаются командами, к которым kombu
    применяет `global_keyprefix` по-разному — `LLEN` префикс получает, `LRANGE` и `LREM`
    нет. Даг дописывает префикс сам и сверяет `llen` с числом прочитанных; расхождение
    останавливает прогон до всяких удалений. На контуре без этого выходило «в очереди 0»
    при `llen` = 578, и удаление молча било мимо. Стенд без префикса ошибку не ловит —
    проверять с `AIRFLOW__CELERY_BROKER_TRANSPORT_OPTIONS__GLOBAL_KEYPREFIX`. Обе команды
    уходят одним `MULTI/EXEC`: порознь между ними успевает `BRPOP` воркера, длины расходятся
    на единицу и сверка валит прогон на живой очереди.
*   **Пороги**: `min_junk_share` (умолчание `0.5`) и `max_delete` (умолчание `5000`). Мусора
    меньше доли или больше предела — таск `purge` падает, ничего не удалив: картина не та,
    для которой инструмент сделан.
*   **Удаление**: параметр `purge`, по умолчанию выключен и в Variable **не сохраняется**.
    Запуск без него — подсчёт с дампом и отчётом.
*   **Дамп и возврат**: полные тела мусорных сообщений уезжают в бакет логов, папка
    `queue_cleanup/<дата>/<время>.json`, и пишутся всегда — в том числе при подсчёте.
    Вернуть: `rpush` по полям `key` (там уже полный ключ с префиксом) и `payload`. В `/tmp`
    пода дамп класть нельзя — под перезапустят, и возвращать будет нечего.
*   **Предел чтения**: очередь длиннее 50 000 сообщений даг не берёт — тела нужны разметке
    в памяти. Проверяется по `LLEN`, до чтения, и падает с указанием ключа и длины: такую
    очередь разбирают пересборкой ключа, а не удалением по одному сообщению.
*   **Сводка выходит при любом исходе**: если разметка упала, отчёт скажет, в каком она
    состоянии, вместо второй ошибки на том же прогоне. Отказ порога в сводке отличается от
    невключённого удаления — «⛔️ порог не пустил» и причина, а не «☮️ не удаляли».
*   **Чего не заберёт**: сообщения, которые воркеры держат в работе, — их в очереди нет.
    При `task_acks_late = True` они вернутся через `visibility_timeout` (на контуре 6 ч), и
    повторный запуск их подберёт; быстрее — перезапустить поды воркеров.

**Плагин здоровья** (тег `health`), каждый час в :10 (до v3.19 — раз в сутки в 09:10 MSK):
прогон идёт меньше минуты, на пустой очереди ничего не стоит, а при нагрузке картина
нужна в течение часа, а не наутро. Вердикт не выше ⚠️: очередь — не авария. Предупреждение —
мусор в брокере не ниже `min_junk_share`, голодание по приоритету, раны, закрытые без старта,
раздутый сет привязок ответных очередей и не отработавший сборщик; остальные выводы — справка в заметке. Плановый прогон брокер не
чистит: `purge` разовая и не сохраняется. Отчёт для `get_system_health` пишет `health_errors`.

| Таск | Что смотрит |
|---|---|
| `broker` | Сообщения очередей celery: живые и мусор (задача уже в терминальном состоянии или её нет в метабазе). Дамп мусора — в бакет логов |
| `scheduler` | Почему задачи ждут в `scheduled`: лимит дага (`max_active_tasks`), исчерпанный пул, приоритет; раны, закрытые без единого старта; раны запаузенных дагов |
| `capacity` | `queued`+`running` против `parallelism` × живые шедулеры; слоты воркеров из отбивок (`health_beacon`), если они есть на контуре |
| `pidbox` | Сет привязок ответных очередей control-канала (`_kombu.binding.reply.celery.pidbox`): сколько записей, пять для примера |
| `purge` | Удаление размеченного мусора из брокера — с прежними предохранителями |
| `purge_pidbox` | Удаление сета привязок ответных очередей; без галочки — пропуск |
| `report` | Заметка на ран: разделы и **вывод словами** |

**Правила вывода** — из разбора 23–24.09.2026:

| Картина | Вывод |
|---|---|
| Даг ждёт, `queued`+`running` у него ≥ `max_active_tasks` | Упёрся в свой лимит: поднимать лимит в коде дага, а не `parallelism`. Сигма 23.09: 297 задач в `scheduled`, `raw_to_stable_*` с лимитом 4, `slot_reconciler gap=0` — слоты не текли |
| Ждёт слот пула, пул занят целиком | Пул исчерпан |
| Ждёт дольше `stale_min`, дагу и пулу есть место, а впереди по весу и дате рана — окно шедулера (`max_tis_per_query`, не больше `parallelism`), в котором есть задачи дагов на лимите | Окно забито: шедулер берёт голову очереди и кончает цикл, как только в ней нашлось что запустить, — до хвоста не доходит при свободных воркерах и том же весе. Сигма dev 01.10.2026: окно 63, ~53 на лимите дагов, 306 ждали «без причины». Лечится шириной окна (`parallelism`), лимитами этих дагов или весом срочных; лишний шедулер — нет |
| Ждёт дольше `stale_min`, дагу и пулу есть место, вес ниже медианы ушедших в работу за час | Голодает из-за приоритета: `downstream` даёт большим дагам вес в сотни и тысячи (`tfs_kafka_snd` с весом 1 против 22–1921) — `priority_weight` + `weight_rule='absolute'` |
| Ран failed за сутки, ни одна задача не стартовала, есть `skipped` | Закрыт `dagrun_timeout` без старта — след того же голодания (`tfs_kafka_snd` 12:00–15:00) |
| `queued`+`running` ≥ `parallelism` × шедулеры | Слоты executor'а заняты: смотреть `slot_reconciler` в логе шедулера |
| Мусора в брокере ≥ `min_junk_share` | Можно запускать с `purge` |
| Раны запаузенных дагов в `queued` / `running` | Не поедут никогда — `tools_paused_runs_cleanup` |
| Привязок ответных очередей ≥ `max_reply_bindings` | Каждый ответ воркера на ping/inspect читает сет целиком в главном цикле: задачи не берутся, ping молчит, liveness перезапускает поды (сигма dev 30.09.2026). Запуск с `purge_pidbox` |

`parallelism` здесь — из конфига **воркера**, на котором идёт таск; у шедулера он может быть
другим (vault перекрывает `airflow.cfg`). Значение шедулера даёт MCP `get_config_value` →
`components` (etl-core #71).

**Параметры:**

| Параметр | Описание |
|---|---|
| `stale_min` | Ждёт дольше — «давно ждёт», мин *(default: `5`, как у карточки Health)* |
| `queues` | Очереди через запятую; пусто — собрать из конфигурации и метабазы *(default: пусто)* |
| `min_junk_share` | Не удалять, если мусора меньше этой доли очереди *(default: `0.5`)* |
| `max_delete` | Не удалять, если мусора больше этого числа *(default: `5000`)* |
| `schedule` | Расписание; пусто — только вручную *(default: пусто)* |
| `save_params` | Записать форму в Variable `tools_queue_analyze_params` *(default: `False`)* |
| `max_reply_bindings` | Порог записей в сете привязок ответных очередей для вывода 📮 *(default: `1000`)* |
| `purge` | Удалять размеченный мусор. **В Variable не сохраняется** *(default: `False`)* |
| `purge_pidbox` | Удалить сет привязок ответных очередей. Задачи не теряются: в сете только адреса ответов на служебные команды, живые опрашивающие вернут свою запись при следующем опросе. **В Variable не сохраняется** *(default: `False`)* |

### [test_dags.py](test_dags.py)
**Контроль сериализации DAG'ов (`tools_test_dags`).**

Ищет DAG'и, у которых сериализация переписывается на каждом разборе файла, и выясняет
причину. Две независимые группы: `check_serialized` ловит дрожание на парсинге (может
ждать часами), `compare` ведёт версии в S3 и показывает, что изменилось. Отдельно
`parse_time` меряет время разбора файлов и отмечает те, что перевалили половину
`dag_file_processor_timeout`: такой файл обработчик бросит на полпути, и DAG'и из него
исчезнут из метабазы.
*   **Квота S3 дагов** (`s3_quota`, v3.5): заполнение учётки подключения `s3`, из которой ядро
    синхронизирует даги, к её квоте — сумма по всем бакетам учётки (`s3_account_usage` /
    `s3_fill_check` из `plugins/s3_utils.py`, те же, что у `tools_log_cleanup`). ⚠️ 80 %, ❌ 95 %;
    квота из заголовков хранилища или параметра `quota_gb`, нет обеих — skip.
*   **Размер DAG'ов** (`dag_size`, HRPDATALAB-16308; до 28.09.2026 — в часовом
    `tools_system_health`): отдельный таск, вердикт в `health_warn`. Классы по числу тасков
    1 · 2–3 · 4–10 · 11–30 · 31–100 · 101–300 · >300, больше 300 — warn с топом DAG'ов. Счёта
    два, класс по большему: таски в сериализации и число `task_instance` в последнем ране —
    это уже с раскрытыми mapped, и именно оно грузит шедулер. На DAG два поиска по индексу:
    последний ран (`dag_run (dag_id, execution_date)`) и его задачи (`ti_dag_run`). Максимум
    по ранам за 7 дней на dev 28.09.2026 не уложился в 30 с (`task_instance` 13 млн строк);
    цена: expand, который раздувается не каждый ран, виден только когда раздулся последний.
*   **Сводка не падает**: одного замера мало, чтобы отличить дрожание от выкладки — итог в
    сводке `report` и вердикте здоровья. Подтверждённое дрожание — красная перепроверка этого
    DAG'а и ❌ `health_errors` (ран красный); изменения после выкладки — не ошибка.
*   **Сотни изменений разом** (выкладка, обновление core): версии пишутся всем, на
    сравнение уходят первые 100 — `COMPARE_LIMIT`, остальные числом в сводке. Списки между
    задачами через `return` не ходят: XCom-бэкенд контура не принимает больше 500
    элементов, 12.09.2026 на этом упал `find_changed` (685 изменившихся после обновления core).

| Таск | Что делает |
|---|---|
| **`check_serialized.check_serialized_dag`** | Считает по `main.serialized_dag`, у скольких DAG'ов менялась сериализация за год, 3 месяца, месяц, неделю, сутки и час, плюс строка «на последнем парсинге» (`last_updated` попал в окно последнего разбора файла — `dag.last_parsed_time`). **Никогда не падает**: одного замера мало, чтобы отличить дрожание от деплоя. Возвращает список подозрительных DAG'ов, статистика — в XCom `serialized_stats` |
| **`check_serialized.recheck_serialized_dag`** | Mapped-таск, по экземпляру на DAG из списка. Ждёт следующего парсинга (сдвига `dag.last_parsed_time`) и сравнивает сериализацию до и после, показывая расхождения по путям вида `.dag.params[0][1].schema.examples[0]` |
| **`compare.find_changed`** | Находит DAG'и, у которых `dag_hash` разошёлся с последней сохранённой версией, то есть изменившиеся с прошлого прогона. Ничего не скачивает: хэш виден в имени объекта. Список — в XCom `changed_dags` и в заметку, возвращает только счётчики |
| **`compare.snapshot_dags`** | Пишет новые версии в S3 — всех изменившихся, сколько бы их ни было — и возвращает для `expand` пары «прошлая версия → новая», не больше `COMPARE_LIMIT` (100), свежие первыми. Статистика — в XCom `snapshot_stats`, пары сверх лимита — в `not_compared` |
| **`compare.compare_changed`** | Mapped-таск, по экземпляру на изменившийся DAG: сравнивает две соседние версии и показывает расхождения. **Никогда не падает**, итог в XCom `compare`. В списке mapped-тасков вместо `Map Index` — `dag_id` |
| **`parse_time`** | Вне групп: разбирает все файлы DAG'ов и ищет выбросы по времени — медленнее `среднее + 3σ`. Отдельно отмечает файлы, перевалившие половину `dag_file_processor_timeout`: такой файл dag-processor бросит на полпути, и DAG'и из него исчезнут из `serialized_dag`. **Никогда не падает** Он же сверяет построенное с `serialized_dag` и показывает DAG'и, которые разобрались, но в таблицу не доехали: такой DAG виден в UI, но `trigger_dag` по нему падает с `DagNotFound` |
| **`dag_size`** | Вне групп, с 28.09.2026 (до того — проверка часового `tools_system_health`): DAG'и по числу тасков — в определении и в последнем ране с раскрытыми mapped, классы 1 · 2–3 · 4–10 · 11–30 · 31–100 · 101–300 · >300. Больше 300 — ⚠️ в `health_warn`. Заметка — таблица по классам и таблица DAG'ов больше 300 тасков. Размер меняется только с выкладкой, поэтому раз в сутки |
| **`s3_quota`** | Вне групп: заполнение учётки S3, из которой синхронизируются даги (подключение `s3`), к её квоте — сумма по всем бакетам учётки, строка 📦 на бакет. ⚠️ от 80 %, ❌ от 95 %. Квота — из заголовков хранилища (Ceph RGW), иначе параметр `quota_gb`; нет обеих — ☮️ skip. Учётка бакета логов — у `tools_log_cleanup` |
| **`report`** | Сводка всех веток: вердикты, время ожидания, расхождения, покрытие версиями, выбросы парсинга; вердикт здоровья в XCom `health` |
| **`health_warn` / `health_errors`** | Итог плагина здоровья: ⚠️ немые сравнения, DAG больше 300 тасков, учётка S3 дагов от 80 %; ❌ дрожащая сериализация, учётка S3 дагов от 95 % — ран красный. Отчёт для `get_system_health` пишет `health_errors` |

**Исключения:** DAG'и с id по префиксам из `SKIP_DAG_PREFIXES` (сейчас `deadlocker_*`)
не проверяются вовсе — ни в статистике сериализации, ни в версиях, ни в покрытии.
Нагрузочный генератор переписывает свои DAG'и сам по себе, и в отчётах это шум.
Исключение не касается `parse_time`: он меряет разбор **файлов**, а не DAG'и по id.

**Массовое изменение (подробно).** После выкладки или обновления core меняется сериализация сотен
DAG'ов разом. Версии записываются все, а сравниваются первые `COMPARE_LIMIT`: остальные
идут в сводку числом и списком в XCom `not_compared`. У массового изменения расхождения
почти у всех одни и те же, а сотни экземпляров сравнения на часы заняли бы пул.

**Параметры:**

| Параметр | По умолчанию | Значение |
|---|---|---|
| `snapshot_limit` | `0` | Сколько DAG'ов обходить за прогон. `0` — все. Ненулевое включает ротацию: изменившиеся → без копии → с самой старой копией, полное покрытие за `ceil(всего / limit)` суток |
| `schedule` | `0 23 * * *` | Расписание; пусто — только вручную. Сохраняется вместе со `snapshot_limit` галочкой `save_params` |
| `quota_gb` | `0` | Квота учётки S3 с бакетом дагов (ГБ), если хранилище её не отдаёт; `0` — `s3_quota` пропускается. Сохраняется галочкой `save_params` |
| `cleanup_deleted` | `False` | Удалять ли версии DAG'ов, которых больше нет в `serialized_dag`. Выключено намеренно: пропажа чаще временная (Broken DAG, неудачный парсинг, `dag_stale_not_seen_duration`), и копия как раз тогда и нужна |

**Хранилище версий:**

```
dag_snapshots/<dag_id>/00001.<dag_hash>.json.gz
dag_snapshots/<dag_id>/00002.<dag_hash>.json.gz
```

Новая версия пишется **только когда сменился `dag_hash`** — если содержимое то же, объект не
плодится, и в истории остаются ровно те точки, где DAG менялся. `dag_hash` вынесен в имя
объекта: `list_objects_v2` пользовательские метаданные не отдаёт, и иначе на каждый DAG
пришлось бы качать последнюю копию, чтобы понять, изменилось ли что-нибудь.

Бакет и соединение — те же, что у логов задач (`[logging] remote_log_conn_id` /
`remote_base_log_folder`), префикс в корне бакета. Срок хранения у бакета один на всё
(`tools_log_cleanup`), поэтому последнюю версию неизменившегося DAG'а старше
`SNAP_REFRESH_DAYS` (7 дней) прогон переписывает на месте — номер и содержимое те же, дата
новая. Старые версии уходят по сроку сами. При ненулевом `snapshot_limit` полный круг
обхода обязан укладываться в 7 дней.

**Вердикты `compare_changed`** (сравниваются два неизменяемых объекта в S3, поэтому
результат воспроизводим — перезапуск таска через неделю покажет то же самое):

| Статус | | Значение |
|---|---|---|
| `changed` | 📝 | Есть расхождения — в отчёте пути |
| `same_json` | ✅ | `dag_hash` разный, а JSON совпал |
| `duplicate_dag_id` | 👯 | Сменился `fileloc` — два файла на один `dag_id` |
| `snapshot_broken` | ⚠️ | Версия не читается или не разбирается |

Если экземпляр сравнения упал и не оставил XCom, `report` считает его «немым» и пишет
об этом отдельной строкой: версия уже записана, поэтому следующий прогон этот DAG не
переоткроет — хэши совпадут. Чинится очисткой упавшего экземпляра: обе версии лежат
в S3, он перечитает те же объекты и выдаст тот же вердикт.

**Вердикты `recheck_serialized_dag`:**

| Статус | | Значение |
|---|---|---|
| `stable` | ✅ | `dag_hash` совпал — прошлое изменение было разовым (деплой) |
| `no_parse` | ⏱️ | Парсинга не дождались: очередь в dag-processor'е. Не падение |
| `unstable` | ❌ | Сериализация переписана снова — разбор файла недетерминирован |
| `duplicate_dag_id` | 👯 | Сменился `fileloc`: на один `dag_id` претендуют два файла и затирают сериализацию друг друга. Airflow такие коллизии между файлами не диагностирует — `AirflowDagDuplicatedIdException` срабатывает внутри одного `DagBag`, то есть одного файла |

Итог каждого экземпляра уходит в XCom `recheck` — до возможного падения, иначе у упавшего
таска не осталось бы return-значения. В списке mapped-тасков вместо `Map Index` `0,1,2…`
показывается `dag_id`.

### [test_kafka.py](test_kafka.py)
**Ручные проверки Kafka (`tools_test_kafka_snd` / `tools_test_kafka_rcv`).**

Два DAG'а для изолированной проверки связки: отправка одного сообщения в топик и просмотр
сообщений из топика.
*   ⚠️ Отправка идёт **мимо очереди** `export.er_sent_files`: файл не попадает в счётчики
    лимитов маршрута и не занимает пул отправителя. Для разовой проверки годится, для
    регулярной отправки нужен тракт, а не этот DAG.

Имена топиков TFS даны с его стороны, поэтому наши направления зеркальны:

| Действие | conn_id | Топик |
|---|---|---|
| пишем | `tfs-kafka-in` | `TFS.HRPLT.IN` |
| читаем | `tfs-kafka-out` | `TFS.HRPLT.OUT` |

Дефолты параметров расставлены по этой таблице; на запуске переопределяются.

⚠️ **Топики зависят от контура**: в таблице — сигма, на альфе маршрут ПКАП
(`TFS.PKAPHR.IN` / `TFS.PKAPHR.OUT`). Из `KAFKA_SND_TOPICS` их сюда не подставить —
этот даг выкладывается на оба контура, а `plugins/tfs_utils.py` живёт вместе с ЕР,
и жёсткий импорт сломал бы даг там, где тракта нет. На альфе топик задаётся руками.

**Параметры:**

| Параметр   | Описание |
|---|---|
| `conn_id`  | Airflow Kafka conn_id (kafka_config_id); выпадающий список — kafka-коннекты из Variable `local_connections`, её наполняет `tools_test_connections` (таск `collect`) |
| `topic`    | Имя топика |
| `message`  | Только write: текст сообщения, уходит как есть. Маркеры `{RqUID}` и `{RqTm}` заменяются при отправке; по умолчанию — `TransferFileCephRq` |
| `mode`     | Только read: `read_last` / `wait` |
| `timeout`  | Только read: сколько ждать сообщение, сек (окно read_last / poll_timeout) |
| `max_messages` | Только read: сколько последних сообщений читать в `read_last` |

**Режимы приёма** (`mode`):

*   `read_last` (по умолчанию) — читает последние `max_messages` сообщений, **уже лежащих**
    в топике (tail через seek к high_watermark−N), свежей consumer group без коммита offset.
    Порядок запуска не важен, в боевую группу не входит — ничего ни у кого не перехватывает.
*   `wait` — `ConsumeFromTopicOperator`: синхронно опрашивает топик на воркере, triggerer
    не требуется. Ловит только сообщения, опубликованные ПОСЛЕ старта опроса (consumer group,
    auto.offset.reset=latest), в пределах `timeout` секунд.
    ⚠️ Работает в consumer group коннекта, а у `tfs-kafka-out` она общая с боевым дагом
    `tfs_kafka_rcv` — единственным штатным потребителем этого топика. Сообщение,
    доставшееся тесту, до него уже не дойдёт, а значит и до выгрузки, которая ждёт
    квитанцию: топик `TFS.HRPLT.OUT` общий на все маршруты ТФС. Запускать здесь режим
    `wait` можно только при остановленном `tfs_kafka_rcv`.
    Прочитанные им квитанции лежат в `export.tfs_receipts` — обычно смотреть надо туда,
    а не в топик.

Запускать вручную (schedule=None). Для сквозной проверки: обоим DAG-ам поставить один топик
(`TFS.HRPLT.IN` — туда пишем мы, чужих слушателей там нет), и в режиме `wait` сначала
триггерить `tools_test_kafka_rcv`, а `tools_test_kafka_snd` — пока идёт опрос
(`timeout` секунд). Для `read_last` порядок любой.

### [mcp_skills.py](mcp_skills.py)
**Навыки агента для MCP-эндпоинта (`tools_mcp_skills`, раз в 30 минут).**

Кладёт навыки `*/skill/*.md` из каталога дагов (сейчас это `ctl_worker/skill/ctl-worker.md`)
в Variable `mcp_skill__<имя>`, оглавление — в `mcp_skills`. Эндпоинт вебсервера отдаёт их
ресурсами `airflow://skills` и `airflow://skill/<имя>`.
*   **Зачем через метабазу**: вебсервер даги из S3 не синхронизирует, его каталог дагов
    пуст, а S3 напрямую ему на сигме читать нельзя. Файлы есть у воркера — он и публикует.
*   **Пишет только изменившееся**, снимает навык, чей файл исчез. `testbed/` и скрытые
    каталоги пропускаются, файл больше 256 КБ — ошибка таска. **Одно имя у двух файлов**
    (навыки публикуют и другие команды) таск не роняет: публикуется уже опубликованный, иначе
    ближайший к корню, при равной глубине — первый по алфавиту пути; остальные — ⚠️ в заметке.
*   **Контракт с etl-core** (`mcp_skill.py`): ключи переменных меняются только вместе.
*   **Документация дагов** — второй таск `publish_docs`: остальные `.md` (README каталогов,
    QUICKSTART, ТЗ) в `docs/<путь>` бакета логов, оглавление с заголовками — в Variable `af_docs`.
    Их показывает пункт UI **Docs → DAG Docs** (etl-core, `plugins/dag_docs_plugin.py`).
    Не публикуются навыки (они уже есть), `CLAUDE.md`, `CONTEXT.md`, `openspec/`, `testbed/`.
*   **Тексты — в бакете логов с 25.09.2026**, на обоих контурах одним путём: вебсервер читает
    их через лог-сервер воркера. У записи оглавления поле `at` — когда записан текст; текст
    переписывается и при смене файла, и когда `at` старше `DOC_REFRESH_DAYS` (7 дней), чтобы не
    уйти по сроку `tools_log_cleanup`. Разовая галочка `purge_docs` удаляет оставшиеся с прежней
    схемы Variables `af_doc__*` (флага `store_docs` больше нет).

| Что | Где |
|---|---|
| Текст навыка `<имя>` | Variable `mcp_skill__<имя>` |
| Оглавление: имя → sha256, путь, размер | Variable `mcp_skills` (JSON) |

| Что | Где |
|---|---|
| Текст документа `<путь>` | `docs/<путь>` в корне бакета логов |
| Оглавление: путь → sha256, размер, заголовок, `at` (когда записан текст) | Variable `af_docs` (JSON) |

Навыки остаются в Variables: навык нужен и тогда, когда воркеров нет, а метабаза жива.

### [dummy.py](dummy.py)
**Задачи выполняются (`tools_dummy`, раз в час, `3 * * * *`).**

Два таска: `dummy_task` (`EmptyOperator`) шедулер отмечает успешным сам, до воркера он не
доходит — зелёный значит, что шедулер жив; `ping` — настоящая задача на воркере. В заметке
`ping` — под и две задержки: «шедулер» (конец `dummy_task` → `ping` в очереди) и «очередь»
(в очереди → старт на воркере). Красный по `dagrun_timeout` (50 мин, меньше интервала —
раны не копятся): какой таск не зелёный, то и стоит. Создаётся включённым.
До 28.09.2026 — ручной даг для проверки Markdown в UI, до 24.09.2026 — `dummy_dag` в
S3-инструментах альфы.

## Сохраняемые параметры

`db_cleanup`, `log_cleanup`, `log_events`, `system_health`, `pg_activity`, `mcp_skills`,
`paused_runs_cleanup`, `queue_analyze`, `test_connections` и `test_dags` берут значения по умолчанию из своей Airflow
Variable (`tools_<имя>_params`; у `pg_activity` — `tools_pg_activity_cfg`), а при её отсутствии —
из кода. Механизм общий — `saved_params`, `saved_schedule` и `store_params_task` в
`plugins/utils.py`; сохраняет отдельный таск `params` галочкой `save_params`. Variable записывается только запуском с галочкой
сохранения и только при изменившихся значениях: разовый эксперимент в UI ночное окно не
двигает, а осознанная правка двигает — без выкладки.

`schedule` — такой же сохраняемый параметр у всех перечисленных дагов; пусто или `None` — даг
только ручной. Сам запуск идёт по старому расписанию, новое
подхватывается со следующего разбора файла. Негодное значение таск не записывает (падает),
а уже записанное битым игнорируется в пользу кода — иначе разбор файла упал бы и убрал из
UI саму форму, через которую это чинят.

`queue_analyze` устроен так же (Variable `tools_queue_analyze_params`); расписание по
умолчанию `10 * * * *` (каждый час), а удаление из брокера (`purge`) — разовое, так что плановый
запуск только разбирает.

Разрушительные галки в Variable **не сохраняются** никогда — ни убийство сессий в
`pg_activity`, ни удаление из очереди в `queue_analyze`, ни `purge_docs` в `mcp_skills`: следующий запуск ничего не сделает
сам.

## Как запустить тесты

1.  Перейдите в Airflow UI.
2.  Найдите DAG `test_hrp_operators` (для операторов) или `test_connections` (для коннектов).
3.  Нажмите **Trigger DAG w/ config**.
4.  Для операторов: укажите целевые `conn_id` и бакет для тестов.
5.  Нажмите **Trigger**.

## Добавление новых тестов

При создании нового оператора в `hrp_operators`:
1.  Зарегистрируйте оператор в `sber_app_dataplatform_etl_core.hrp_operators.__init__`.
2.  Добавьте импорт и таск в соответствующую `task_group` внутри `test_hrp_operators.py`.
3.  Добавьте логику валидации данных после выполнения оператора.
4.  Убедитесь, что `cleanup` корректно удаляет все созданные артефакты.
